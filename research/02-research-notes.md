## 第一階段：現實世界問題（跨領域廣泛掃描，不先鎖定資安）

### 1-1 資訊安全 / SOC
- 分析師每班次面對 **1,000–5,000 則告警**，每天約 **3 小時**耗在人工 triage；企業級 SOC 每日 **10,000–15,000 則**，人工能處理的不到一半。[S1]
- Microsoft/Omdia《State of the SOC 2026》：**46% 告警是誤報**；分析師超過 **25% 時間**花在處理誤報。[S1]
- **76%** SOC 團隊把告警疲勞列為首要營運挑戰，**71–73%** 出現分析師 burnout，平均在職僅約 2 年。[S1]
- 組織平均要看 **10.9 個資安主控台**，69% 部署 10 種以上偵測工具。[S1]
- 美國每年人工告警 triage 成本估 **33 億美元**。[S1]

### 1-2 使用者回報釣魚郵件
- 一次釣魚活動打到 300 人 → 產生 **300 份各自獨立的回報**；其中約 **80–85% 根本不是威脅**（電子報、內部通知、廠商信）。分析師整個班次前段都在確認「這些不是威脅」。[S3]
- 2025 年 IC3 通報網路犯罪損失 **209 億美元**，其中 BEC＋釣魚＋冒名政府合計超過 40 億，年增 46%。[S3]

### 1-3 系統維運 / SRE
- 現代分散式系統中「症狀」與「根因」可能跨多個服務、多個團隊、多套工具；**找出 why 的時間遠大於 fix 的時間**。傳統可觀測性工具要工程師手動關聯 metrics / logs / traces / 最近的變更。[S4]
- 告警疲勞會埋掉真事件，延後確認與調查，直接墊高 MTTR。[S4]

### 1-4 網路 / 系統組態
- 組態錯誤（misconfiguration）已是系統故障的**主要成因之一**，造成大量嚴重服務中斷。[S5]
- 診斷複雜組態問題通常從「使用者抱怨」或「管理員察覺」開始，接著是**大量人工判斷要跑哪些測試**。[S5]

### 1-5 公部門陳情 / 環保稽查
- 臺南市環保局公害陳情稽查**每月平均近 1,800 件**，平均 20 分鐘就 1 件；類型前三名為空污、環境衛生、噪音。[S6]
- 高雄市**約 80 人每月扛 2,000 件**環保公害陳情案；台東縣**全縣僅 5 名稽查員**。[S6]
- 異味類案件常因風向與上升氣流，稽查人員**無法在有效時間內查獲污染源**；郊區、農田無監視器可調閱。[S6]
- 臺北市 1999／陳情系統整合市政信箱、1999 熱線、臨櫃與電話陳情，**案件需分類、派工、跨機關轉辦**；結案回報若走公文相對耗時。[S7]

### 1-6 道路 / 公共設施通報
- 全民督工 App、各縣市「路平報馬仔」等系統開放民眾拍照通報；通報項目含坑洞、龜裂、凹陷、人手孔蓋破損、標線不清等，**需人工判讀屬於哪一類、屬於哪個權管單位**。[S8]

### 1-7 農業
- 全台設 **26 處作物病蟲害診斷服務站**＋0800 專線，但**農改場與農會業務繁多，農友常無法即時取得協助**。[S9]
- 農友實務上常直接問農藥行；政府正在推動植物醫師制度，以解決「田間判定病蟲害、開處方、精準用藥」的人力缺口。[S9]

### 1-8 高齡用藥
- 65 歲以上長者平均同時服用 **5–8 種藥**，超過 1/4 同時使用 **10 種以上**。[S10]
- 家屬普遍不知道多種藥之間是否交互作用、長輩常忘記吃或重複服用；藥師難以走進長輩生活場域，用藥風險缺乏專業介入。[S10]

### 1-9 防災資訊
- 中央與地方各自開發防災 App，**資訊過度分散、平台林立**，民眾要下載不同系統才拿得到資訊。[S11]
- 災情資料來自政府回報系統、民眾社群上傳等**不同管道**，若無法整合比對視覺化，災情判斷會產生落差。[S11]

### 1-10 開源維護 / 開發者工具
- 絕大多數開源專案由 **1–2 人**維護；issue triage 已取代寫程式成為維護者主要工作，AI 讓通知更多、佇列更長。[S12]
- 最煩瑣的環節之一就是**正確分類進來的 issue**；自動 labeling 被視為主要解法（Dosu 等產品即以此為賣點）。[S12]

### 1-11 其他掃描到但證據較弱的領域
- 製造業設備維修工單非結構化、老師傅經驗傳承：**搜尋僅得到表單範本，找不到可公開取得的實務資料集** → 資料面高風險。[S13]
- 工地安全巡檢：有標準表單（工程會 110.05.11 修正「工地職業安全衛生施工前檢查紀錄表」）與缺失改善對策表，**表單是公開的，但實際巡檢紀錄不公開**。[S14]
- 政府採購招標公告：政府電子採購網有招標／決標查詢與全文檢索，資格與條款複雜、廠商需逐案閱讀。[S15]
- 客訴分類：中小企業仍靠電話追蹤與人工記錄，進度與權責不清。[S16]

## 第二階段：目前怎麼被處理（工作流程與痛點）

| 領域 | 現在誰做 | 用什麼 | 缺點 |
|------|----------|--------|------|
| SOC 告警 | L1 分析師 | SIEM ＋ 平均 10.9 個主控台 | 46% 誤報、每班上千則、平均 2 年就離職 [S1] |
| 釣魚回報 | L1 分析師 | 郵件佇列、人工開信 | 80–85% 是雜訊，同一波 campaign 重複查 [S3] |
| 系統故障 | on-call 工程師 | Grafana/Kibana 手動關聯 | 找根因比修好還久 [S4] |
| 環保陳情 | 稽查員 | 電話派工、現場稽查 | 20 分鐘一件、異味到現場已消散 [S6] |
| 1999 陳情 | 話務＋研考人員 | 人工分類派工 | 跨機關轉辦、公文回報慢 [S7] |
| 病蟲害 | 農改場／農會／農藥行 | 電話、送樣、圖鑑 | 無法即時、答案品質取決於問到誰 [S9] |
| 長者用藥 | 家屬／藥師 | 分散的查詢網站 | 家屬看不懂、藥師進不去家庭 [S10] |
| 開源 issue | 1–2 名維護者 | 手動貼 label | 無償、夜間假日做 triage [S12] |

**共同結構：**「大量非結構化文字 → 人工閱讀 → 分類／抽取關鍵欄位 → 判斷嚴重度 → 決定給誰 → 寫成結構化紀錄」。
這正是 LLM 的語意理解 ＋ 資訊抽取 ＋ 分類 ＋ 結構化輸出可以切入的位置。

## 第三階段：實際應用價值與商業價值（在選 Top 20 之前完成）

- **可量化的成本**：人工 triage 在美國一年 33 億美元 [S1]；高雄環保稽查一人月扛 25 件（2000/80）[S6]。
- **既有商業產品存在＝需求已被市場驗證**：Cofense Triage、Hoxhunt、Torq、Panther、Rootly、Dosu（開源 issue 自動分類）皆為商業／服務化產品 [S2][S3][S12]。
  → 代表這些題目**不是我們憑空想像的需求**。
- **既有產品的不足**：多為訂閱制、綁定特定 SIEM／雲、對中文與台灣在地情境支援弱、中小企業與地方政府買不起。
  → 我們的差異化定位：**開源自架 ＋ 中文在地資料 ＋ 小模型可離線 ＋ 可稽核的結構化輸出**。

## 第五階段：LLM / Hugging Face 技術可行性

- **QLoRA 微調 1B–3B 模型在 Colab 免費 T4（16GB）上完全可行**；4-bit 量化下 3B 模型可完整放進 GPU 不需 offload；社群案例顯示該級別微調可在**約 18 分鐘～數小時**完成。[S27]
- **3–4B 級距中 Qwen3 4B 表現優於 Gemma 3 4B 與 Llama 3.2 3B**；訓練資料含較多程式與結構化資料的模型，在 tool-calling 與資訊抽取上開箱表現較好。[S28]
- **JSON Schema 約束（grammar-constrained decoding）可保證輸出格式合法**，模型好壞只影響內容正確性而非格式合法性。Llama-3.2 3B 未微調時 JSON schema 任務表現差，**微調後顯著改善**。[S28]
- **分類任務不一定要用生成式 LLM**：ModernBERT 等 encoder 模型在中小資料量分類上**贏過 zero-shot 生成式模型**，吞吐量約 93 samples/s，相對 LLM 的 1–5 samples/s。[S29]
  → 對「大量告警／陳情自動分類」這種高吞吐任務，**encoder 分類器 ＋ 生成式 LLM 做解釋**的雙模型架構最務實，
    而且天然形成「Base vs Fine-tuned 可量化比較」的評測設計。

**Fine-tuning 資料量警訊：** 790 筆足以訓練輕量分類頭，但**不足以微調 7B 模型而不嚴重過擬合**；
穩定微調通常需要 **5,000–100,000 筆**領域指令對。小資料集微調常見「train loss 降但品質沒升」。[S30]
→ 我們的策略必須是：**小模型（≤4B）＋ LoRA/QLoRA ＋ 數千筆（含合成擴增）**，而不是硬微調 7B。

## 第六階段：Raspberry Pi / Edge 可行性（實測數據）

- Raspberry Pi 5 (8GB) CPU-only 推論：**1.5B 模型約 5–15 tok/s；3B 模型約 2–5 tok/s**；社群另有 1B 約 10–15 tok/s、3B 約 4–7 tok/s 的數據。[S31]
- **8GB 是跑 2–3B 級距＋合理 context 的實務下限**；Pi 5 (8GB) 的舒適區間是 **1–2B 量化模型、每秒數 token**，足以做 **routing、分類、小型 agent**。[S31]

**推論（直接寫進限制）：**
1. **主推論不能放 Pi。** Pi 適合：資料採集、本地前處理、輕量分類／路由、MQTT gateway、Linux endpoint、離線降級模式。
2. 若題目要求「即時互動式問答」，Pi 上 3B 模型每秒 2–5 token ≈ 一句話要等十幾秒，**Demo 會很難看** → 該類題目 Pi 只能當前端／採集端。
3. Docker 在 Pi 上最大的坑是**架構不符**：x86 build 丟到 arm64 會 `exec format error`；要用 `docker buildx --platform linux/amd64,linux/arm64`；QEMU 模擬慢 5–20 倍，且**模擬會掩蓋真機才會出現的問題**。[S32]

## 第七階段：Function Calling 可行性與風險

- BFCL 評估的核心就是「給 function schema ＋ 使用者問題，模型要**選對函式並填對參數**」。[S33]
- **Relevance Detection** 指標專門量測「當沒有任何函式相關時，模型會不會硬叫工具」→ 這正是幻覺工具呼叫的量化方式。[S33]
- **小模型 function calling 落差極大**：2.5B 級模型 BFCL-v2 約 55%，某些 7B 模型只有 12%。[S33]
- **多輪比單輪掉 5–10 分**（所有模型皆然）。[S33]

**推論：**
1. FC 版本必須**用雲端／較大模型，或經過 FC 微調的模型**來做決策，不能直接丟給 Pi 上的 1.5B。
2. FC 的價值只有在「**資訊必須即時去外部查、而且查哪個來源要看情況決定**」時才成立。
   若所有資料都能事先塞給模型，FC 是純成本。
3. FC 版必須額外做：工具 schema 設計、參數驗證、錯誤重試、選錯工具的 fallback、**Relevance Detection 測試**。
   工程成本估 **+3～5 人日**，一個月專題可以吸收，但**只有在題目真的需要時才值得**。

## 第八階段：實際工程失敗案例（提前知道會死在哪）

| 風險 | 具體證據 | 對策 |
|------|----------|------|
| 微調資料太少→過擬合 | 790 筆不足以微調 7B；需 5k–100k [S30] | 縮小模型到 ≤4B、用 LoRA、合成資料擴增、留 held-out set |
| 微調產出亂碼 | 教學案例：格式沒對齊、缺 special token、生成參數錯 → 全是亂碼 [S30] | 固定 chat template、先跑 10 筆 smoke test |
| 結構化輸出失敗 | 未微調的 3B 在 JSON schema 任務表現差 [S28] | grammar／JSON schema 約束解碼 ＋ 重試 |
| 工具選錯／參數錯 | 小模型 BFCL 僅 12–55%；多輪再掉 5–10 分 [S33] | 限制工具數量（≤5）、參數用 enum、加驗證層 |
| Pi 效能不足 | 3B 在 Pi 5 僅 2–5 tok/s [S31] | 主推論上雲／PC，Pi 只做採集與輕量分類 |
| Docker 架構不符 | x86→arm64 `exec format error`；QEMU 慢 5–20 倍且掩蓋真機問題 [S32] | buildx 多架構、真機至少跑一次驗證 |
| API 限流 | NVD 無 key 30 秒 5 次 [S25]；環境部 API 每次 1,000 筆 [S17]；TDX 未註冊 50 次/日 [S18] | 全部先落地成本地快取／資料庫，Demo 時不打線上 API |
| 資料其實拿不到 | 1999 逐案內文、工單、巡檢紀錄皆不公開 [S7][S13][S14] | 這類題目一律降權，或改成自建標註集 |

## 第九階段：論文與技術研究（確認方法與評測方式，不是抄標題）

- **LLM4Log（2026）**：系統性回顧 LLM 在日誌分析的完整流程（logging 生成、log parsing、異常偵測、失效預測、**根因分析**、摘要），涵蓋 145 篇論文、7 類任務。[S34]
- **LogEval（2024）**：日誌分析 benchmark，涵蓋 log parsing、異常偵測、故障診斷、摘要，每任務 4,000 筆公開日誌、15 種 prompt。→ **可直接借用其評測任務設計。**[S34]
- **LogPrompt**：以 prompt engineering 引導 LLM 做可解釋的日誌異常偵測，**zero-shot 即勝過傳統深度學習方法**，強調產出自然語言解釋。→ 這是我們「Base model 也要能跑」的依據。[S34]
- **LogSage（2025）**：CI/CD 失敗偵測與修復，**是唯一支援「可解釋根因分析→自動執行解法」完整鏈路**的方法。[S34]
- **Fine-tuned 小模型 vs zero-shot 生成式模型**：在有適量訓練資料時，微調的小型 BERT 系模型在四項應用上**全面勝過 zero-shot 的 ChatGPT/Claude**。[S29]
  → **這是我們「為什麼要 fine-tune」最強的引用依據，也是 Base vs Fine-tuned 量化比較的正當性來源。**

# 補搜：影像能力納入後的第二輪研究

> 起因：初版需求分析完成後才得知明樺具備影像辨識經驗。
> 由於第一輪的搜尋問題（Q1「大量人工**閱讀**」）本身偏向文字，
> 必須把問題改寫成 Q1′「哪些工作仍需要人**親眼看、目視判讀、現場檢查**」並重新搜尋。

## 補-1 目視與紙本類的現實問題

- **紙本表單人工鍵入**：某高分子材料廠日均產生 **800 餘張手寫檢測單，3 名員工需 6 小時**才能完成錄入；金融業複雜報銷單**人工錄入單張平均逾 30 分鐘** [S36]
- **手寫報表延遲**：傳統工廠依賴手寫報表記錄每日生產數據，文書人員隔日才輸入系統，導致**產銷會議使用的數據已過時** [S36]
- **公文處理**：紙本公文資料多由人工輸入，面對大量紙本時容易在**分文、編號、登錄**出現疏失；以**一單位一年近 20 萬件**公文計算，每份平均縮短 4 小時辦文時間，**一年可減少 80 萬小時** [S40]
- **憑證報帳**：報銷流程涉及蒐集、簽核、入帳、對帳、匯款、歸檔，順利需 **7–10 個工作天**，不順利可長達一個月；規模一大，**每月處理請款要燒掉一個會計近一半工時** [S41]
- **人工目視檢測**：某電子製造企業焊接後檢測依賴人工目視，**誤判率一度高達 20% 以上**；長時間觀看造成視覺疲勞、細緻度不足 [S37]
- **人工抄表**：台水抄表員逐戶步行抄錄，水表常位於屋頂；抄表環境可能是昏暗地下室、狹窄管道間甚至危險化學設施，有安全風險。台電已與台水合作推動智慧電表，**方向是用通訊模組取代人工，而非用影像辨識** [S44]

## 補-2 影像相關的公開資料（查證結果）

| 資料 | 內容 | 可得性 | 適用性 |
|------|------|--------|--------|
| 繁體中文文字辨識資料集 | 玉山開源的繁中 OCR 辨識集 | **公開** | 通用文字，非特定表單 [S38] |
| 繁體中文手寫資料集 | AI-FREE Team 開源手寫集（非商業授權） | **公開** | 手寫單字，非完整表單 [S38] |
| JVZY 文件退化資料集 | 2 萬張影像、192 萬字，含注音與文件退化特徵 | **公開** | 文件影像增強 [S38] |
| TC-STR 7k | 約 1,554 張真實場景影像、7,543 個裁切文字 | **公開** | 場景文字 [S38] |
| FUNSD | **199 張**完整標註掃描表單，支援文字偵測、版面分析、實體標註 | **公開** | 表單理解的標準基準 [S43] |
| DocVQA / SROIE / CORD / RVL-CDIP | 文件問答、收據、票據、文件分類 | **公開** | 英文為主 [S43] |
| 台灣特定領域標註影像（病害、工安、通報） | — | **查無公開標註集** | 農業開放平臺提供的是資料而非標註影像 [S23] |

> **這一項推翻了初版的一個假設。** 初版寫「影像類沒有可用的公開資料」是錯的——
> **通用的繁中 OCR 與表單理解資料集確實存在**。
> 但**特定領域的標註影像（田間病害、工地缺失、道路缺失）仍然查無公開集**，
> 這才是真正的瓶頸。

## 補-3 影像模型的技術可行性（推翻第二個假設）

- **Qwen2.5-VL 提供 3B / 7B / 72B 三種尺寸，並有量化版本**；官方與社群皆有微調程式碼 [S42]
- **在免費 Colab T4 上可行**：需停用 Flash Attention（僅支援 Ampere 以後架構），並使用適合 8GB 顯存的像素設定；LLaMA Factory 提供免費 T4 的 Colab notebook [S42]
- 文件理解方面，LayoutLMv3 BASE 在相關基準上達 **F1 0.9029** [S43]

> **這推翻了初版「多模態微調成本遠超免費雲端資源」的說法。**
> 3B 級的視覺語言模型在免費 T4 上是可以微調的。
> 因此拒絕影像題目的理由**不能再用「跑不動」**，必須改用真正的理由：
> **特定領域的標註影像拿不到，而且影像模型不是 LLM。**

## 補-4 樹莓派加相機的實測效能

- 無加速器：物件偵測 **5–8 FPS**（640×640）；降到 416×416 的 nano 模型可達 **10–12 FPS** [S45]
- 語言模型：Gemma 2B INT4 約 **8–15 tokens/s** [S45]
- 支援的實際應用包含物件偵測、影像分類、**植物病害辨識**、**文字辨識** [S45]
- 加裝 AI 加速模組後可達 30 FPS 以上 [S45]

> **視覺推論在樹莓派上是可行的**（與語言模型不同，影像分類對算力的需求低得多）。
> 因此「樹莓派不能做影像」的說法不成立。
> 但這**不改變結論**——限制在資料與 LLM 主軸，不在算力。

## 補-5 既有產品查證

- **藥袋 AI 辨識已有現成產品**：AI記藥王（拍藥袋自動辨識藥名、劑量、服用方式，長輩友善大字體介面）、衛福部食藥署「藥掃描」App（掃條碼查仿單、外盒、外觀）[S39]

> 而目視檢測類題目要與成熟的 AOI 產業競爭。
