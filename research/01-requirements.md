# 階段零：需求分析與團隊資源限制分析（先於任何搜尋）

> 本文件在「執行任何一次網路搜尋之前」完成。目的是把「我們是誰、我們有什麼、我們不能做什麼」
> 轉換成「應該去調查什麼問題」，而不是一開始就去搜尋現成的專題題目清單。

## 1. 任務硬性條件（不可協商）

| # | 條件 | 判定意義 |
|---|------|----------|
| R1 | 製作時間 **1 個月** | 任何需要長期資料蒐集、長期硬體驗證、長期標註的題目直接淘汰 |
| R2 | **LLM 必須是主軸**，不是點綴 | 必須能回答「以往是誰用什麼方式做、為何 LLM 能做得更好」 |
| R3 | **全端系統** | 需要前端 + 後端 + 資料層，不能只是一個 notebook |
| R4 | **必須經歷部署、必須有 Docker** | 題目必須可容器化；不能依賴無法容器化的專用驅動 |
| R5 | 呈現方式不限，但**要能 Demo** | 評審能在 5–10 分鐘內看懂並看到結果 |
| R6 | **四人都必須有 LLM 實作成分** | 題目必須能切成 4 條含 LLM 的工作線 |
| R7 | 需同時產出 **不使用 / 使用 Function Calling** 兩種版本的分析 | 題目必須存在「模型需要主動取得外部資訊」的真實需求，否則 FC 版會很牽強 |
| R8 | 要**容易被一般人理解**、要有**實際應用價值與商業價值** | 純學術玩具題淘汰 |

## 2. 團隊能力盤點（依履歷與描述，非臆測）

| 成員 | 背景 | 可承擔 | 不可承擔 |
|------|------|--------|----------|
| **冠文（隊長）** | 明新科大資工 2026/6 畢；役畢；退伍後約 1.5 年後端實作。FastAPI+Uvicorn、Flask、MySQL、Redis、MongoDB Atlas；**Docker + Render 實際部署過**；**Anthropic Tool Use（Function Calling）兩輪架構、強制結構化輸出實戰**；React/Vite 接觸過；TQC+ 機器學習專業級；曾任四人專案隊長 | 架構設計、樹莓派實作、後端主幹、FC/結構化輸出、部署、帶人 | 無法同時當四個人用；不能把整份工程壓在一人身上 |
| **明樺** | 資工科班，**有影像辨識經驗**，但**無實際專案開發經驗** | 模型訓練與評測（比一般新手能扛更重的評測責任）、資料前處理、影像相關任務、Python 腳本 | 不能獨立設計架構、不能負責關鍵路徑 |
| **囷洧** | 非資訊本科（環工），**無專案經驗**，時間被兼職切碎 | 領域知識（環境法規/水質空品/稽查流程）、資料蒐集、標註規則制定、Prompt 設計、人工評分 | 不能負責需要長時間連續投入的工程 |
| **宇傑** | 有電腦軟體工作經驗但**無專案開發經驗** | 前端整合（在既有骨架上修改）、測試、文件、Demo 腳本、邊界清楚的獨立模組 | 不能負責模型訓練核心 |

**推論：** 團隊實際「可交付工程量」約等於 **1 名中階後端 + 3 名需要被明確指派任務的新手**。
題目複雜度上限必須壓在「**一條主線 + 三條可平行、低耦合的支線**」。

### 2-1 補充：明樺的影像辨識經驗（後補資訊）

這項能力是在初版需求分析完成後才補充的，因此獨立記錄它對評估的影響：

**不改變的兩個硬限制**
1. **沒有 GPU。** 影像模型的訓練與推論成本不會因為有人會做就消失。
2. **只有一個月。** 多模態要多一條資料蒐集與標註線。

**不改變排名的根本理由**
任務要求明訂「**LLM 必須是主軸**」。影像辨識模型不是 LLM——把影像放進來，反而會**稀釋 LLM 的核心性**（評分項 E3）。
因此影像能力天生只能是配角，不可能翻轉任何一題的排名。

**實際產生的三個影響**
1. **明樺的角色升級**：從「跑別人寫好的訓練腳本」變成「能獨立負責模型訓練與評測」，這讓每一題的 E5（微調與可量化評測）都更站得住——但這是**齊頭加分**，不改變相對排序。
2. **第 4 題（病蟲害）多了一條第二階段路徑**：純文字版做完、評測有數字之後，才由明樺加影像輔助判斷。
3. **C19（道路通報）的落選理由需要修正**：主因是**查不到可下載的通報案件語料**，不是團隊不會做影像。加上影像後它的分數**不會上升**——E4 資料仍是 7、E6 完成度會下降、E8 也不會加分，因為影像不是 LLM 工作。

### 2-2 補充：樹莓派加相機，值不值得？

有了影像能力之後，很自然會想「那是不是很多題都可以加樹莓派的影像輸入」。
逐題檢查後，答案是**不會變多，仍然只有一題**。原因是要同時滿足三個條件：

| 條件 | 為什麼是必要的 |
|------|----------------|
| **1. 需要定點、連續、無人值守的取像** | 若是使用者自己拿起來拍（藥袋、道路缺失、作物葉片），**手機就夠了**，加樹莓派只是增加成本與故障點 |
| **2. 影像只做前處理** | 判斷仍須由語言模型負責，否則違反「LLM 必須是主軸」 |
| **3. 標註影像資料拿得到** | 一個月內要自己拍、自己標一套可訓練的影像集，幾乎不可能 |

**逐題篩選結果**

| 題目 | 條件 1 | 條件 2 | 條件 3 | 結論 |
|------|:------:|:------:|:------:|------|
| 4 作物病蟲害 | ✓ 田間定點 | ✓ | ✗ 田間病害影像須自拍自標 | **第二階段可加，第一個月不行** |
| 7 環保陳情 | ✓ 現場節點 | ✓ | ✗ 違規燃燒影像拍不到 | 不採用 |
| 19 空品事件 | ✓ 補點 | △ 影像貢獻低 | ✗ | 不採用 |
| 1 長者用藥 | ✗ 使用者自己拍 | ✓ | — | **要相機但不要樹莓派**（手機即可） |
| 5 標案公告 | ✗ 文件在電腦上 | ✓ | — | 只需文件文字擷取，無取像需求 |
| 其餘 15 題 | ✗ | — | — | 沒有取像需求 |

**修正一個先前判斷過快的說法：** 初版寫「未提供相機模組」，把它當成硬體限制。
實際上樹莓派相機模組取得容易、成本低，**硬體不是真正的門檻**。
真正的門檻是**條件 3——標註影像資料**。這個修正不改變結論，但理由必須寫對。

**因此樹莓派的使用情形維持不變：** 1 題核心、5 題選配、14 題明確不需要。
第 4 題新增一條「第二階段加樹莓派與相機」的擴充路徑，但不列入第一個月的必達範圍。

## 3. 硬體與運算資源盤點

- **樹莓派：任務描述為「我有一塊」，初步構想又提到「有數枚」→ 保守以 1 塊可用板子規劃**，
  任何需要多節點同時上線才成立的題目要降權。
- 其餘成員只有**一般 PC**，**沒有明確提供 GPU**。
- **未提供**：Jetson、PLC、工業相機、感測器套件、MCU、示波器、專用網路設備。
  → 任何需要上述硬體的題目，除非該硬體是「百元等級、台灣現貨、免驅動」，否則淘汰。
- 可用的免費算力：Google Colab（T4，有時數限制）、Hugging Face 免費資源、雲端免費層（Render Free）。

**推論：**
1. **大型模型訓練與推論必須放在 PC / Colab / Cloud**，樹莓派只能做 Edge/Embedded 的合理工作
   （資料採集、本地前處理、輕量分類、MQTT gateway、Linux endpoint）。
2. 若題目其實不需要樹莓派，**不應為了用掉板子而硬加**（R-Pi 是加分項不是必要項）。
3. 類比訊號採集有不確定性（雜訊、校正、接線），**任何依賴類比感測器精度的題目風險極高**，
   1 個月內容易卡在硬體除錯而非 LLM。

## 4. 由限制反推「要調查什麼」（搜尋問題清單）

> 這些是接下來要拿去搜尋的**問題**，不是要拿去搜尋的**題目**。

**Q1（現實問題）** 哪些行業/職務目前仍存在「大量人工閱讀、判斷、分類、整理、排查」的工作？
**Q2（工作流程）** 這些工作現在由誰做、用什麼工具做、一件要花多久、錯誤率如何？
**Q3（LLM 切入點）** 這些工作中，哪一段是「語意理解 / 資訊抽取 / 分類 / 多來源整合 / RCA / 結構化輸出」可以真正取代或加速的？
**Q4（使用者）** 有沒有明確、可指認、數量足夠的目標使用者？他們為什麼願意換掉現有做法？
**Q5（既有方案）** 現在市場上已經有什麼產品在做？它們的不足在哪？我們的差異點是什麼？
**Q6（資料）** 台灣有沒有**真的可以下載**的公開資料/API 能支撐 Dataset、Fine-tuning、Demo？授權、頻率、是否要 API Key？
**Q7（模型）** 這題適合哪一種模型（分類/抽取/生成/SLM）？多大？PC 或 Colab 能不能 fine-tune 完？
**Q8（評測）** Base model 與 fine-tuned model 能不能做出**可量化**的比較？指標是什麼？
**Q9（樹莓派）** 這題的 Pi 到底負責什麼？CPU/RAM 夠不夠？要不要額外硬體？取得難度與成本？
**Q10（FC）** 這題是否真的存在「模型需要主動去查外部狀態」的需求？不用 FC 能不能完整成立？加 FC 多花多少工？
**Q11（失敗風險）** 別人做類似東西時最常死在哪裡？（幻覺、資料品質、API 限流、Pi 資源、Docker、延遲）
**Q12（工程可行性）** GitHub 上有沒有可參考的實作證明這條路走得通？授權可用嗎？

## 5. 淘汰紅線（在候選池階段就會用到）

1. 沒有明確使用者 → 淘汰
2. 需要未提供的硬體 → 淘汰
3. Dataset 只存在於「假設」而非「查證過的下載連結」 → 淘汰
4. LLM 只是包裝、拿掉 LLM 系統照樣成立 → 淘汰
5. 無法在 1 個月內做出可 Demo 的完整鏈路 → 淘汰
6. 無法切出 4 條含 LLM 的工作線 → 降權
7. 依賴類比感測器精度或長期佈點才成立 → 降權/淘汰
8. 一般人聽完 30 秒還聽不懂在解決什麼 → 降權
