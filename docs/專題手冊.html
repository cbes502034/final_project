家庭記帳與財務控管系統

以家庭為單位的記帳系統：每個人有自己的帳本，父母看得到未成年子女的消費， 一個 master 帳號做集中管理。LLM 的位置不在「產生建議」，而在 把一段話拆成好幾筆帳——那是這個系統最容易被放棄的環節，也是規則寫不完的地方。

01

源起

主題換過三次。最後選記帳，不是因為它最酷，是因為四個人都對它有共鳴—— 每個人都記過帳，也都放棄過。這件事比題目本身更重要：組員講得出使用情境， 討論才會有內容。

硬性要求：LLM 必須是主軸

如果 LLM 只用來產生財務建議，會有一個致命問題——把 LLM 拿掉，系統照樣能跑。 記帳、統計、圖表、預算全都不需要模型。評審一定會問這題。

解法：把 LLM 放在「記一筆帳」這個動作上

記帳 App 最大的失敗原因不是功能不夠，是懶得輸入。 選分類、填金額、挑日期、打店名——摩擦一高，兩週後就放棄。 讓使用者寫一段話就好，摩擦才降得下來。

為什麼規則式做不到

難點例子規則寫得出來嗎
相對日期今天午餐吃了120 / 昨天加油勉強
中文數字媽媽給我兩千勉強
店名歧義在全家買飲料165 ← 是店名，不是家人做不到
收支方向媽媽給我兩千 → 是收入不是支出做不到
語意分類便利商店算餐飲還是日用品？做不到
合計語意三個平台訂閱費共3400做不到
段落切分一段話裡到底有幾筆帳做不到

每個人的講法都不一樣，規則永遠寫不完。 這就是 LLM 在本系統不可取代的位置。

資料飛輪

使用者每修正一次解析結果，就等於免費標了一筆訓練資料。這些修正存進 nlp_parses，同時是評測的來源與下一輪的訓練資料。 用得越久 → 資料越多 → 模型越準 → 摩擦越低。

LLM 的三個用途，依重要性排序

#用途拿掉會怎樣評測指標
1段落記帳（文字 → 結構化欄位）系統回到手動輸入，核心價值消失一次輸入完全正確率
2消費自動分類使用者每筆都要自己選分類分類 Macro-F1
3財務控管建議少一個加值功能，系統還能用建議可用性評分
02

專案說明

一句話：以家庭為單位的記帳系統，用自然語言降低輸入摩擦，用月／年兩個時間準據做財務控管。

系統要做到的四件事

  • 每個人有自己的帳本，資料互不混雜
  • 子女的消費同步給監管者，由 master 集中管理
  • 月、年兩個時間準據做統整
  • LLM 抓出收支狀況，產生財務控管建議

三個設計原則

  • 模型不直接寫資料庫：解析與寫入分兩步，中間一定有人確認
  • 金額一律由後端算：模型只負責敘述，每條建議附可驗算的依據
  • 監管雙向可見：系統不提供「隱藏監管」選項

選型的四個前提

限制造成的影響
只有一個月不能有學習曲線陡的東西。每個新框架都要換算成「幾天學會」
四人中三人沒有專案經驗工具要好上手、錯誤訊息看得懂、查得到中文資料
一人有 FastAPI / Docker / Render 實戰後端主幹沿用熟悉的，不為了「更好」而換
沒有 GPU模型只能用 API，或在 Colab 免費 T4 上微調小模型
選型原則：能不加的就不加

每多一個相依，就多一個可能在最後一週爆炸的點。這句話是後面所有「不用某某技術」的共同理由。

三週排程

W1
前後端整合完畢
四個模組各自把「資料表 → API → 畫面」串通。這週結束時系統要能跑，只是還沒有模型。重點是「串通」不是「做完」——按得下去、打得到 API、寫得進資料庫、顯示得出來，就算成功。
W2
LLM 製作
各人在自己的分支、自己的模組裡接上模型，做自己那部分的 prompt 與微調。
W3
LLM 改善／加強功能
評測、迭代。行有餘力再加功能。
第 1 週要凍結的三份契約

分類體系（成員3 定，成員2 寫進 prompt、成員4 做建議要用）—— 這是唯一的跨模組阻塞點。
API 回應形狀（各模組自己定，但要寫進 js/api.js）
解析結果的 JSON Schema（成員2 + 成員1，模型呼叫層要照這個驗）

系統不提供「隱藏監管」的選項。偷偷監看家人的消費會破壞信任， 而信任正是家庭記帳能持續下去的前提。

C · 記帳（核心）

#功能說明優先
C1段落記帳寫一整段話 → 模型切成 N 筆，逐筆抽欄位M 核心
C2單句記帳一句話 → 一筆M 核心
C3解析結果確認逐欄顯示信心度，使用者確認後才寫入M 核心
C4缺欄位標記缺什麼就標在那一欄上（紅框 + 必填），補齊前送出鈕停用M 核心
C5低信心提示信心 < 85% 的欄位標黃並說明原因M 核心
C6記錄修正使用者改了什麼要存起來，這是訓練資料M 核心
C7兩種模式互斥段落記帳／單筆手動，選定一種另一種停用M
C8單筆手動記帳傳統表單，不經過模型，走 POST /api/transactionsM
C9編輯／刪除修改既有紀錄M
C10分類體系系統預設 + 家庭自訂，支援兩層M
C11帳戶管理現金／銀行／信用卡／悠遊卡S
C12CSV 匯入從銀行帳單匯入S
C13收據拍照 OCR辨識金額。第二階段，不進第一版S
切分比抽欄位更難發現錯誤

模型要先判斷一段話裡有幾筆。切錯（把兩筆合成一筆）比抽錯更難發現—— 欄位再準也沒用。所以畫面上每一列都標出它對應原句的哪一段， 切分結果同樣要讓使用者確認。

D · 統計與預算

#功能說明優先
D1月統計收入、支出、結餘、儲蓄率M
D2年統計同上。當年度要標示「未完整」M
D3分類佔比圓環圖M
D4趨勢圖近 6 個月收支對照M
D5月預算依分類設上限，超支變紅M
D6家庭總覽各成員本月狀況、超支項目M
D7每月存款目標註冊時就要填。改動保留歷史不覆蓋M
D8超支警告三級：達標中／接近上限／存不到目標M
D9年預算同 D5S
D10匯出報表CSV / PDFS

存款目標怎麼算

可支配上限 = 本月收入 − 每月存款目標
使用率 = 支出 ÷ 可支配上限

使用率 < 80%   → 達標中
80% ~ 100%     → 接近上限
> 100%          → 存不到目標，算出短少多少
家庭總數會蓋掉個人的問題

結餘多的成員會把其他人的超支蓋過去——家庭整體顯示安全，個別成員卻存不到目標。 所以家庭總覽除了總數，一定要逐人列出狀態。這是聚合統計的陷阱，報告裡值得講。

E · LLM 財務建議

#功能說明優先
E1月度建議結算後產生，個人 + 家庭兩個層級M
E2附依據每條建議都要列出可驗算的數字M
E3分級良好 / 參考 / 需注意M
E4未成年建議同步同時送給監管者M
E5年度建議年結分析S

建議的邊界規則（硬約束，寫進 prompt）

規則為什麼
金額一律由資料庫計算模型不擅長算術。財務數字算錯會讓使用者做出錯誤決定
每條建議都要附依據使用者要能自己驗算，不能是黑盒子
不提供投資／保險／稅務建議這些是受規範的專業意見，超出系統範圍
不對個人做價值判斷只描述數字與趨勢，不說「你太浪費」
未成年建議同時送監管者監管是設計目的，但必須雙方都看得到

刻意不用的東西

這一段跟工具清單一樣重要。講得出為什麼不用，才顯得清單不是隨手抄的。

React / Vue

八個畫面已經寫完，重寫是純成本。三個沒有專案經驗的人要同時學 React、Vite、hooks， 再加上後端與模型，一個月做不完。

這是有意識的取捨，不是能力不足——要寫進報告。有時間該升級的是打包（Vite）， 不是框架，因為那只影響建置流程，不必重寫畫面。

Django

內建 admin 與 auth 聽起來很划算，但實戰經驗在 FastAPI，換框架等於放棄既有優勢。 Django ORM 與 Pydantic 是兩套思維，混用會亂。

而且本專案的 API 是給自己的前端用，不需要 Django 的完整後台。

Redis（第一版）

session 用 sessions 表就夠；一個家庭幾百筆交易，直接查資料庫毫秒級； LLM 回應存進 nlp_parses 反而更有用，因為那同時是訓練資料。

多一個服務就多一個要維護、要部署、要除錯的東西。有時間再加。

第一版不微調

做法成本預期效果
API + few-shot + 結構化輸出低，一週內可上線一次輸入完全正確率約 0.6–0.75
API + 微調小模型高，要標註 + 訓練 + 評測目標 0.75+
但評測不能省

第一版先用 API 把系統跑起來，收集 nlp_parses 的真實資料，第二階段再微調—— 這樣即使微調來不及，系統仍然完整可用。 但就算不微調，也要交出「零樣本 vs few-shot」的對照數字，那是本專題的量化成果。

API 目錄：按人員分類

共 37 支路由。權限標示：公開 / 登入 / master / 監管者。 ★ 代表與 LLM 直接相關。

成員1
帳號與權限 · 17 支

路由數最多，但多是規格明確的 CRUD。難的是權限判斷的正確性，不是數量。

成員2
記帳 · 10 支

四支 nlp 路由是整個系統的核心。解析與寫入刻意分兩步。

成員3
統計與預算 · 6 支

路由少但每支的計算邏輯都不簡單，而且分類體系由這裡定義。

成員4
財務建議 · 2 支

路由最少。工作量在 prompt 設計與全系統評測，不在路由數。

路由數差距很大，但工作量不是這樣算的

17 支 對 2 支看起來很不平均，可是成員4 要扛整個專題的量化成果—— 模型評測是報告的重點，那份工作沒有對應的路由數。 分工要用「一條完整的功能模組」來衡量，不是數 API。

查詢參數的權限行為

不帶 userId 時回傳「你看得到的所有人」；帶了 userId 但你沒有權限看那個人 → 回 403 而不是空陣列。空陣列會讓人以為對方沒記帳。

07

MVC 流程

FastAPI 本身不是 MVC 框架，但分層的職責可以一對一對應過去。 報告裡用 MVC 講會比較好懂，實作上就是 routers / services / models 三層。

View
site/ 前端
  • app.js 八個畫面的繪製
  • api.js 唯一的資料入口
  • 不含任何金額計算
  • 只負責顯示與收集輸入
Controller
routers/ + services/
  • routers/ 接收請求、驗權限、回傳
  • services/ 商業邏輯
  • schemas/ Pydantic 驗證進出
  • 模型呼叫也在這一層
Model
models/ + PostgreSQL
  • SQLAlchemy 資料表定義
  • Alembic 管理結構變更
  • 唯一的真實資料來源
  • 所有金額從這裡算出來

一次請求走完的路：以「段落記帳寫入」為例

1
View · 使用者按下「確認並寫入 5 筆」
app.js 把畫面上五列的欄位收回來，呼叫 API.nlpConfirmBatch(items)。 前端不做任何金額運算，只把使用者確認過的值送出去。
2
View · api.js 決定送去哪裡
mock 模式寫進 localStorage；http 模式 fetch 打 POST /api/nlp/confirm-batch。兩個轉接器的簽章一樣，上層完全無感。
3
Controller · router 收下並驗證
Pydantic schema 驗欄位型別；core/deps.py 從 JWT 取出目前使用者； services/permission.py 確認這個人有沒有權限寫這筆。驗不過就 403，不進 service。
4
Controller · service 執行商業邏輯
寫入 transactions，同時把「模型原本解析的值」與「使用者改成什麼」 一起寫進 nlp_parses。這一步就是資料飛輪的入口。
5
Model · SQLAlchemy 落地
交易提交進 PostgreSQL。金額欄位是 NUMERIC(14,2)， 不用浮點數——財務系統用 float 會有進位誤差。
6
回程 · 重算後回傳
router 回 {created: 5}，前端接著重打 GET /api/summary——總覽的數字一律由後端重算， 前端不自己加總，否則兩個畫面遲早會對不起來。
為什麼強調「金額由後端算」

前端自己加總看起來比較快，但只要有兩個地方各自加總， 數字對不起來只是時間問題。這個專案在原型階段就踩過一次： 我的總覽用明細加總、家庭總覽用成員表，同一個人出現兩個支出數字。

08

LLM 架構

兩條路徑，優先順序差很多。路徑 A 是系統的核心，路徑 B 是加值。

路徑 A · 段落記帳（核心）

1
使用者寫一段話
「早上買早餐55，中午跟同事吃飯320，下午在全家買咖啡，晚上加油1200，今天打工賺了1500」
2
POST /api/nlp/parse-batch — 模型做兩件事
先切分：這段話裡有幾筆？
再抽欄位：每一筆的日期、金額、收支方向、分類、店家，各自附一個信心度。
prompt 帶 few-shot 範例與家庭的分類體系；輸出格式由 Pydantic schema 約束。
3
Pydantic 驗證 — 過不了就重試
模型回傳的 JSON 一定要通過 schema 驗證才採用。 驗不過就帶著錯誤訊息重試，重試仍失敗才回錯誤給前端。
4
前端逐筆列出來給人確認
每一列標出它對應原句的哪一段（切分也要被檢查）。
缺欄位→ 標在那一欄上，紅框 + 「必填」，補齊前送出鈕停用。
信心 < 85% → 標黃並顯示百分比。
5
POST /api/nlp/confirm-batch — 這時才寫入
模型從頭到尾沒有碰過資料庫。 寫入的同時把「模型解析值 + 使用者修正值」一起存進 nlp_parses。
6
資料飛輪 — 修正變成下一輪的燃料
nlp_parses 同時是評測的來源（算一次輸入完全正確率） 與下一輪 few-shot / 微調的訓練資料。使用者用得越多，資料越多。
為什麼一定要分成 parse 與 confirm 兩支

如果模型解析完就直接寫入，它錯了使用者只能事後去改， 而且錯誤不會被記錄下來——飛輪就轉不起來。 分兩步讓「使用者的修正」變成一份有標註的資料，這是整個設計裡最值錢的一步。

路徑 B · 財務建議（加值）

1
analytics service 先把所有數字算出來
收入、支出、各分類佔比、預算使用率、存款目標達成率——全部由 SQL 與 Python 算。
2
把「算好的數字」組進 prompt
模型拿到的是結果，不是原始資料。它沒有機會去算錯。
3
要求模型只做敘述與歸納
邊界規則寫進 prompt：不做投資／保險／稅務建議、不對個人做價值判斷。
4
Pydantic 驗證輸出格式
建議必須有標題、內容、分級三個欄位，缺一不可。
5
把數字存進 advices.basis_json
使用者要能自己驗算。每條建議都附上它是根據哪些數字算出來的。
順序不能顛倒

模型不做任何算術。 財務數字算錯會讓使用者做出錯誤決定， 而模型本來就不擅長算術。先算再敘述，不是先敘述再驗算。

評測：本專題的量化成果

指標怎麼算為什麼用它
一次輸入完全正確率五個欄位全對才算一次成功單看個別欄位的分數會高估體驗——使用者在意的是「我寫一句話，它有沒有一次記對」
切分正確率一段話切出的筆數與人工標註一致切錯比抽錯更難發現
分類 Macro-F1各分類的 F1 取平均避免被「餐飲」這種大類別的高分蓋過
零樣本 vs few-shot 對照同一份測試集跑兩種 prompt這是報告裡最有說服力的一張表
09

分工心智圖

不是「一個做前端、一個做後端」，而是每人吃一條完整的功能模組—— 從資料表、API、畫面，一路到該模組自己的 LLM。 填上名字後按儲存，其他人打開這頁就會看到。

連線上的數字是該分支的 API 支數 橘色＝該模組自己的 LLM 工作 ⚑ 第 1 週要凍結的跨模組契約
尚未儲存過
這樣切的三個好處

責任清楚——某個畫面壞了，知道找誰。
可以平行動工——四個人各改各的檔案，衝突少。
每個人都碰得到 LLM——這是任務的硬性要求，垂直切片自然做到， 不需要另外指派一個「模型負責人」。LLM 的部分各自在自己的分支下微調， 主要的分工還是落在後端模組上。

⚑ 分類體系是唯一的跨模組阻塞點

成員3 定的分類體系，成員2 要寫進 prompt、成員4 做建議時要用。 第 1 週就要凍結，其他兩份契約各模組自己就能定。
