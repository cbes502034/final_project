四人 × 一個月 · LLM 技術方案

記帳模型設計

自行微調 Hugging Face 開源模型，用 function calling 把「語意判斷」跟「事實計算」分開。 這份是給組內看的技術方案：選哪顆模型、怎麼訓、怎麼接、目標打到多少。

① 模型篩選 ② 為什麼挑最小的 ③ 系統位置 ④ 五個工具 ⑤ 兩輪流程 ⑥ 訓練管線 ⑦ 怎麼上線 ⑧ 目標成效 ⑨ 風險與排程
這份方案的三個前提

1. 成品不能靠商業 API。 課程要學的是操作 LLM，串一支別人的 API 沒有技術含量可言， 所以上線提供服務的模型必須是我們自己微調的開源權重。
2. 必須有 function calling。 不是為了交作業硬加，下面每一個工具都是「讓模型自己做會出錯」才存在的。
3. 沒有 GPU。 只能靠 Colab 或 Kaggle 的免費 T4，這一條直接決定了模型大小的上限。

01

模型篩選

四個篩選條件：繁中要能用、要有原生的工具呼叫格式、免費 T4 上 QLoRA 跑得動、授權乾淨。

模型參數繁中原生工具呼叫T4 微調授權判斷
Qwen2.5-1.5B-Instruct 1.5B可用有 ~40 分鐘Apache-2.0 主力
Qwen2.5-7B-Instruct 7B最好有 2–4 小時，吃緊Apache-2.0 對照組
Qwen2.5-3B-Instruct 3B好有 ~1.5 小時Qwen Research（非商用） 備案
Llama-3.1-8B-Instruct 8B中等有 吃緊Llama 3.1 社群授權 不選
Breeze-7B-Instruct（聯發科） 7Bzh-TW 特化無 吃緊Apache-2.0 不選
TAIDE-LX-7B-Chat 7Bzh-TW 特化無 吃緊需申請 不選

被刷掉的三顆，理由

Llama-3.1-8B

工具呼叫沒問題，但繁中明顯輸 Qwen——「全家」「全聯」「悠遊卡」這種台灣語境它會歪。授權也有使用條款要讀。

Breeze-7B

繁中是它的強項，但沒有原生的工具呼叫 template。等於要從零教模型什麼是 tool call，多一整層難度，一個月不划算。

TAIDE

同樣沒有原生工具格式，而且取得要走申請流程，時程上多一個不受控的變數。

授權與規格請在動工前自己去 model card 確認一次

上表的授權、VRAM 與訓練時間是我依規格推估的，不是實測值。 Qwen2.5 系列大多是 Apache-2.0，但 3B 那顆是 Qwen Research 授權（限非商用）， 校內專題沒問題、之後想商用會卡住。開工第一件事就是去 Hugging Face 的 model card 對一次。

02

為什麼主力挑最小的那顆

直覺會想選最大的。但在一個月、四個人、沒有 GPU 的條件下，1.5B 反而是更好的選擇，有三個理由。

1
迭代速度決定你能試幾次
微調不是跑一次就好——資料要改、超參要調、prompt 要換。 40 分鐘一輪跟 3 小時一輪，一個月下來差的是能試 20 次還是 5 次。 對三個沒有專案經驗的人來說，能多試幾次比模型大幾倍重要。
2
小模型的微調增益最明顯，報告才有東西寫
7B 這種任務本來就做得還可以，微調完提升有限， 數字擺出來反而像在說「其實不必微調」。1.5B 沒微調前會很差，微調後會好——落差大，對照表才有說服力。 微調是本專題的硬性要求，那就要挑一顆能把微調價值秀出來的模型。
3
它是唯一 demo 得起來的
1.5B 量化成 GGUF q4 大約 1GB，CPU 上跑得動。 7B 沒有 GPU 就沒辦法在展示當天穩定提供服務。 一個跑不起來的模型，評測分數再漂亮也沒用。
可以立的核心主張

「微調後的 1.5B，在這個窄任務上打贏沒微調的 7B。」
這句話如果成立，就同時回答了「為什麼要微調」跟「為什麼小模型夠用」。 所以 7B 不是備案，是對照組——它存在的目的就是被比較。

03

模型在系統裡的位置

整個設計的骨架只有一句話：模型負責語意判斷，工具負責事實與計算，兩者之間沒有捷徑。

04

五個工具，各自為什麼存在

每一個工具都是因為「讓模型自己做會出錯」才被切出來的。 如果一個工具拿掉之後系統照樣正確，那它就不該存在。

resolve_date(expr, today)
取事實。「今天」「昨天」「上禮拜三」換算成實際日期。 模型算日期會錯，而且錯得很難發現——差一天，使用者不會注意到，月統計卻已經跑掉。這是純函式，交給 Python。
lookup_category(text, merchant)
取事實。查這個家庭實際有哪些分類。 不查的話模型會幻想出不存在的分類（「便利商店」但系統裡只有「餐飲／日用品」）。 分類體系是成員3 定的契約，模型只能從裡面挑。
record_transactions(items[])
交結果。模型把解析好的 N 筆交出來——但這不是寫入。 後端收下、Pydantic 驗過、回前端讓使用者逐欄確認，確認了才真的進資料庫。 這支就是整個段落記帳的輸出口。
get_month_summary(user_id, period)
拿數字。財務建議要用的收入、支出、各分類佔比。 模型不准自己算，只能問。問到什麼就講什麼。
get_savings_status(user_id, period)
拿數字。存款目標、可支配上限、使用率、短少多少。 同上——這些數字錯了會讓使用者做出錯誤的財務決定。
這樣分，function calling 就不是硬加的

兩個取事實、一個交結果、兩個拿數字。 拿掉任何一個，系統就會開始產生錯誤的資料或錯誤的建議—— 這就是「為什麼需要 function calling」的答案，不必另外編理由。

05

兩輪工具呼叫的流程

模型跑兩輪：第一輪問事實，第二輪交結果。中間那次「後端執行工具」是分界線。

第二輪模型實際吐出來的東西

{
  "name": "record_transactions",
  "arguments": {
    "items": [
      { // 早上早餐55
        "span": "早上買早餐55",
        "occurred_on": "2026-09-10",   // 來自 resolve_date，不是模型算的
        "amount": 55, "kind": "expense",
        "category_id": "C01",           // 來自 lookup_category，不是模型編的
        "merchant": null,
        "confidence": { "amount": 0.98, "kind": 0.97, "category": 0.88 }
      },
      { // 中午全家買咖啡 —— 金額沒講，模型要留空而不是猜
        "span": "中午在全家買咖啡",
        "occurred_on": "2026-09-10",
        "amount": null, "kind": "expense",
        "category_id": "C01",
        "merchant": "全家便利商店",     // 「全家」是店名不是家人，這是模型的價值所在
        "confidence": { "amount": 0.0, "kind": 0.95, "category": 0.65 }
      }
    ]
  }
}
要教會模型的最重要一件事：不知道就留空

「中午在全家買咖啡」沒有金額。模型猜一個 65 出來，比留 null 糟糕得多—— 留 null 前端會標紅要使用者補，猜一個數字就直接變成一筆錯帳。 訓練資料裡必須刻意放進大量「欄位不全」的例子，否則模型會學會硬掰。

06

訓練管線

資料從哪來、怎麼訓、怎麼確認有變好、怎麼上線。

訓練設定

項目設定為什麼
框架Unsloth ＋ TRL SFTTrainerUnsloth 在 T4 上約快兩倍、省 VRAM，且支援 Turing 架構
量化QLoRA 4-bit NF416GB T4 要塞下訓練，只能走 4-bit
LoRAr=16, alpha=32, dropout=0這個資料量不需要更大的 r，太大反而過擬合
目標層q,k,v,o,gate,up,down全掛。只掛 attention 對格式學習的幫助有限
精度fp16T4 是 Turing，沒有 bf16，也用不了 flash-attention-2
序列長度1024一段記帳文字加工具定義綽綽有餘，開太長只是浪費 VRAM
批次batch 1 × grad accum 8等效 batch 8，配 gradient checkpointing
學習率2e-4, cosine, warmup 5%LoRA 的常用起點，先跑再說
輪數2–3 epochs資料量小，超過 3 輪很容易背起來
損失遮罩只算 assistant 回合關鍵。prompt 要 mask 掉，否則模型在學怎麼寫問題而不是怎麼答
檢查點每 50 步存 Google DriveColab 免費版會斷線，斷了要能接著跑

資料怎麼來

種子：四人各手寫 100 段

第 1 週就要開始，不能等前後端做完。每個人寫自己真實的記帳講法，四個人的語言習慣不一樣，這正是我們要的多樣性。

擴增：模板組合

台灣店家清單 × 金額型態（含中文數字）× 時間詞 × 句型，程式化組出 3–5 千筆。 難點要過取樣：店名歧義、收支方向、合計語意、一段多筆。

留出集：200 段手工標註

永遠不進訓練。而且要由「沒寫那批種子的人」來標，避免標註習慣汙染評測。

商業 AI 可以當標註助手，但不能出現在成品裡

課程的重點是學會操作 LLM。直接串商業 API 就只是接了一支 API， 技術含量在別人那邊——所以成品的模型必須是我們自己微調的，這點沒有討論空間。
但拿商業模型先產一版候選標註、再由人逐筆修正是另一回事。 這在業界叫蒸餾或弱監督，本來就是標註流程的常規做法， 而且它不會稀釋技術含量——切分策略、工具設計、QLoRA 調參、評測， 這些難的部分一件都沒少。

但有兩條線不能越過

1. 留出集必須 100% 人工標註，絕不能讓商業模型碰。 這是最容易踩到而且最致命的一條——如果測試集是商業模型標的， 評測量到的就變成「我們的模型有多像那個老師」，而不是「我們的模型有多正確」。 老師錯的地方，我們學得越像分數越高，整張對照表會變成假的。
2. 候選標註一定要人逐筆看過，不能照單全收。 直接收下等於把商業模型的錯誤一起學進去，而那些錯誤剛好集中在 最難的那幾類（店名歧義、收支方向）——也就是我們最想做對的地方。

報告裡要明講標註流程用了什麼輔助，把它寫成方法的一部分。 講清楚反而是加分：它顯示我們知道資料從哪來、也知道那樣做的風險在哪。

07

怎麼上線

這是整份方案風險最高的地方。Render 免費方案跑不動任何一顆模型，所以要準備三層退路。

層級做法優點缺點
展示日 Colab T4 起推論服務 ＋ cloudflared 通道，FastAPI 打過去 免費、跑得動 GPU、速度可接受 Colab 一斷線就沒了，不能當常駐服務
常駐 GGUF q4_k_m ＋ llama.cpp，放 Hugging Face Space 免費 CPU 一直在，不用顧 CPU 推論慢，一段話大概要等幾秒
保底 前端 mock 模式（現在站上跑的就是這個） 模型全掛，網站還是完整可展示 不是真的模型輸出，要在畫面上標明

格式保證：微調之外還要加一層

微調讓模型傾向輸出正確格式，但不保證。商業 API 的 structured output 我們沒有了， 要自己補上 constrained decoding——用 XGrammar / outlines / lm-format-enforcer 把生成限制在工具呼叫的 JSON schema 上。

兩層疊起來才夠

微調讓它「想對」，約束解碼讓它「寫對」。 只有微調，小模型偶爾還是會吐出壞掉的 JSON；只有約束解碼，格式對了內容卻是亂猜的。 兩個都要。這也是為什麼「工具呼叫格式合法率」要單獨列成一個指標——它是最容易做到 99% 的一項， 也是最能看出這一層有沒有做的一項。

08

目標成效

四個指標，一張對照表。報告最後要交出來的就是這張表。

指標 1.5B 未微調 1.5B 微調後 7B 未微調 這個指標在測什麼
工具呼叫格式合法率 待測 > 0.98 待測 吐出來的 tool call 解析得動嗎。加上約束解碼後應該接近 1.0
段落切分正確率 待測 > 0.85 待測 一段話切成幾筆有沒有對。切錯比抽錯更難被發現
一次輸入完全正確率 待測 > 0.70 待測 主指標。日期金額方向分類全對才算成功
分類 Macro-F1 待測 > 0.80 待測 取各分類 F1 平均，不讓「餐飲」這種大類蓋過小類
該留空卻硬猜的比率 待測 < 0.05 待測 金額沒講時有沒有亂編。這項越低越好，錯帳都從這裡來
「待測」是刻意留的，不要先填數字

基線必須第 1 週用留出集實際跑出來，不能用估的。 我可以給目標值（那是我們要追的），但基線一旦用猜的，整張對照表就沒有意義了—— 評審一問「你們的基線怎麼來的」就會破功。
第 1 週的任務之一就是：把 1.5B 跟 7B 的 zero-shot 都跑過留出集，把左右兩欄填實。

最想看到的一格

「1.5B 微調後」那一欄，全面高於「7B 未微調」那一欄。
如果成立，這份專題的結論就是一句很有力的話： 在夠窄的任務上，一顆小模型配上好的訓練資料，勝過一顆大四倍的通用模型。

09

風險與排程

誠實講：換成自行微調之後，工作量比呼叫 API 重不少。排程要跟著改。

四個風險，各自的退路

風險徵兆退路
Colab 訓練到一半斷線 免費版常態，尤其晚上 每 50 步存 Drive，斷了接著跑。備援用 Kaggle（每週 30 小時，比 Colab 免費版慷慨）
微調後沒有比較好 評測跟基線差不多 退回 base ＋ few-shot ＋ 約束解碼，系統照樣能跑。 而且負面結果也是結果——照實寫進報告，比硬凹數字好
展示當天服務起不來 通道掛掉、Space 排隊 三層退路（見第 7 節）。最差就是 mock 模式，網站不會死
標註量被低估 第 2 週還在寫種子資料 這是最可能發生的一個。第 1 週就要開工，不能等前後端做完

調整後的三週

W1
前後端整合 ＋ 同步開始標資料 ＋ 跑出基線
原本的「前後端整合完畢」不變，但多了兩件必須平行進行的事： 四人各寫 100 段種子資料、以及把 1.5B / 7B 的 zero-shot 跑過留出集把基線填實。
標註不能等。它是唯一一件「越早開始越好、而且不依賴任何人做完」的工作。
W2
微調 ＋ 把 function calling 接起來
模板擴增 → 轉格式 → 第一次 QLoRA → 第一次評測。 同時把五個工具在 FastAPI 這側實作完、兩輪流程串通。 這週結束要能從畫面輸入一段話，走完兩輪，跑出確認表格。
W3
加約束解碼 ＋ 迭代 ＋ 部署 ＋ 最終評測
補上 constrained decoding、依評測結果回頭補資料再訓一輪、 匯出 GGUF 佈上 HF Space、把對照表的數字全部填實。

四個人分別扛什麼

成員原本的模組在這份方案裡負責
成員1帳號與權限 模型服務層與工具派發：services/llm.py、tool dispatch、重試、逾時、把兩輪流程包成一支可呼叫的介面
成員2記帳 解析任務本體：工具 schema、訓練資料的組裝與擴增、QLoRA 微調、record_transactions
成員3統計與預算 數字工具與分類體系：get_month_summary、get_savings_status、lookup_category 背後的分類契約
成員4財務建議 評測與建議：留出集標註、評測腳本、四個指標的對照表、建議生成的 prompt 與邊界規則
留出集為什麼交給成員4

因為他不寫種子資料。標訓練集的人不要標測試集—— 同一個人標，會不自覺用同一套判斷標準，評測就會偏樂觀。
