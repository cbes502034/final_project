# 前後端串接契約

> **這份文件的形狀是從前端程式跑出來的，不是手寫的。**
>
> 做法：把 `frontend/js/data.js` + `frontend/js/api.js` 的 mock 轉接器從**空的資料**開始實際走一遍
> （註冊 → 建家庭 → 邀請 → 照看 → 開帳本 → 記帳 → 預算 → 建議 → 解散），把每一支的回傳 dump 出來。
> mock 就是「跑在瀏覽器裡的後端」：規則跟這份文件一樣，資料存在 `localStorage`，**沒有任何假資料或範例帳號**。
>
> **所以這裡寫的形狀就是前端真的在吃的東西。** 後端照著做，
> 把 `frontend/index.html` 的 `<meta name="api-base">` 填上網址，畫面就會動。
>
> 70 支路由已經全部掛在後端（`backend/app/routers/`），還沒做的回 **501**，
> 畫面會直接說「後端還沒做這一支（HTTP 501）｜出錯的函式：API.xxx（路由，成員N）」，
> 左下角那張表會列出這一頁打過的每一支：**回應正確的亮綠燈、出錯的亮紅燈**（可以整個複製）。

## 已經定案的六件事

這六件是前端現況與一般後端寫法會打架的地方，**已經決定好了**，照做就好。

### 1. ID 是字串 ✅ 後端回字串

資料庫的主鍵是整數（`BIGSERIAL`），**回給前端時一律轉成字串**：`1` → `"1"`。

```python
from app.toolkit import crud

crud.to_dict(tx)            # id、*_id、created_by 預設就轉成字串（str_ids=True）
```

- 前端**從來不解析 ID 的內容**，只拿來比對與放回網址。mock 的 ID 長 `"U1"`、`"N1789…"`，後端的長 `"1"`、`"42"`，前端都一樣收。
- 前端送回來的也是字串。路徑上的 `{tx_id}` 由守衛轉成整數（`guards.own()`、`in_group()`、`can_see_user()` 已經做好，轉不動回 **404**，不是 500）。
- 為什麼不回整數：JavaScript 的 `Number` 超過 2^53 會失去精度，大型系統的 ID 常刻意用字串；而且前端已經照字串寫好、測過了。

### 2. 人身上不放收支數字

`GET /api/auth/me` 的 `user`、`GET /api/family` 的 `members[]` **不帶** `income`／`expense`／`budget`。

- 收支一律從明細現算：個人的在 `GET /api/summary`，全家每個人的在 `GET /api/summary?scope=family` 的 `members[]`。
  把數字存在人身上，每記一筆、改一筆、刪一筆都要記得同步更新，漏一次就跟明細對不起來。
- `savingsGoal`（每月想存多少）**要回**：個人化設定與個人資料頁的輸入框用它當預設值。

### 3. 名稱、衍生數字前端補得出來，後端可以不帶

後端只要回「查資料庫才拿得到」的東西。下面這些前端的 `api.js` 會自己補（**後端有帶就用後端的**）：

| 哪一支 | 前端補的欄位 | 用什麼算 |
|---|---|---|
| `GET /api/summary` | `net`、`rate`、`savings.allowance／used／left／ratio／level／shortfall／actual`、`byCat[].name／color` | `income`、`expense`、`savings.goal` ＋ 門檻（`data.js` 的 `savingsRule`，跟後端 `SAVINGS_WARN_RATIO`／`SAVINGS_OVER_RATIO` 一致） |
| `GET /api/budgets` | `pct`、`over`、`catName`、`catColor`、`userName` | `used`、`limit` ＋ 分類與成員清單 |
| `GET /api/transactions` | `catName`、`catColor`、`userName` | `cat`、`user` ＋ 分類與成員清單 |
| `GET /api/notifications` | `actorName`、`catName` | `actorId`、`cat` |
| `GET /api/guardianships` | `guardianName`、`wardName`、`mine` | `guardian`、`ward` ＋ 成員清單 |
| `GET /api/advices` | `userName` | `user` |

分類清單來自 `GET /api/categories`、成員清單來自 `GET /api/family`，前端拿一次快取起來；
新增分類、加入／離開家庭、改角色、改名字之後自動重拿。

⚠️ **權限、可見範圍、密碼、金額加總、寫入一律是後端的**，前端不代勞——放前端等於任何人改一下瀏覽器就能繞過。
`savings.level` 前端補得出來，但 `members[].savingsLevel`（逐人）一樣要後端算，前端不會替每個人補。

### 4. 錯誤怎麼回、前端怎麼顯示

錯誤一律回 FastAPI 的預設形狀 `{"detail": "給使用者看的一句話"}`（`toolkit/errors.py` 的 `bad_request()`、`forbidden()`…）。
前端依狀態碼分四種：

| 種類 | 什麼時候 | 畫面上 |
|---|---|---|
| 業務錯誤 | 400／401／403／404（有 detail）／409／422 | **照 `detail` 原話顯示**，不加技術資訊。所以 detail 要寫成人話 |
| 後端錯誤 | 5xx、404 `Not Found`（路由不存在）、405、**501（還沒做）** | 「後端還沒做這一支（HTTP 501）｜出錯的函式：API.createCategory（POST /api/categories，成員2）」 |
| 連不上 | 網路斷線、CORS 擋掉 | 「連不上後端｜出錯的函式：…」 |
| 形狀不對 | 回應少了畫面一定要讀的欄位，**或清單裡某一筆的型別不對** | 「回應少了 alerts｜…」、「回應形狀不對：transactions 第 1 筆的 amount 應該是數字，收到字串 "120"｜…」 |

後三種都在訊息後面接「是哪一支、哪條路由、誰負責」——前提是前端沒問題：照契約打過去，拿回來的不對。
路由與負責人寫在 `api.js` 的 `FN`，跟 `backend/app/ownership.py` 一對一（有測試擋）。

**回應檢查有兩層**，都在 `api.js`：

| 層 | 在哪 | 看什麼 | 漏掉的話 |
|---|---|---|---|
| 最上層的 key | `SHAPE` | `{"transactions": …, "total": …}` 兩個 key 在不在 | 畫面讀到 `undefined.map`，壞在很後面 |
| 清單裡的每一筆 | `ROWS` | 每一筆的欄位與**型別**：`amount` 是數字不是字串 `"320"`、`date` 是 `2026-09-17`、`archived` 是 `true`／`false` | 金額加起來變字串接龍、日期排不出順序 |

⚠️ 檢查在前端補名字（`catName`、`userName`）**之前**跑，所以看的是後端回的原樣。
`ROWS` 的內容跟 mock 與真後端都對過（`tests/test_frontend_adapter.py`）。

**前端備援只剩一種情況：`503`（服務暫時叫不動）。**

| 哪一支 | 503 的時候前端怎麼頂 | 回應多一個 |
|---|---|---|
| `POST /api/nlp/parse`、`/parse-batch` | 前端的規則解析（金額、中文數字、分類關鍵字、日期）。**寫入還是走後端** | `fallback: true` |
| `POST /api/advices/generate` | 用 `summary` ＋ `budgets` 的數字在前端寫成句子，**不會存** | `fallback: true` |
| `GET /api/auth/sessions` | 只列這一台 | `fallback: true` |

⚠️ **501（還沒做）、405、404、連不上一律不頂**，照實壞掉。
以前 501 也會走備援，結果是「後端沒做，畫面上照樣看得到效果」——驗收時分不出哪幾支真的接好了。
503 留著是因為那是上線後真的會發生的事（模型那端掛了），這時候還能用規則記帳是對的產品行為。

### 4-1. 還沒接的那一支，畫面上長什麼樣

| 在哪裡 | 畫面上 |
|---|---|
| 一頁的主要資料（總覽、統計、明細、帳本、家庭、建議） | 內容整塊換成一張錯誤卡：「後端還沒做這一支／出錯的函式 `API.summary`　`GET /api/summary`　負責：成員3／目前：已連接後端 `<網址>`」。頁首標題、我｜全家、篩選、工具列照常在，也還能切去別頁 |
| 一頁裡的附屬區塊（個人資料的「存錢計畫」） | 只有那一塊變成錯誤卡，同一頁的其他區塊（我的資料、密碼、登入中的裝置、主題）照常能用 |
| 按下去才打的動作（確認寫入、寄重設信） | 右下角浮出一句「寫入失敗：後端還沒做這一支｜出錯的函式：…」，剛剛填的東西不會被清掉 |
| 通知鈴鐺 | 平常「沒有通知就整個收起來」；**那一支還沒做的時候鈴鐺會留著**，打開寫「後端還沒做這一支…這一支做好之前，通知都收不到」。收起來的話這件事就沒有地方講了 |
| 左下角那張表 | 這一頁打過的每一支都在上面，一個函式一列、只留最新一次的結果。**綠燈＝後端回了、形狀也過了 SHAPE 與 ROWS 的檢查，畫面一定接得住**；紅燈＝還沒做、出錯或形狀不對，下面附訊息與後端原話。全部綠的時候收成一顆綠色膠囊，一出現紅的就自動展開。有「複製全部」可以直接貼到群組。業務錯誤（403、409、422…）不列——那是後端**正確**地回答「不能這樣做」；模型叫不動時前端頂出來的備援結果也不算綠燈 |
| 那三支 503 才有備援的 | 501 的時候一樣照實壞掉；只有模型服務叫不動（503）才會頂，回應多 `fallback: true` 並浮出一句「後端的解析還沒接上，先用前端的規則……」 |

**順序**：`POST /api/auth/login`（成員1）沒做的話，整個站停在登入頁——
**成員1 先做完，其他三個人才看得到自己那幾頁**。
成員1 做完之後，每一頁各自壞在自己的那一支，互不影響：
明細與帳本等成員2、總覽與統計等成員3、家庭與通知等成員4。
（備援只在 503 生效，所以「還沒做」的階段每一支都是照實壞掉，沒有例外。）

### 5. 新增成功回 201，其他回 200 ✅

「建立了一筆新資料」的 POST 回 **201 Created**：註冊、記一筆、確認寫入、開帳本、加人進帳本、
新增分類、新增門檻、建立家庭、產生邀請碼、送出邀請、開始照看、產生建議。

其他一律 200：登入、續期、登出、結算、加入家庭、接受邀請、確認密碼、忘記密碼……——
那些是「做一件事」，不是「生出一筆新資料」。

前端兩種都收（只看 `res.ok`），所以這一條純粹是為了讓 70 支的語意一致；
`@router.post(..., status_code=201)` 一行就設定好了，`/docs` 上也會標出來。

### 6. API 的欄位名不等於資料表的欄位名 ✅

前端契約用短名，資料表用完整名，中間由 `crud.to_dict(rename=...)` 轉。
**在資料表裡找不到 `date` 是正常的**——它在資料表裡叫 `occurred_on`。

| 資料表欄位（PostgreSQL） | API 欄位（前端吃的） | 型別怎麼變 |
|---|---|---|
| `occurred_on` | `date` | `DATE` → 字串 `"2026-09-17"` |
| `category_id` | `cat` | `BIGINT` → 字串 `"1"` |
| `user_id` | `user` | `BIGINT` → 字串 `"3"` |
| `group_id` | `group` | `BIGINT` → 字串 `"5"` |
| `amount` | `amount` | `NUMERIC(14,2)` → 數字 `120.5`，不是 `"120.50"` |

```python
# 讀出來：一行帶過
crud.to_dict(tx, rename={"occurred_on": "date", "category_id": "cat",
                         "user_id": "user", "group_id": "group"})

# 寫進去：反方向，自己轉
occurred_on = date.fromisoformat(body.date)     # 格式不對要回 422
crud.save(Transaction, {"occurred_on": occurred_on, "category_id": category.id, ...})
```

改名**不是自動的**，是每一支自己寫在 `rename=` 裡，所以只有上面這幾個會變，其他欄位（`kind`、`merchant`、`note`、`source`）兩邊同名。

哪一層看哪份文件：

| 想知道 | 看哪裡 |
|---|---|
| 資料表有哪些欄位 | `frontend/js/data.js` 的 `schema`（正本）→ 手冊的「各表欄位」 |
| API 收什麼、回什麼 | 這份文件的「逐支契約」、路由說明字串的【請求主體】【成功回應】、`/docs` 的 Schema |

## 怎麼接：四步驟

### 第 1 步　路由已經在了，打開自己的檔案

`backend/app/routers/` 底下每個人的檔案裡，70 支路由**已經掛好**：守衛、請求主體的模型、說明字串都寫好了，
函式裡只有一行 `raise not_ready("GET /api/summary", OWNER)`（回 501）。

⚠️ **每一支的說明字串就是那一支的規格書**，十一個段落：這支做什麼、前端怎麼打、誰能打、請求、成功回應、
錯誤回應、會用到的資料表、每一步用的工具與資料庫方法、寫法步驟、**完整寫法**、做完怎麼確認。
「完整寫法」的第二步是要貼上去的程式（只有函式內容）。做法只有兩個動作：刪掉 `@stub`、
把 `raise not_ready(...)` 那一行換成第二步。裝飾器、參數、import 都已經放好最終版本，不用動。
說明裡的程式有測試在跑（`tests/routes/`），所以它不會跟實作走散。

```python
@router.get("/summary", summary="總覽的所有數字")
@block_admin                       # ← 守衛：沒登入 401、平台管理員 403，已經擋好
@stub                              # ← 還沒做的標記：ownership 會算成待辦
def get_summary(me: User, db: Session = Depends(get_db)):
    raise not_ready("GET /api/summary", OWNER)
```

做一支＝刪掉 `@stub`、把 `raise not_ready(...)` 那一行換成說明字串的第二步。增刪改查用 `app/toolkit/crud.py`，規則用 `app/toolkit/` 對應的模組。

### 第 2 步　前端切到真後端

改 `frontend/index.html` 這一行：

```html
<meta name="api-base" content="https://fambudget-backend.onrender.com">
```

留空 = mock（跑在瀏覽器裡的後端）。填上網址 = **全部**改打真後端，不會混著用 mock。
⚠️ 網址千萬不要填 `fambudget-api.onrender.com`——那個子網域是別人的服務。

### 第 3 步　一支一支換成真的

還沒做的那幾支，畫面會在出錯的地方說「後端還沒做這一支」和負責人，其他頁照常能用；
上面那四支有前端備援的，畫面甚至不會壞。**所以可以慢慢接，不用等全部做完才切。**

`python -m app.ownership` 隨時看每個人還剩幾支（有 `@stub` 的算還沒做）。

### 第 4 步　跑測試

```bash
cd backend
pytest                               # 全部：形狀、守衛、增刪改查、前端代勞與錯誤訊息
pytest tests/routes                  # 每一支路由的驗收測試（同一組跑兩次：[說明] 與 [你的]）
pytest tests/routes -k "create_transaction and u4f60" -v   # 只看路由檔裡寫的那一支
                                                           # u4f60 是標籤「你的」的跳脫碼；
                                                           # -k 直接打中文會 0 selected
```

`tests/routes/` 的每個測試都跑兩次：**[說明]** 是把說明字串裡的「完整寫法」套上去跑（保證那段程式是對的），
**[你的]** 是你自己寫的那一支——還是 `@stub` 就自動跳過，拿掉 `@stub` 之後就會跑。兩個都綠，就代表接對了。

`tests/test_frontend_adapter.py` 會把前端的 `api.js` 接到一個假後端跑一遍，確認「後端只回原始欄位時前端補得起來」
與「每一種錯誤都講得出是哪一支」。

### `GET /api/auth/me` — 我是誰

**前端呼叫**　`API.me()`　**用在**　總覽（我／全家）、右上角帳號選單、每一頁的權限判斷、路由閘（沒登入帶去登入頁、管理員帶去 `#/admin`、沒走完設定帶去 `#/setup`）

**請求**　無參數，只帶 `Authorization: Bearer <access_token>`

**回應**

```json
{
  "user": {
    "id": "U1", "name": "王大明", "email": "daming@wang.tw",
    "role": "parent", "familyId": "F1", "avatar": "明", "avatarUrl": null,
    "age": 52, "birthYear": 1974, "joined": "2026-01-05",
    "theme": "sky", "onboardedAt": "2026-01-05T09:00:00+08:00",
    "savingsGoal": 20000, "isPlatformAdmin": false
  },
  "family":  { "id": "F1", "name": "王家", "period": "2026-09" },
  "visible":   ["U1", "U2", "U3"],
  "queryable": ["U1", "U2", "U3", "U4"],
  "guardedBy": []
}
```

**前端拿去幹嘛**

- `user.role` → `parent`／`child`／`null`（還沒加入家庭）。決定儀表板與帳號選單顯示哪些項目（子女沒有「全家」模式）
- `user.isPlatformAdmin` → `true` 的人只會被帶去 `#/admin`，看不到任何財務頁。一般人可以省略這個欄位
- `user.avatar` → 右上角帳號按鈕的頭像字（**一個中文字**）；`avatarUrl` 有值就改用圖片
- `user.onboardedAt` → **`null` 的人還沒走完註冊後的個人化設定**，登入後先帶去 `#/setup`。每一步都能跳過，走完或全部跳過才送 `PATCH /api/auth/me` 的 `onboarded`。⚠️ 一定要回這個欄位——沒回的話前端當成「走過了」，新註冊的人永遠不會被問存款目標
- `user.theme` → 介面主題，**一定有值**（沒選過就是 `'paper'`）。前端登入後套上，換裝置也一樣
- `user.savingsGoal` → 個人化設定與個人資料頁「每月想存多少」的預設值
- `family` → 還沒有家庭是 `null`；`period` 是目前的結算月份，前端很多地方拿它當預設值
- `visible` → 看得到全部紀錄的人（自己 ＋ 我照看的人 ＋ 同家庭的其他家長）
- `queryable` → 再加上跟我共用帳本的人（只看得到共用帳本那部分）
- `guardedBy` → 畫面上**刻意不顯示**「誰看得到你的紀錄」這類提示（家不是監獄）；欄位保留給權限說明與後端判斷

**陷阱**

- `guardedBy` 是**被監管者自己**要看的，不是只有管理者能拿。這是刻意的設計。
- 不帶 `income`／`expense`／`budget`（見上面定案的第 2 件）。
- `age` 只是顯示用，⚠️ **任何權限判斷都不准讀它**。資料表存 `birth_year`，回傳時換算。

### `GET /api/summary` — 總覽的所有數字

**前端呼叫**　`API.summary({ scope, period, groupId })`　**用在**　總覽（我／全家）、**統計頁**、前端產生建議的備援

**請求**

| 參數 | 型別 | 說明 |
|---|---|---|
| `scope` | `str` | `me` 只看自己、`family` 看全家（家長才有意義）。預設 `me` |
| `period` | `str` | 這一版固定是本月（**台灣時間的今天**所在的月份），前端也沒有送；之後要看歷史月份再加 |
| `groupId` | `str` | 只算那一本帳。不帶或 `all` = 全部 |

**回應**（✱ = 前端補得出來，後端可以不帶）

```json
{
  "period": "2026-09",
  "scope":  "me",
  "income": 68000,
  "expense": 41230,
  "net":     26770,              ✱
  "rate":    0.39,               ✱
  "count":   4,

  "wardIncome": 0, "allowance": 3000, "wardSpend": 1850,

  "savings": {
    "goal": 20000,
    "allowance": 48000, "used": 41230, "left": 6770,     ✱
    "ratio": 0.859, "level": "near",                     ✱
    "shortfall": 0, "actual": 26770,                     ✱
    "rule": { "warnAt": 0.8, "overAt": 1.0, "note": "..." }   ✱
  },

  "byCat":   [ { "cat": "C03", "name": "居住", "color": "cat-home", "amount": 18500 } ],   ← name／color ✱
  "monthly": [ { "m": "2026-04", "income": 68000, "expense": 39800 } ],
  "yearly":  [ { "y": "2026", "partial": true, "income": 540000, "expense": 331000 } ],
  "members": [ { "id": "U1", "name": "王大明", "role": "parent", "avatar": "明",
                 "income": 68000, "expense": 41230, "savingsGoal": 20000,
                 "allowance": 48000, "savingsRatio": 0.859,
                 "savingsLevel": "near", "shortfall": 0 } ]
}
```

**前端拿去幹嘛**

- `income` / `expense` / `net` / `rate` → 總覽大數字卡裡的收入／支出／結餘
- `savings.level` → 決定警告卡是綠（`safe`）黃（`near`）紅（`over`）
- `savings.shortfall` → 紅色時顯示「比目標少 NT$ X」
- `byCat` → **圓環圖**（`color` 是代號，見最後一節「顏色是代號」）
- `monthly` → **近 6 個月趨勢圖**（由舊到新，最後一個是本月）
- `yearly` → 近 3 年對照；`partial: true` 是還沒過完的今年，畫面會標「到目前」
- `wardIncome`／`allowance`／`wardSpend` → 家長給出去的零用金、孩子花掉多少（產生建議時用）
- `members` → 總覽全家模式的「每個人的這個月」（`scope=family` 時才需要）
- `count` → 這個月記了幾筆（建議會說「資料還太少」）

**陷阱**

- ⚠️ **所有數字從 `transactions` 加總**，`monthly`、`yearly`、`byCat`、`members[]` 也是。
  帶了 `groupId` 時每一個數字都只算那一本帳——總覽的大數字跟趨勢圖不能一個有篩一個沒篩。
- ⚠️ **`kind = 'transfer'` 不進任何加總。**
- 門檻（80% / 100%）寫在設定（`SAVINGS_WARN_RATIO`、`SAVINGS_OVER_RATIO`），`services/analytics.py` 的
  `savings_status()` 已經寫好；前端補 `level` 時用的是 `data.js` 的 `savingsRule`，**兩邊要一致**。
- **`allowance` 可能是 0 或負數**（存款目標訂得比收入高）。
  算 `ratio` 時直接除會 `ZeroDivisionError` → 整支 API 500。`savings_status()` 已經處理。
- `scope=family` 時 `members` 要逐人回傳各自的 `savingsLevel`，
  因為**家庭整體達標不代表每個人都達標**。算某個人時只走監管那條路（見「群組」一節），不要把共用帳本裡別人的錢算進來。
- 這支是統計頁唯一的資料來源（`GET /api/stats` 已經拿掉）。

### `GET /api/transactions` — 收支明細

**前端呼叫**　`API.transactions({ userId, groupId, from, to, categoryId, kind, source, q, page })`
**用在**　收支明細、總覽最下面的「今天的紀錄」、**成員紀錄頁（唯讀監管檢視）**

**請求**

| 參數 | 型別 | 說明 |
|---|---|---|
| `userId` | `str` | 只看某個人。**不帶＝看我有權限看的所有人** |
| `groupId` | `str` | 只看某一本帳。不帶或 `all` = 全部 |
| `from` / `to` | `str` | 日期範圍 `YYYY-MM-DD`，**兩端都包含**。今天的紀錄就是 `from=to=今天`（**真實日期、使用者的時區**，不是 UTC——台灣早上 8 點前 UTC 還是昨天） |
| `categoryId` | `str` | 只看某個分類 |
| `kind` | `str` | `income`、`expense`，或 `transfer` |

⚠️ **`transfer` 不進任何收支加總。** 家用轉 15,000 到旅遊基金，錢沒有離開這個家，
只是換了一本帳；記成 `income` 的話收入會憑空多一筆——跟「零用金記成支出」同一種錯。

| `source` | `str` | `nlp` 或 `manual` |
| `q` | `str` | 關鍵字，比對店家與備註 |
| `page` | `int` | 第幾頁，從 1 開始（一頁 200 筆） |

**回應**

```json
{
  "transactions": [
    {
      "id": "T1040", "user": "U1", "group": "G1", "date": "2026-09-10",
      "amount": 320, "kind": "expense", "cat": "C01",
      "merchant": "公司附近自助餐", "note": "午餐",
      "source": "nlp", "raw": "中午自助餐320",
      "parsed": { "conf": 0.97, "catConf": 0.95 },
      "userName": "王大明", "catName": "餐飲", "catColor": "cat-food"
    }
  ],
  "total": 14
}
```

**前端拿去幹嘛**

- `source === "nlp"` → 顯示「段落記帳」標籤
- `raw` → 有值就顯示「原句『...』」
- `catName` / `catColor` → 左邊的分類圓標（後端可以不帶，前端用 `cat` 對分類清單補）
- `userName` → 顯示是誰記的（後端可以不帶，前端用 `user` 對成員清單補）
- `group` → 判斷那本帳結算了沒（結算過的那幾列沒有修改／刪除）

**陷阱**

- **帶了 `userId` 但沒權限看那個人 → 回 403，不要回空陣列。**
  空陣列會讓使用者以為「對方這個月沒記帳」。
- ⚠️ **不認得的查詢參數要回 422，不要默默忽略。**

  這條是踩過才寫的：前端一直送 `?user=U3`，契約寫的是 `userId`。
  mock 收到不認得的鍵就當作沒有，於是「篩選沒生效」在 mock 下
  看起來完全正常——清單照常出現，只是沒篩而已。
  要等到接上真後端、看到別人的紀錄混進來，才會發現。

  現在 mock 會直接丟錯（「不認得的篩選參數」），後端也請這樣做（FastAPI 的查詢參數模型設 `extra="forbid"`）。
  **默默忽略是最難抓的錯，因為它不會壞給你看。**
- `parsed` 只有 `source === "nlp"` 時才有意義，但**建議一律回**
  （手動的回 `{"conf": 1, "catConf": 1}` 或整個省略都可以，前端有防呆）。

### `POST /api/transactions` — 手動新增一筆

**前端呼叫**　`API.createTransaction({...})`　**用在**　記帳頁的「單筆手動」

**請求主體**

```json
{ "date": "2026-09-10", "amount": 250, "kind": "expense",
  "cat": "C01", "groupId": "G1", "merchant": "全家便利商店", "note": "" }
```

`groupId` 不帶 = 記進我第一本還沒結算的帳；一本都沒有回 **409**（「先到帳本開一本」）。

**回應**　新建立的那一筆（形狀同上面明細的單筆），`source` 必須是 `"manual"`

**陷阱**

- ⚠️ **`source` 一定要記 `manual`，不可以記 `nlp`。**
  這支不經過模型。混在一起的話 `nlp_parses` 會被汙染，
  成員4 算模型正確率時分母就錯了。
- `amount` **永遠是正數**，收支方向看 `kind`。
- ⚠️ **結算過的帳本唯讀**：`groupId` 指到已結算的帳本回 **409**（`toolkit/ledger.py` 的 `require_open`）。
  沒帶 `groupId` 時，預設帳本也要跳過已結算的——不然使用者會在不知情的情況下記進去。
  `POST /api/nlp/confirm`、`confirm-batch` 同一條規則。

### `PATCH /api/transactions/{id}` — 修改一筆

**前端呼叫**　`API.updateTransaction(id, patch)`　**用在**　收支明細每一列的「修改」

**請求主體**　只送改過的欄位

```json
{ "amount": 180, "cat": "C01", "note": "午餐＋飲料" }
```

可以改的欄位：`date`、`amount`、`kind`、`cat`、`merchant`、`note`、`groupId`。

**回應**　改完的那一筆（形狀同上面明細的單筆），多一個 `updatedAt`

**陷阱**

- ⚠️ **只有本人**（403）。監管是唯讀的，家長看得到子女的紀錄不等於改得動。
- ⚠️ **結算過的帳本裡的紀錄不能改**（409），`groupId` 換到結算過的帳本也不行。
  結算就是大家對過帳了，改一筆，已經對好的數字就不對了。
- ⚠️ **不認得的欄位回 422**，例如 `source`、`user`。來源是「怎麼記進來的」，
  不是使用者能改的屬性；改 `user` 等於把自己的帳塞給別人。**不要默默忽略**——
  前端以為改了、畫面卻沒變，是最難抓的錯。
  （擋它的是 `schemas/transaction.py` 的 `TransactionPatchIn` 設了 `extra="forbid"`，FastAPI 自動回 422；
  其他 `*PatchIn` 也一樣。）
- `amount` 一樣永遠是正數；分類要跟 `kind` 對得上（支出不能選「薪資」，400）。
  只改 `kind` 沒帶 `cat` 時，mock 會把分類換成那一邊的「其他」。
- 改的是模型解析出來的那筆（`source = "nlp"`）時，把改過的值寫進
  `nlp_parses.user_corrected`——那就是模型抓錯的標註，成員4 算正確率要用。
- 工具：`toolkit/ledger.py` 的 `clean_patch(body)`、`require_editable(me, owner, settled_at)`。

### `DELETE /api/transactions?ids=T1040,N1789124882105` — 一次刪多筆

**前端呼叫**　`API.deleteTransactions(ids)`　**用在**　收支明細的「選取多筆」

**查詢參數**　`ids`：逗號分隔，最多 100 筆。重複的只算一次。

**回應**

```json
{ "deleted": ["T1040", "N1789124882105"] }
```

**陷阱**

- ⚠️ **全部成功或全部不動。** 其中一筆是別人的（403）、找不到（404）、
  在結算過的帳本裡（409），**就一筆都不刪**。先把每一筆檢查完，再在同一個
  資料庫交易裡刪。刪到一半才失敗的話，使用者根本不知道哪些已經不見了。

  網址放名詞、動作放方法（見專題文件的 RESTful 那一頁）；用查詢字串帶 id，
  不用 DELETE 帶主體（有些代理伺服器會把 DELETE 的主體丟掉）。
- 工具：`toolkit/ledger.py` 的 `clean_ids(raw)`（去空白、去重複、空的丟錯、超過 100 筆丟錯）
  ＋ 每一筆 `require_editable`。

### `POST /api/nlp/parse-batch` — 段落解析 ★ 系統核心

**前端呼叫**　`API.nlpParseBatch(text)`　**用在**　記帳頁

**請求主體**

```json
{ "text": "早上買早餐55，中午跟同事吃飯320，晚上加油1200，今天打工賺了1500" }
```

**回應**

```json
{
  "raw": "早上買早餐55，中午…",
  "matched": false,
  "items": [
    {
      "seq": 1,
      "span": "早上買早餐55",
      "date": "2026-09-10",
      "amount": 55,
      "kind": "expense",
      "cat": "C08",
      "merchant": "",
      "note": "",
      "conf": { "date": 0.93, "amount": 0.99, "kind": 0.97, "cat": 0.88 },
      "missing": [],
      "hint": ""
    }
  ],
  "note": "這段話被切成 5 筆。切分本身也是模型的判斷…"
}
```

**前端拿去幹嘛**（這支最複雜，看仔細）

| 欄位 | 前端的行為 |
|---|---|
| `items` | 一列一筆，畫成可編輯的表格 |
| `seq` | 表格最左邊的編號 |
| `span` | 顯示成「原句『…』」，讓使用者檢查**切分**對不對 |
| `amount` **可以是 `null`** | 抽不到就傳 `null`，該格顯示紅框「缺」 |
| `missing` | **陣列裡有哪一欄，那一欄就標紅 + 加「必填」** |
| `conf.xxx < 0.85` | 那一格標黃並顯示百分比 |
| `hint` | 顯示在原句下方的小字提示 |
| 有任何一筆 `missing` 非空 | **送出鈕停用**，顯示「還有 N 筆缺欄位，共 M 筆」 |

**陷阱**

- ⚠️ **這支絕對不可以寫進資料庫。** 只解析，使用者確認後才由
  `confirm-batch` 寫入。這是整個設計最重要的一條。
- ⚠️ **抽不到就回 `null` + 放進 `missing`，不要猜一個數字。**
  空白使用者一定會發現；猜錯的數字他可能直接按下確認就送出去了。
- `conf` 是**逐欄**的，不是整筆一個分數。模型常常是「金額很確定、分類不確定」，
  逐欄給，前端才能只把分類那一格標黃。
- `cat` 回傳的必須是**真的存在的分類 ID**。模型自己編一個名稱回來的話，
  前端的下拉選單會找不到，那一格會空白。

### `POST /api/nlp/confirm-batch` — 確認後一次寫入

**前端呼叫**　`API.nlpConfirmBatch(items)`　**用在**　記帳頁按下「確認並寫入 N 筆」

**請求主體**

```json
{ "items": [ { "span": "早上買早餐55", "date": "2026-09-10", "amount": 55,
               "kind": "expense", "cat": "C01", "merchant": "", "note": "", "groupId": "G1",
               "orig": { "by": "model", "date": "2026-09-10", "amount": 55, "kind": "expense",
                         "cat": "C08", "merchant": "", "note": "" } } ] }
```

外層的欄位是**使用者確認或修改過**的值，照這些寫進 `transactions`。
`orig` 是解析當下的原始結果，前端記下來、使用者怎麼改都不動它——兩邊不一樣的欄位就是模型抓錯的地方。
`groupId` 只有第一筆會帶（記進目前正在看的那本帳），不帶就記進第一本還沒結算的帳。
前端還會多送 `seq`、`conf`、`missing`、`hint`，後端忽略即可。

**回應**　`{ "created": 5 }`

**陷阱**

- ⚠️ **要嘛全部成功，要嘛全部不寫**（同一個資料庫交易）。
  寫到第 3 筆失敗的話，前面 2 筆已經進去了，使用者看到「寫入失敗」
  但明細裡多了兩筆，**然後他會再按一次，變成重複記帳**。
- ⚠️ **同時要寫 `nlp_parses`**：`raw` = `span`、`model_output` = `orig`、`user_corrected` = 跟 `orig` 不一樣的那幾欄。
  這是資料飛輪的入口，漏掉的話第 3 週就沒有訓練資料。
- ⚠️ **`orig.by` 是 `"rules"` 的不算模型的成績**：那是後端還沒接上時前端規則解析的。算正確率時要濾掉。
- `orig` 是前端送來的，只拿來當評測資料，**不影響寫進 `transactions` 的內容**。

### `POST /api/nlp/parse` / `POST /api/nlp/confirm` — 單句版

跟批次版一樣，差別只在一次一筆。

- `parse` 請求 `{ "text": "早餐55" }`，回應：

  ```json
  { "raw": "早餐55", "matched": false,
    "out": { "date": "2026-09-14", "amount": 55, "kind": "expense", "cat": "C01",
             "merchant": "", "conf": 0.9, "catConf": 0.75 },
    "note": "…" }
  ```

  前端檢查 `out` 一定要在（`SHAPE`）。一樣**不可以寫進資料庫**。
- `confirm` 請求是使用者確認過的那一筆（`date`、`amount`、`kind`、`cat`、`merchant`、`note`、`raw`、`groupId`），
  回應是新建立的那一筆交易（`source` 是 `"nlp"`）。

**前端目前沒有畫面在用這兩支**（段落版已涵蓋），優先序可以降低。後端還沒做時，`parse` 由前端規則頂著。

### `GET /api/categories` — 分類體系

**前端呼叫**　`API.categories()`　**用在**　記帳頁與修改紀錄的分類下拉、前端補名稱的對照表

**回應**

```json
{ "categories": [
  { "id": "C01", "name": "餐飲", "kind": "expense", "color": "cat-food", "icon": "食", "custom": false },
  { "id": "C21", "name": "寵物", "kind": "expense", "color": "cat-other", "icon": "寵", "custom": true, "familyId": "F1" }
] }
```

**陷阱**

- 系統預設分類（`family_id IS NULL`）＋ **我們家**的自訂分類。別人家的自訂分類不回。
- 系統預設分類由 `python -m app.cli init-db` 放進去，名稱、收支、顏色跟 `data.js` 的 `categories` 一致（測試會比對）。

### `POST /api/advices/generate` — 產生這個月的建議

**前端呼叫**　`API.generateAdvices({ scope })`　**用在**　財務建議頁的「產生這個月的建議」（我／全家）

### `PUT /api/auth/me/avatar` — 上傳大頭貼

**前端呼叫**　`API.uploadAvatar(dataUri)`　**用在**　個人資料頁

**請求主體**

```json
{ "image": "data:image/jpeg;base64,/9j/4AAQSkZJRgABAQ..." }
```

**回應**

```json
{ "avatarUrl": "data:image/jpeg;base64,/9j/4AAQ...", "avatar": "明" }
```

**前端拿去幹嘛**

- `avatarUrl` 有值 → 顯示圖片
- `avatarUrl` 是 `null` → 退回顯示 `avatar` 那個文字

**這個設計是刻意的**：`avatar`（單一中文字）保留不動，
另外加一個可為 null 的 `avatarUrl`。這樣**前端現有的文字頭像完全不用改**，
只要多一層「有圖就用圖」的判斷。

**陷阱**

- ⚠️ **Render 的磁碟是暫時性的。** 檔案寫進 `/uploads/` 這種地方，
  服務重新部署或重啟之後**就不見了**。免費方案沒有持久磁碟。<br>
  所以大頭貼要**存資料庫**（`users.avatar_bytes BYTEA` + `avatar_mime TEXT`）。
  大頭貼縮到 256×256 之後大約 20~50 KB，存資料庫完全沒問題。
- ⚠️ **縮圖在前端做。** 後端縮圖要裝 Pillow，映像檔會大好幾十 MB。
  瀏覽器的 canvas 本來就會縮圖，`canvas.toBlob()` 一行搞定。
- ⚠️ **不可以只看副檔名或 `Content-Type` 判斷是不是圖片。**
  那兩個都是使用者說了算的，可以隨便偽造——
  有人可以把一個腳本改名成 `avatar.jpg` 上傳。<br>
  後端要用 `toolkit.images.validate_avatar()`，它看的是
  **檔案開頭的識別位元組**，那是格式本身的一部分，偽造不了。
- 大小上限 **200 KB**，超過回 422。沒有上限的話有人上傳 500 MB 就能把服務打掛。
- 用 **PUT 不是 POST**：換大頭貼是「把它設定成這張」，
  做幾次結果一樣，所以是冪等的。

**後端大概長這樣**

```python
from app.guards import login_required
from app.toolkit import crud, errors, images

@router.put("/auth/me/avatar")
@login_required
def upload_avatar(body: AvatarIn, me: User, db: Session = Depends(get_db)):
    try:
        data, mime = images.from_data_uri(body.image)
    except images.InvalidImage as exc:
        raise errors.unprocessable(str(exc)) from exc

    crud.save(User, {"id": me.id, "avatar_bytes": data, "avatar_mime": mime}, db=db)
    db.commit()
    return {"avatarUrl": images.to_data_uri(data, mime), "avatar": me.display_name[-1:]}
```

## 監管是唯讀的 ⚠️ 這一節請整組讀過

### 三條界線

| 管理者可以 | 管理者不可以 |
|---|---|
| ✅ 看子女的記帳明細 | ❌ 修改子女的紀錄 |
| ✅ 看子女的統計與超支狀態 | ❌ 刪除子女的紀錄 |
| ✅ 收到子女新增紀錄的通知 | ❌ **登入子女的帳號** |

**第三條最重要，而且不只是安全問題，是產品決定。**

監管的正當性建立在「看得到但碰不到」。如果管理者能登入對方的帳號，
被監管的人就**無法信任自己的紀錄沒有被動過手腳** —— 那整個監管機制的信任基礎就沒了。

所以：

- 前端的「切換身分」鈕**已經拿掉了**，改用真正的登入／登出
- `POST /api/auth/switch`（管理者登入子女帳號）**任何一端都不可以做**
- 管理者要看子女的資料，走 `GET /api/transactions?userId=U3`，**不是換身分**
- ⚠️ **看得到誰，只有三條路，而且都寫在資料裡：**

  ```sql
  -- 我看得到誰的全部紀錄
  SELECT :me AS user_id                                   -- 1. 自己
  UNION
  SELECT ward_id FROM guardianships                       -- 2. 我照看的人
   WHERE guardian_id = :me AND ended_at IS NULL
  UNION
  SELECT fm.user_id FROM family_members fm                -- 3. 同一個家庭的其他家長（我也是家長時）
    JOIN family_members me ON me.family_id = fm.family_id
   WHERE me.user_id = :me AND me.role = 'parent' AND me.status = 'active'
     AND fm.role = 'parent' AND fm.status = 'active';
  ```

  **角色只打開「家長之間」這一扇。** 家長看子女一定要有監管關係——
  是家長不等於看得到每個孩子的消費明細：前者是「管得動」，後者是「看得到」，是兩件事。
  沒有照看任何孩子的家長，就只看得到自己和另一位家長。

  這樣做的理由是：「誰看得到我」必須是一份**可以查、可以列出來**的清單。
  一旦寫成 `if role == 'parent': return everyone`，被監管的人就無法確認
  自己的紀錄到底被誰看過。

  ⚠️ **監管是單向的。** 你看得到我，不代表我看得到你。
  被監管的人看不到任何別人，包含監管他的人。

  規則寫在 `toolkit/scope.py`（`visible_users()`），去資料庫拿資料餵進去的是 `guards.visible_scope()`。
- ⚠️ **看不到那個人，連他的存款目標也不要送。**
  名字、角色、監管關係是公開的（被監管的人必須知道自己被誰看著），
  但收入、支出、預算、存款目標是個人財務資料，
  **不在可見範圍內就不要放進回應裡**。前端把欄位藏起來不算保護。
- 前端的路徑是 `#/member/U3`（家庭成員頁點某一張卡片進去），
  從通知點進來會變成 `#/member/U3/T1051`——**那一筆會用藍框標起來**，
  不然使用者還要自己在一長串紀錄裡找是哪一筆。
  這個畫面上**每一列都沒有刪除鈕**，只有「唯讀」標記。

### 後端要怎麼擋

守衛已經寫好（`app/guards.py`），**看**跟**改**是兩個不同的守衛：

```python
from app.guards import guard, own, visible_scope

@router.get("/transactions")                      # 看：監管 ∪ 同帳本
def list_tx(me=Depends(guard()), db=Depends(get_db)):
    users, groups = visible_scope(me, db)
    rows = crud.find(Transaction, {"or": [{"user_id__in": users}, {"group_id__in": groups}]})

@router.patch("/transactions/{tx_id}")            # 改：只認本人
def update_tx(body: TxPatchIn, tx=Depends(own(Transaction, "tx_id")), db=Depends(get_db)):
    ...                                           # 別人的回 403「這是別人的資料，你只能檢視」
```

⚠️ 「看得到」和「改得動」**不是同一件事**，不要共用一個判斷。
這是很容易偷懶的地方，偷懶的後果是監管者可以改小孩的帳。

## 即時通知

### 為什麼用輪詢，不用 SSE 或 WebSocket

看起來 SSE 更「即時」，但它有一個硬傷：

> **`EventSource` 沒辦法送自訂標頭。**
> 你不能帶 `Authorization: Bearer <token>`，只能把 token 放在網址上。

而網址會進**瀏覽器歷史、伺服器日誌、Referer 標頭、代理伺服器**。
為了 SSE 破壞「token 絕不放查詢參數」這條規則，不划算。

WebSocket 可以帶標頭，但要另外處理連線管理、斷線重連、
多個 worker 之間的廣播 —— **對一個六週的專題來說太重了**。

**輪詢 20 秒**對「子女記了一筆帳」這種通知完全夠用。而且：

- 斷線重連是免費的（下一次輪詢自然就接上了）
- 過代理伺服器不會有問題
- Render 免費方案的服務休眠不會讓它壞掉

---

### `GET /api/notifications` — 通知清單

**前端呼叫**　`API.notifications({ since })`　**用在**　右上角的通知鈴鐺

**請求**

| 參數 | 型別 | 說明 |
|---|---|---|
| `since` | `str` | 上次拿到的最大 id。**只回比它新的**，第一次不帶 |
| `unreadOnly` | `bool` | 只要未讀的 |

**回應**

```json
{
  "notifications": [
    {
      "id": "N12",
      "type": "ward_transaction",
      "actorId": "U3", "actorName": "王小華",
      "txId": "T1051",
      "amount": 320, "cat": "C01", "catName": "餐飲", "merchant": "全家",
      "createdAt": "2026-09-11T13:20:05Z",
      "readAt": null
    }
  ],
  "unread": 3,
  "maxId": "N12"
}
```

**前端拿去幹嘛**

- `unread` → 鈴鐺上的紅點數字
- 有新的（`maxId` 變了）→ **播提示音 + 跳出通知**
- `actorName`、`amount`、`catName`、`merchant` → 組成通知文字：
  「王小華剛記了一筆 餐飲 NT$ 320（全家）」
- `txId` → 點通知跳到那一筆
- `maxId` → 存起來，下次當 `since` 傳回去

**陷阱**

- 三種 `type`：`ward_transaction`（我照看的人記帳）、`group_transaction`（我開了通知的帳本有人記帳）、
  `budget_alert`（我的支出跨過我設的門檻）。前兩種由記帳的路由寫進去；**`budget_alert` 就是這一支自己檢查後寫的**
  （見下面「階段性提醒」），所以這支 GET 會寫資料——那是刻意的，提醒只發給設門檻的人自己。
- ⚠️ **一定要用 `since` 分頁，不要每次都回全部。**
  通知會一直累積，三個月後一次回三千筆，手機會當掉。
- ⚠️ **`unread` 是「總未讀數」，不是「這次回傳那幾筆裡的未讀數」。**

  這個很容易寫錯：如果用分頁後的結果去算，第二次輪詢帶了 `since`、
  沒有新通知、回傳空陣列，`unread` 就變成 0，**紅點會被清掉**，
  使用者以為自己看過了。

  ```sql
  -- ✅ 對：不受 since 影響
  SELECT COUNT(*) FROM notifications
   WHERE recipient_id = :me AND read_at IS NULL;
  ```

  （這個 bug 我在實作 mock 時真的踩到了，所以特別寫出來。）
- ⚠️ **只回「我該收到的」通知。** 通知是寫給特定收件人的，
  查詢時要 `WHERE recipient_id = 我`，不是用監管關係現算——
  監管關係解除之後，舊的通知還是屬於當時的收件人。
- `createdAt` 用 **ISO 8601 + UTC**（結尾 `Z`），前端自己轉本地時間。
  回「3 分鐘前」這種字串的話，前端就沒辦法排序或重新計算了。
- ⚠️ **`notifications` 由新到舊排（最新的在 `[0]`），但 `maxId` 要給「整體最新」的那一個。**

  這兩件事很容易打架。清單是新→舊，所以「最後一筆」是**最舊的**——
  如果順手寫成 `maxId = rows[-1].id`，下次帶著這個 `since` 回來，
  比它新的全部都會被算成「已經給過了」，**新通知永遠進不了清單**，
  但 `unread` 又是用全部算的，於是紅點跳動、清單卻不動。

  ```sql
  -- 查詢：只拿比 since 新的，由新到舊
  SELECT * FROM notifications
   WHERE recipient_id = :me
     AND (:since IS NULL OR id > :since)
   ORDER BY id DESC
   LIMIT 20;

  -- maxId 另外查，不要從上面那批取
  SELECT MAX(id) FROM notifications WHERE recipient_id = :me;
  ```

  （這個我也踩到了。前端 `state.items = 新的.concat(舊的)` 靠的就是新→舊這個順序。）
- ⚠️ **`since` 是嚴格大於（`>`），不是大於等於。**
  寫成 `>=` 的話，每次輪詢都會把同一筆重送一遍，於是每 20 秒叮一聲、
  清單裡出現重複的同一筆。

### 前端的音效怎麼做

⚠️ **不要放 mp3 檔案。** 用 Web Audio API 直接合成一個短音：

```js
const ctx = new AudioContext();
const osc = ctx.createOscillator();
const gain = ctx.createGain();
osc.frequency.value = 880;
gain.gain.setValueAtTime(0.15, ctx.currentTime);
gain.gain.exponentialRampToValueAtTime(0.001, ctx.currentTime + 0.3);
osc.connect(gain); gain.connect(ctx.destination);
osc.start(); osc.stop(ctx.currentTime + 0.3);
```

好處：**不用託管音檔、不用等下載、離線也能響**。

⚠️ **瀏覽器會擋自動播放。** 使用者第一次跟頁面互動（點任何東西）之前，
`AudioContext` 會是 `suspended` 狀態。所以要在第一次點擊時 `ctx.resume()`。

⚠️ **一定要有靜音開關**，存在 `localStorage`。
半夜跳出聲音會讓人直接關掉整個系統。

## 認證怎麼串（前端已經做好了）

前端有登入頁（`#/login`）、註冊頁（`#/register`）、個人資料頁（`#/profile`），
`req()` 會自動帶 `Authorization: Bearer`，收到 401 會自動續期並把請求重送一次。
**後端只要把下面這幾支做出來、形狀對得上，前端一行都不用改。**

```
1. 登入頁送 POST /api/auth/login  { email, password }
2. 後端回 { accessToken, refreshToken, expiresIn, user }
3. 前端存進 localStorage['fambudget.auth']，
   之後每個請求帶 Authorization: Bearer <accessToken>
4. 收到 401 → 自動打 POST /api/auth/refresh { refreshToken }
   → 拿到新的 accessToken → 把剛才失敗的請求重送一次
5. 登出 → POST /api/auth/logout，前端清掉 token
```

**閒置太久會先問，不會直接把人踢掉。**

`expiresIn`（access token 還有幾秒過期，後端 `ACCESS_TOKEN_MINUTES` 決定，預設 30 分鐘）
前端會存下來，當成「閒置多久要問一次」的門檻：

| 狀況 | 畫面 |
|---|---|
| 閒置滿 `expiresIn` 秒（沒有點、沒有打字、沒有捲動） | 跳出「還在嗎？」，倒數 60 秒 |
| 按「繼續使用」 | 打 `POST /api/auth/refresh` 換新的 token，留在原地，什麼都沒掉 |
| 按「登出」，或倒數歸零 | `POST /api/auth/logout` → 回登入頁 |
| 換不到新的 token（refresh token 也過期或被撤銷） | 直接回登入頁，提示「登入已經過期，請重新登入」 |

⚠️ 這一層是**體感**，不是安全機制——真正的保護是後端的 token 會過期。
前端只是讓過期這件事**被看見**，不要變成使用者回來點一下就沒頭沒尾地跳回登入頁、
正在填的東西一起不見。所以後端不用為它多做任何一支，`expiresIn` 照常回就好。

### `POST /api/auth/register` — 註冊

**前端呼叫**　`API.register({ name, email, password })`

**回應**　同 `login`（註冊完直接登入，不用再叫使用者登一次）；新帳號 `role` 是 `null`、`onboardedAt` 是 `null`、`theme` 是 `paper`

**陷阱**

- ⚠️ **email 要存成小寫**，比對時也要小寫。
  `Ming@lin.tw` 跟 `ming@lin.tw` 是同一個人，讓他註冊兩次之後誰都登不進去。
- ⚠️ **「這個 email 已經註冊過了」要回 409，不是 422。**
  409 Conflict 的語意就是「跟現有資源衝突」。
- 密碼規則用 `toolkit.passwords.check_strength()`，不要自己寫一套。
- ⚠️ **存款目標不在註冊時問。** 主體帶了 `savingsGoal` 回 **400**——舊前端塞進來的值被默默吃掉，

  每月想存多少（`PUT /api/savings-goal`）→ 理財習慣（`PUT /api/auth/me/finance`）→ 主題（`PATCH /api/auth/me`）。
  為什麼搬：塞在註冊表單裡，大部分人會隨便填 0 先過，總覽的「還可以花」就沒有意義。

### `POST /api/auth/password-reset` — 忘記密碼：寄重設信

**前端呼叫**　`API.requestPasswordReset(email)`　**用在**　登入頁的「忘記密碼？」

**請求主體**　`{ "email": "daming@wang.tw" }`

**回應**（⚠️ **有沒有這個帳號都一模一樣**）

```json
{ "ok": true, "message": "如果這個 email 有註冊，重設密碼的信已經寄出，30 分鐘內有效。" }
```

**後端要做的事**

```python
from app.toolkit import password_reset as pr, mailer

email = pr.normalize_email(body.email)                  # 格式不對 → 400
user = 找 users（email 小寫比對）
if user and pr.should_send(那個人最近一筆 password_resets.created_at):
    token = pr.new_token()
    寫一列 password_resets(user_id, token_hash=pr.hash_token(token), expires_at=pr.expires_at())
    subject, text, html = pr.mail_content(user.display_name, pr.reset_link(settings.app_base_url, token))
    mailer.send_mail(user.email, subject, text, html, to_name=user.display_name)
return {"ok": True, "message": pr.GENERIC_MESSAGE}      # 找不到人、冷卻中，都回這句
```

**陷阱**

- ⚠️ **「沒這個帳號」絕對不能講出來**，狀態碼也要一樣。講了，這支就是帳號列舉工具——
  不用猜密碼，先把「哪些 email 有註冊」撈出來再下手。回應時間也盡量不要差太多。
- ⚠️ **token 只存雜湊**（`hash_token`）。資料庫外流時，拿到的東西點不開任何連結。
- ⚠️ **寄信走 Brevo 的 HTTP API，不能用 SMTP。** Render 免費方案從 2025-09-26 起擋掉
  連外的 25／465／587 埠：smtplib 在本機會通，部署上去就永遠逾時。
  金鑰 `BREVO_API_KEY`、寄件信箱 `MAIL_FROM` 在 Render 後台填，**不可以 commit**。
- 寄信失敗（`MailError`／`MailNotConfigured`）要記 log，**回應照樣回 `GENERIC_MESSAGE`**——
  回錯誤的話，「寄信失敗」只會發生在帳號存在的時候，一樣洩漏帳號在不在。
- 同一個人 60 秒內不重寄（`should_send`），不然任何人都能拿你的 email 一直轟炸你的信箱。
- 連結長成 `https://fambudget-web.onrender.com/#/reset/<token>`：token 在 **# 後面**，
  瀏覽器不會把它送給伺服器，不會留在伺服器紀錄、也不會跟著 Referer 外洩。
- mock（沒有後端時）會多回一個 `demoMail`（信的內容），因為瀏覽器寄不出信，只好把連結攤在畫面上。**真後端絕對不能回這個欄位**，那等於把重設連結交給任何輸入別人 email 的人。

### `POST /api/auth/password-reset/confirm` — 用信裡的連結設新密碼

**前端呼叫**　`API.confirmPasswordReset(token, password)`　**用在**　`#/reset/<token>` 設定新密碼頁

**請求主體**　`{ "token": "1mO04jDjqJpRQT4V6_buPYtuq5EAZkNb8rJdCcnx_hY", "password": "………" }`

**回應**　`{ "ok": true }`

**後端要做的事**

```python
row = 用 pr.hash_token(body.token) 找 password_resets   # token 格式不對 hash_token 會丟 ValueError
pr.require_usable(row.expires_at if row else None, row.used_at if row else None)
passwords.check_strength(body.password)                  # 太弱 → 422
user.password_hash = passwords.hash_password(body.password)
row.used_at = now()
這個人所有的 sessions 設 revoked_at = now()
```

**陷阱**

- ⚠️ **找不到、過期、用過，回同一句話**（400，`pr.INVALID_MESSAGE`），不讓人分辨是哪一種。
- ⚠️ **成功後撤銷這個人所有的 sessions。** 連結可能是別人翻到信箱拿去用的，

- 30 分鐘失效、**只能用一次**：`used_at` 要跟改密碼在同一個資料庫交易裡寫進去。
- 前端拿到 token 之後會把它從網址列拿掉（`history.replaceState`），不留在瀏覽紀錄裡。

### `POST /api/auth/login` — 登入

**回應**

{
  "accessToken": "eyJhbGciOiJIUzI1NiJ9...",
  "refreshToken": "eyJhbGciOiJIUzI1NiJ9...",

### `POST /api/auth/refresh` — 換新的 access token

**前端呼叫**　`req()` 自動打，畫面程式碼不會直接叫它

**請求主體**　`{ "refreshToken": "..." }`
**回應**　`{ "accessToken": "...", "refreshToken": "...", "expiresIn": 1800 }`

**陷阱**

- ⚠️ **refresh token 要輪替**：換發新的，同時把舊的撤銷（`sessions` 那一列標記失效）。
  不輪替的話，一條外洩的 refresh token 可以用滿 14 天。
- ⚠️ **前端同時只會打一次 `/refresh`。**
  一次載入會同時發好幾個請求，過期時它們會一起收到 401；
  前端用一個「續期中」的旗標擋住，只有第一個會真的去換，其他的等它。
  後端也要能承受重送（同一個 refresh token 連打兩次）——
  **回 401 就好，不要把使用者的所有 session 都撤銷**，
  那會變成「網路抖一下就被登出所有裝置」。
- ⚠️ **這支不要驗 access token**，它的存在意義就是 access token 已經死了。

### `POST /api/auth/logout` — 登出

**請求主體**　`{ "refreshToken": "..." }`
**回應**　`204 No Content`（或 `{ "ok": true }`，前端不看回應）

**陷阱**

- ⚠️ **後端失敗了，前端還是會把本機的 token 清掉。**
  使用者按了登出就一定要登出，不能因為伺服器沒回應就把他留在登入狀態。
  所以這支要做成**冪等**的：重複登出、token 已經失效，都回 204，不要噴 400。
- access token 是無狀態的，撤不掉——它會自己在 30 分鐘內過期。
  真正被撤銷的是 refresh token。要立刻全面失效的話用 `/api/auth/logout-all`。

### `POST /api/auth/verify-password` — 重大操作前再確認一次密碼

**前端呼叫**　`API.verifyPassword(password)`　**用在**　移出家人、退出／解散家庭、改角色、移除帳本之前的確認視窗

**請求主體**　`{ "password": "………" }`　**回應**　`{ "ok": true }`；不對回 **400**「密碼不正確」

**陷阱**

- ⚠️ **密碼不對回 400，不是 401。** 401 對前端的意思是「access token 過期了」，`req()` 會先去續期再重送一次——
  每打錯一次密碼就白白換一次 token。（改密碼時舊密碼不對也是 400，同一個道理。）

## 群組（帳本）

一個家庭可以開好幾本帳：家用、旅遊基金、小華的零用。
**每一筆記帳都屬於其中一本**，而且每一本可以各自設一個每月存款目標。

分類回答「錢花在什麼」，群組回答「這筆算在哪一份預算上」——兩個是不同的軸。

### 可見範圍是兩條路的聯集

```sql
-- 過一條就看得到。⚠️ 是 OR，不是 AND
SELECT * FROM transactions t
 WHERE t.user_id IN (                    -- A：我或我監管的人記的
         SELECT :me
         UNION SELECT ward_id FROM guardianships
          WHERE guardian_id = :me AND ended_at IS NULL)
    OR t.group_id IN (                   -- B：記在我有加入的帳本裡
         SELECT group_id FROM group_members WHERE user_id = :me)
```

兩條各自回答一個不同的問題：

- **A 是監管。** 家長對子女的可見度不該被帳本切斷——否則子女只要另外開一本
  不加家長的帳，記在那裡就完全躲掉了。他甚至不用離開任何群組，
  所以「離開群組要核准」也堵不住這個洞。
- **B 是分享。** 把誰加進帳本，就是選擇讓他看到那本帳，這是記帳的人
  自己的行為。共用帳本只分享那一本，不是分享整個人。

⚠️ **寫成 `AND` 就變回交集了**，那是早期版本的錯：它讓監管一鍵可繞，
同時又讓「把人加進帳本」什麼也不代表。

⚠️ **算某個人的統計時只走 A。** 加上 B 會把共用帳本裡別人的錢
算進這個人的總額——家用帳本裡配偶花的錢，不該出現在我的支出裡。

工具箱有寫好的：`toolkit.scope.visible_users()` / `visible_groups()` / `filter_rows()`。

### `GET /api/groups` — 我加入的群組

**前端呼叫**　`API.groups()`／`API.groups({ includeArchived: true })`
**用在**　右上角的切換器、群組管理頁

| 參數 | 型別 | 說明 |
|---|---|---|
| `includeArchived` | `bool` | 連封存的一起回。預設 `false` |

**回應**

```json
{
  "me": "U1",
  "groups": [
    { "id": "G1", "name": "家用", "icon": "用", "color": "book-indigo",
      "owner": "U1", "note": "日常開銷，全家共用", "created": "2026-01-05",
      "kind": "standing", "endsOn": null, "settledAt": null,
      "archived": false, "settled": false, "overdue": false,
      "members": ["U1", "U2", "U3", "U4"],

      "count": 7, "goal": 0, "canEdit": true, "notify": false }
  ]

```

**陷阱**

- ⚠️ **只回我加入的。** 別人的帳本<b>連名字都不該看到</b>。
- ⚠️ **`count` 要算「我實際看得到的筆數」，用跟明細同一條規則。**

  這個我踩到了：一開始 count 和明細用了不一樣的條件，
  切換器上寫「家用 10 筆」，點進去卻只有 7 筆。
  數字和清單只要不是同一段條件算出來的，遲早會對不起來。
  **面板上的數字和點進去看到的必須一致**，否則使用者會以為系統壞了。
- `canEdit` 是「我是不是建立者」。改名、加人、封存、結算都只有建立者能做。
- `kind`：`standing` 一般帳本、`temp` 活動帳本（有 `endsOn` 結束日）。`overdue` = 活動帳本過了結束日還沒結算，畫面會提醒。
- `notify` 是**我自己**在這本帳的通知開關（`group_members.notify`）。

### `POST /api/groups` — 建立

**請求主體**　`{ "name": "旅遊基金", "color": "book-violet", "note": "", "kind": "temp", "endsOn": "2026-10-05" }`

`kind` 不帶是 `standing`；`temp` 一定要帶 `endsOn`（400）。
**回應**　建立好的群組

**權限：只要登入就可以建，不看角色。**
`member` 也能開自己的帳本，而且他是那本帳的建立者（可以改名、加人、封存）。
這是刻意的——**記帳的分類方式是個人的事，不該由家裡的階級決定**。
家裡的階級管的是「誰看得到誰的錢」，不是「你能不能替自己的開銷分類」。

**陷阱**

- ⚠️ **建立者要自動寫一筆 `group_members`。**
  漏了的話他自己也看不到剛建的帳本——`GET /api/groups` 是用 group_members 查的。
- **同一個家庭**裡名字不要重複（含已封存的），重複回 **409**。⚠️ 只比自己家的——比了別人家的，等於告訴使用者別的家庭有哪些帳本。

### `PATCH /api/groups/{gid}` — 改名稱／圖示／顏色，或**復原封存**
### `DELETE /api/groups/{gid}` — 封存；`?permanent=true` 移除

**請求主體**（PATCH）　`{ "name": "…" }`／`{ "color": "…" }`／`{ "archived": false }`
**回應**　PATCH 回更新後的群組；DELETE 回 `{ "id": "G2", "archived": true }`（移除：`{ "id": "G2", "removed": true }`）

**陷阱**

- ⚠️ **封存是設 `archived_at`，不是真的刪。**
  裡面的記帳紀錄還在，真刪了那些紀錄的 `group_id` 會變成孤兒。
- ⚠️ **封存在使用者眼裡跟刪除長得一模一樣**——那本帳從切換器、統計、
  清單裡通通消失了。所以這三件事缺一不可：

  1. `GET /api/groups?includeArchived=true` 要**看得到已封存的**
  2. `PATCH` 帶 `{"archived": false}` 要能**復原**
  3. 按下封存之前要**再確認一次**

  這是踩過才補的：我先做了封存、也在文件裡寫了「不是刪除」，
  但沒做出「看已封存的」和「復原」的畫面——
  **對使用者來說，一個救不回來的東西就是被刪掉了**，
  文件上怎麼定義不重要。
- 復原不需要還原任何資料。封存從頭到尾沒有動過任何一筆記帳，
  它只是讓那本帳重新出現在清單上。

**移除**：`DELETE /api/groups/{gid}?permanent=true`，只給**結算過的活動帳本**用。

- 只有建立者（403）；還沒結算回 **409**，請使用者改用封存（`toolkit/ledger.py` 的 `require_removable`）。
- ⚠️ **移除的是帳本，不是紀錄。** 設 `groups.removed_at`，`transactions` 一筆都不動：
  每一筆仍在記帳的人自己的收支明細與統計裡，**過去月份的數字不會變**。
- 移除後這本帳不出現在任何清單（包含 `includeArchived=true`），**不能復原**；
  它的 `group_members` 不再算數，所以「只靠這本帳看得到別人紀錄」的成員之後就看不到了。
- 前端按下去之前要輸入確認碼，文案要講清楚「紀錄不會刪」。寫一筆 `audit_logs`（`remove_group`）。

## 階段性提醒

使用者自己設幾個百分比門檻（例如 60%／85%／100%）。
支出佔**可支配上限**的比例跨過門檻，就發一則通知——走的是同一套通知鈴鐺。

```
可支配上限 = 本月收入 − 每月存款目標
```

所以百分比算的是「花掉可支配額度的幾成」，不是「花掉收入的幾成」。

### 判斷該不該發，比想像中容易寫錯

**誰在什麼時候檢查：`GET /api/notifications`（成員4）。**
提醒只發給「設門檻的人自己」，而他每 20 秒就會來拿一次通知——在那裡一次看完他所有的門檻就夠了，
記帳的三支路由（手動、單句、批次）不用各自再算一次。同一個門檻一個月只響一次，靠 `alert_rules.fired_period` 擋。

工具箱有寫好的 `toolkit.alerts`，直接用：

```python
from app.toolkit import alerts

reached = alerts.usage_percent(spent, allowance)          # 這個月已經用掉幾成（無條件捨去）

for rule in rules:                                        # 我開著、這個月還沒響過的門檻
    if not alerts.should_fire(rule.percent, 0, reached,
                              rule.fired_period, period_key):
        continue
    建立通知(rule)                    # notifications 寫一列 budget_alert
    rule.fired_period = period_key   # 記住這個月響過了
```

（`before` 傳 0 的意思是「還沒響過的門檻，從 0 算起」：用掉的成數到了門檻就發一次，之後這個月不再發。
 如果之後改成記帳時就檢查，`before` 就換成「這一筆之前的成數」，其他都一樣。）

**寫成 `if percent >= threshold` 會有三個 bug：**

- ⚠️ **每記一筆都會重發。** 已經 90% 了，再記一筆變 92%，
  `92 >= 85` 還是成立，於是又響一次。
  要比的是「這次之前」和「這次之後」，跨過的當下才算。
- ⚠️ **一次跨過好幾個門檻只響一次。** 80% 的時候記一筆大的直接跳到 105%，
  85 和 100 兩個都該通知。
- ⚠️ **下個月要重新開始。** 用 `fired_period`（`'2026-09'`）記住上次哪個月響的。

另外 `usage_percent` 是**捨去**不是四捨五入：79.9% 還沒到 80%，不該提前響。

### 提醒型通知長什麼樣

`GET /api/notifications` 會回三種 `type`：`ward_transaction`（我照看的人記帳）、
`group_transaction`（我開了通知的帳本裡有人記帳）、`budget_alert`（我的支出跨過我設的門檻）。
前兩種由記帳的路由寫進去，長得一樣（前端都顯示成「誰記了一筆什麼」）；第三種長這樣：

```json
{
  "id": "N31", "type": "budget_alert",
  "actorId": null, "actorName": null,
  "percent": 85, "reached": 103,
  "groupId": "G2", "groupName": "旅遊基金",
  "spent": 12800, "allowance": 5000,
  "createdAt": "2026-09-12T10:04:00Z", "readAt": null
}
```

**陷阱**

- ⚠️ **前端要用 `type` 判斷，不要靠「有沒有 actorName」去猜。**
  猜的那套在多一種通知的時候就會壞。
- ⚠️ **`percent` 是「你設的門檻」，`reached` 是「實際用掉幾成」，兩個都要送。**
  我一開始只送 `percent`，畫面上寫「已用掉 90%（NT$ 12,800 / NT$ 5,000）」——
  但 12,800 是 5,000 的 256%，讀起來像系統算錯了。

## 平台管理員

平台管理員**不屬於任何家庭、沒有任何財務資料**：只能停權與看稽核。
不能自己註冊成管理員——註冊之後由後端的人跑 `python -m app.cli make-admin 信箱`（或設 `ADMIN_EMAILS` 再跑 `make-admin`）。
所有財務路由對他一律 403（守衛 `@block_admin`）。

### `GET /api/admin/users` — 帳號清單

**前端呼叫**　`API.adminUsers()`　**用在**　平台管理頁

**回應**

```json
{ "users": [ { "id": "U3", "name": "王小華", "email": "xiaohua@wang.tw", "role": "child",
               "joined": "2026-02-11", "suspendedAt": null, "suspendedReason": null } ] }
```

**陷阱**　⚠️ **只有身分欄位**，`income`／`expense`／`savingsGoal` 一律不給。其他平台管理員不列。

- 不能停權平台管理員（`roles.require_suspendable`）；沒被停權的不能解除（400）。
- ⚠️ **停權只擋登入與之後的每一個請求，不刪任何資料。** 已經登入的人下一個請求就被擋（守衛每次都查 `suspended_at`），不是等 token 過期。
- 兩個動作都寫 `audit_logs`。

## 顏色是代號，不是色碼

`categories.color` 和 `groups.color` 存的是**語意代號**，例如 `cat-food`、
`book-indigo`——**不是 `#C4693C` 這種色碼**。

資料只說「這是餐飲」，實際顏色由 `frontend/css/tokens.css` 的
`--cat-food` 決定。這樣做的理由是換外觀：色碼寫在資料裡的話，
換一套外觀時圓餅圖和帳本圓點還是原來的顏色，跟整頁格格不入。

後端只要照存照回即可，但要**驗證代號在允許清單裡**（`groupColors` 那一份），
理由跟不讓使用者自造 goal id 一樣：這個字串最後會進到
`style="background:…"`，那是 CSS 的情境，HTML 跳脫擋不住。
前端還有一層 `tint()` 只放行 `[a-z0-9-]`，但後端不要依賴前端。

## 既知限制（本版刻意不做）

這一節寫的是**知道該做、但這一版決定不做**的東西，以及為什麼。
寫下來的目的是把它跟「沒想到」分開。

### 一、跨家庭共用帳本

帳本的成員只能從**同一個家庭**裡選。跟同學、同事共用一本活動帳本做不到。

不是漏掉，是每一個「列出人」的地方都得先學會分辨「在我的帳本裡、但不在我家」：
家庭成員頁、總覽的全家模式、帳本的加人選單、前端補名字的對照表（現在只查 `GET /api/family` 的成員）。
可見範圍本身不用改——同帳本那條路（`queryable`）本來就不看家庭。

做法是現成的：家庭已經有邀請碼（`POST /api/family/invite`、`/join`），同一套搬到帳本是兩支路由。
**真正的成本在「列出人」的那幾個地方，不在邀請碼。**

⚠️ 邀請走**系統內產碼**，不要走 email——理由在下一條。

### 二、安全類通知還沒有 email

現在的通知只有兩種：`ward_transaction`（監管對象記帳）和
`budget_alert`（跨過提醒門檻），**都是站內的**。改密碼、新裝置登入、
帳號被停權，目前不會通知任何人。

同意類（邀請、建立監管）留在站內是對的——對方已經是使用者，
站內更即時、不會進垃圾桶，而且只有一個地方要看。

**但安全類不一樣，它是 email 唯一無法被站內取代的場景：**
帳號被盜的時候，站內通知是給小偷看的。你需要一個攻擊者拿不到、
但本人拿得到的通道，那必須在系統之外。

本版的替代做法是**寫進 `audit_logs`**，事後查得到誰在什麼時候改了什麼。

⚠️ **正式上線前必須補**：改密碼、新裝置登入、停權三件事要寄信。
寄信的管道已經有了：忘記密碼用的 `toolkit/mailer.py`（Brevo 的 HTTP API；Render 免費方案擋 SMTP 埠，所以不用 SMTP）。
補的時候照忘記密碼那一支的做法：寄信失敗要記 log，但不能讓主要動作跟著失敗。
