# 前後端串接契約

> **這份文件是從前端程式跑出來的，不是手寫的。**
>
> 產生方式：把 `frontend/js/data.js` + `frontend/js/api.js` 的 mock 轉接器
> 實際執行一次，把每一支的真實回傳形狀 dump 出來。
>
> **所以這裡寫的形狀就是前端真的在吃的東西。** 後端照著做，
> 把 `frontend/index.html` 的 `<meta name="api-base">` 填上網址，畫面就會動。
> 形狀不對，畫面就會壞——沒有第三種可能。

---

## 先講四件必須先決定的事

這四個是**前端現況與一般後端寫法會打架的地方**。動工前四個人要先講好，
不然第一週結束接不起來。

### 1. ID 是字串，不是整數 ⚠️ 最重要

前端現在拿到的 ID 長這樣：

```
使用者   "U1"  "U2"  "U3"  "U4"
交易     "T1040"  "N1789124882105"
分類     "C01"  "C05"
建議     "A1"
```

但你用 SQLAlchemy 建表，主鍵自然會是 `int`（1, 2, 3...）。**這兩者對不上。**

**兩個選擇，挑一個，全組統一：**

| 選項 | 做法 | 代價 |
|---|---|---|
| **A. 後端回整數，前端改** | 主鍵就用 `int`，前端把 `"U1"` 改成 `1` | 要改 `data.js` 和 app.js 裡比對 ID 的地方 |
| **B. 後端回字串** | 回應時把 `id` 轉成 `str(id)` | 前端一行都不用改 |

**建議選 B。** 理由：前端已經完成並測試過了，改它是純風險；
而 JSON 的 ID 用字串本來就很常見（JavaScript 的 `Number` 在超過
2^53 之後會失去精度，所以大型系統的 ID 常常刻意用字串）。

選 B 的話，在 Pydantic 的回應模型上這樣寫：

```python
class TransactionOut(BaseModel):
    id: str                      # 不是 int
    model_config = ConfigDict(from_attributes=True)

    @field_validator("id", mode="before")
    @classmethod
    def _id_to_str(cls, v):
        return str(v)
```

### 2. `/api/auth/me` 的 `user` 裡混了統計數字

前端現在拿到的 `user` 物件是這樣：

```json
{ "id": "U1", "name": "林建國", "role": "parent", "avatar": "國",
  "age": 52, "joined": "2026-01-05",
  "income": 68000, "expense": 41230, "budget": 45000, "savingsGoal": 20000 }
```

**後面四個欄位不是使用者的屬性，是「本月統計」。** 放在 `/me` 裡意味著
每次打這支都要順便算一次統計，很怪。

**建議：** 後端照回，但**值從 `analytics` 算**，不要存在 `users` 表上。
或是跟前端講好拿掉，改從 `/api/summary` 拿（前端要改 `vHome` 和 `vMembers`）。

**先決定，不要一個人以為要回、一個人以為不用回。**

### 3. 明細每一筆要 JOIN 帶出顯示用的欄位

```json
{ "id": "T1040", "user": "U1", "cat": "C01",
  "userName": "林建國",          ← JOIN users
  "catName":  "餐飲",            ← JOIN categories
  "catColor": "#FF8A3D" }        ← JOIN categories
```

**前端不會自己去查使用者表和分類表。** 後端一定要在回應裡帶出來，
否則畫面上會顯示空白。

### 4. `/api/stats` 前端根本沒在用

我逐個畫面查過前端實際呼叫的 API：

| 畫面 | 用到的 API |
|---|---|
| 我的總覽 | `me` · `summary` · `transactions` · `budgets` |
| 記帳 | `nlp/parse-batch` · `nlp/confirm-batch` · `transactions` |
| 家庭總覽 | `me` · `summary` · `budgets` |
| **統計** | **`summary` 而已** |
| 財務建議 | `advices` |
| 成員與權限 | `family` · `savings-goal` |

**統計頁只打 `summary`** —— 因為 `summary` 的回應裡已經包含
`byCat`（分類佔比）、`monthly`（近 6 個月）、`yearly`（近 3 年）。

所以 `GET /api/stats` **可以不做**，優先序降到最低。

## 怎麼接：三步驟

### 第 1 步　後端先回得出形狀，值可以是假的

```python
@router.get("/summary")
def summary():
    return {"period": "2026-09", "scope": "me", "income": 0, "expense": 0,
            "net": 0, "rate": 0, "count": 0,
            "savings": {...}, "byCat": [], "monthly": [], "yearly": [], "members": []}
```

**形狀對了，畫面就不會壞**，只是數字是 0。這時前端就能開始接了。

### 第 2 步　前端切換到真後端

改 `frontend/index.html` 這一行：

```html
<meta name="api-base" content="https://fambudget-backend.onrender.com">
```

留空 = mock 模式。填上網址 = 改打真後端。

### 第 3 步　一支一支換成真資料

`mock` 與 `http` 兩個轉接器的**簽章完全一致**，所以可以慢慢接。
哪支後端做好了就哪支動，其他的繼續用假值。

## 逐支契約

下面每一支都寫清楚：**前端怎麼呼叫、你要收什麼、你要吐什麼、前端拿去幹嘛。**

型別標記說明：`int` 整數、`float` 小數、`str` 字串、`bool` 真假、`[...]` 陣列。

---

### `GET /api/auth/me` — 我是誰

**前端呼叫**　`API.me()`　**用在**　我的總覽、家庭總覽

**請求**　無參數，只帶 `Authorization: Bearer <access_token>`

**回應**

```json
{
  "user": {
    "id": "U1", "name": "林建國", "role": "parent", "avatar": "國",
    "age": 52, "joined": "2026-01-05",
    "income": 68000, "expense": 41230, "budget": 45000, "savingsGoal": 20000
  },
  "family":  { "family": "林家", "period": "2026-09", "updated": "...", "currency": "TWD" },
  "visible": ["U1", "U2", "U3", "U4"],
  "guardedBy": []
}
```

**前端拿去幹嘛**

- `user.role` → 決定側欄顯示哪些項目（`member` 看不到家庭總覽）
- `user.avatar` → 左下角的頭像字（**一個中文字**）
- `visible` → 我看得到哪些人，用來過濾畫面
- `guardedBy` → **有值就在總覽頁顯示「誰看得到你的紀錄」**

**陷阱**

- `guardedBy` 是**被監管者自己**要看的，不是只有管理者能拿。這是刻意的設計。
- `family.period` 是目前的結算月份，前端很多地方拿它當預設值。

---

### `GET /api/summary` — 總覽的所有數字

**前端呼叫**　`API.summary({ scope, period })`　**用在**　我的總覽、家庭總覽、**統計頁**

**請求**

| 參數 | 型別 | 說明 |
|---|---|---|
| `scope` | `str` | `me` 只看自己、`family` 看全家。預設 `me` |
| `period` | `str` | `2026-09`。不帶就是本月 |

**回應**

```json
{
  "period": "2026-09",
  "scope":  "me",
  "income": 68000,
  "expense": 41230,
  "net":     26770,
  "rate":    0.39,
  "count":   4,

  "savings": {
    "goal": 20000, "allowance": 48000, "used": 41230, "left": 6770,
    "ratio": 0.859, "level": "near",
    "shortfall": 0, "actual": 26770,
    "rule": { "warnAt": 0.8, "overAt": 1.0, "note": "..." }
  },

  "byCat":   [ { "cat": "C03", "name": "居住", "color": "#A78BFA", "amount": 18500 } ],
  "monthly": [ { "m": "2026-04", "income": 68000, "expense": 39800 } ],
  "yearly":  [ { "y": "2024", "income": 810000, "expense": 520000 } ],
  "members": [ { "id": "U1", "name": "林建國", "role": "parent", "avatar": "國",
                 "age": 52, "joined": "2026-01-05",
                 "income": 68000, "expense": 41230, "budget": 45000,
                 "savingsGoal": 20000,
                 "allowance": 48000, "savingsRatio": 0.859,
                 "savingsLevel": "near", "shortfall": 0 } ]
}
```

**前端拿去幹嘛**

- `income` / `expense` / `net` / `rate` → 四張 KPI 卡
- `savings.level` → 決定警告卡是綠（`safe`）黃（`near`）紅（`over`）
- `savings.shortfall` → 紅色時顯示「比目標少 NT$ X」
- `byCat` → **圓環圖**（`color` 直接當填色用，前端不查分類表）
- `monthly` → **近 6 個月趨勢圖**
- `yearly` → 年度對照
- `members` → 家庭總覽的逐人清單（`scope=family` 時才需要）

**陷阱**

- **`level` 一定要後端算好**。門檻（80% / 100%）寫在後端，
  前端只認 `safe` / `near` / `over` 三個字串。
  哪天門檻要改成 75%，只改後端一個地方。
- **`allowance` 可能是 0 或負數**（存款目標訂得比收入高）。
  算 `ratio` 時直接除會 `ZeroDivisionError` → 整支 API 500。
  用 `toolkit.money.ratio()` 就不會。
- `scope=family` 時 `members` 要逐人回傳各自的 `savingsLevel`，
  因為**家庭整體達標不代表每個人都達標**。

### `GET /api/transactions` — 收支明細

**前端呼叫**　`API.transactions({ userId, kind, source, q, ... })`
**用在**　我的總覽、記帳頁、**成員紀錄頁（唯讀監管檢視）**

**請求**

| 參數 | 型別 | 說明 |
|---|---|---|
| `userId` | `str` | 只看某個人。**不帶＝看我有權限看的所有人** |
| `from` / `to` | `str` | 日期範圍 `YYYY-MM-DD` |
| `categoryId` | `str` | 只看某個分類 |
| `kind` | `str` | `income` 或 `expense` |
| `source` | `str` | `nlp` 或 `manual` |
| `q` | `str` | 關鍵字，比對店家與備註 |
| `page` | `int` | 第幾頁，從 1 開始 |

**回應**

```json
{
  "transactions": [
    {
      "id": "T1040", "user": "U1", "date": "2026-09-10",
      "amount": 320, "kind": "expense", "cat": "C01",
      "merchant": "公司附近自助餐", "note": "午餐",
      "source": "nlp", "raw": "中午自助餐320",
      "parsed": { "conf": 0.97, "catConf": 0.95 },
      "userName": "林建國", "catName": "餐飲", "catColor": "#FF8A3D"
    }
  ],
  "total": 14
}
```

**前端拿去幹嘛**

- `source === "nlp"` → 顯示「段落記帳」標籤
- `raw` → 有值就顯示「原句『...』」
- `catName` / `catColor` → 左邊的分類圓標
- `userName` → 顯示是誰記的

**陷阱**

- **帶了 `userId` 但沒權限看那個人 → 回 403，不要回空陣列。**
  空陣列會讓使用者以為「對方這個月沒記帳」。
- ⚠️ **不認得的查詢參數要回 422，不要默默忽略。**

  這條是踩過才寫的：前端一直送 `?user=U3`，契約寫的是 `userId`。
  mock 收到不認得的鍵就當作沒有，於是「篩選沒生效」在 mock 下
  看起來完全正常——清單照常出現，只是沒篩而已。
  要等到接上真後端、看到別人的紀錄混進來，才會發現。

  現在 mock 會直接丟錯（「不認得的篩選參數」），後端也請這樣做。
  **默默忽略是最難抓的錯，因為它不會壞給你看。**
- `parsed` 只有 `source === "nlp"` 時才有意義，但**建議一律回**
  （手動的回 `{"conf": 1, "catConf": 1}` 或整個省略都可以，前端有防呆）。

### `POST /api/transactions` — 手動新增一筆

**前端呼叫**　`API.createTransaction({...})`　**用在**　記帳頁的「單筆手動」

**請求主體**

```json
{ "date": "2026-09-10", "amount": 250, "kind": "expense",
  "cat": "C01", "merchant": "全家便利商店", "note": "" }
```

**回應**　新建立的那一筆（形狀同上面明細的單筆），`source` 必須是 `"manual"`

**陷阱**

- ⚠️ **`source` 一定要記 `manual`，不可以記 `nlp`。**
  這支不經過模型。混在一起的話 `nlp_parses` 會被汙染，
  成員4 算模型正確率時分母就錯了。
- `amount` **永遠是正數**，收支方向看 `kind`。

### `DELETE /api/transactions/{id}` — 刪除一筆

**前端呼叫**　`API.deleteTransaction(id)`

**回應**　`{ "deleted": "T1040" }`（或 `204 No Content`，前端兩種都收）

**陷阱**　⚠️ **只有本人可以改、可以刪。監管是唯讀的。**

### `POST /api/nlp/parse-batch` — 段落解析 ★ 系統核心

**前端呼叫**　`API.nlpParseBatch(text)`　**用在**　記帳頁

**請求主體**

```json
{ "text": "早上買早餐55，中午跟同事吃飯320，晚上加油1200，今天打工賺了1500" }
```

**回應**

```json
{
  "raw": "早上買早餐55，中午…",
  "matched": false,
  "items": [
    {
      "seq": 1,
      "span": "早上買早餐55",
      "date": "2026-09-10",
      "amount": 55,
      "kind": "expense",
      "cat": "C08",
      "merchant": "",
      "note": "",
      "conf": { "date": 0.93, "amount": 0.99, "kind": 0.97, "cat": 0.88 },
      "missing": [],
      "hint": ""
    }
  ],
  "note": "這段話被切成 5 筆。切分本身也是模型的判斷…"
}
```

**前端拿去幹嘛**（這支最複雜，看仔細）

| 欄位 | 前端的行為 |
|---|---|
| `items` | 一列一筆，畫成可編輯的表格 |
| `seq` | 表格最左邊的編號 |
| `span` | 顯示成「原句『…』」，讓使用者檢查**切分**對不對 |
| `amount` **可以是 `null`** | 抽不到就傳 `null`，該格顯示紅框「缺」 |
| `missing` | **陣列裡有哪一欄，那一欄就標紅 + 加「必填」** |
| `conf.xxx < 0.85` | 那一格標黃並顯示百分比 |
| `hint` | 顯示在原句下方的小字提示 |
| 有任何一筆 `missing` 非空 | **送出鈕停用**，顯示「還有 N 筆缺欄位，共 M 筆」 |

**陷阱**

- ⚠️ **這支絕對不可以寫進資料庫。** 只解析，使用者確認後才由
  `confirm-batch` 寫入。這是整個設計最重要的一條。
- ⚠️ **抽不到就回 `null` + 放進 `missing`，不要猜一個數字。**
  空白使用者一定會發現；猜錯的數字他可能直接按下確認就送出去了。
- `conf` 是**逐欄**的，不是整筆一個分數。模型常常是「金額很確定、分類不確定」，
  逐欄給，前端才能只把分類那一格標黃。
- `cat` 回傳的必須是**真的存在的分類 ID**。模型自己編一個名稱回來的話，
  前端的下拉選單會找不到，那一格會空白。

### `POST /api/nlp/confirm-batch` — 確認後一次寫入

**前端呼叫**　`API.nlpConfirmBatch(items)`　**用在**　記帳頁按下「確認並寫入 N 筆」

**請求主體**

```json
{ "items": [ { "span": "早上買早餐55", "date": "2026-09-10", "amount": 55,
               "kind": "expense", "cat": "C01", "merchant": "", "note": "" } ] }
```

送出的是**使用者確認或修改過**的值，不是模型原本的值。

**回應**　`{ "created": 5 }`

**陷阱**

- ⚠️ **要嘛全部成功，要嘛全部不寫**（同一個資料庫交易）。
  寫到第 3 筆失敗的話，前面 2 筆已經進去了，使用者看到「寫入失敗」
  但明細裡多了兩筆，**然後他會再按一次，變成重複記帳**。
- ⚠️ **同時要寫 `nlp_parses`**：模型原本解析成什麼、使用者改成什麼。
  這是資料飛輪的入口，漏掉的話第 3 週就沒有訓練資料。

---

### `POST /api/nlp/parse` / `POST /api/nlp/confirm` — 單句版

跟批次版一樣，差別只在一次一筆。回應形狀：

- `parse` → `{ raw, parsed: {...}, confidence: {...}, note, parseId }`
- `confirm` → 新建立的那一筆交易

**前端目前沒有畫面在用這兩支**（段落版已涵蓋），優先序可以降低。

### `GET /api/categories` — 分類體系

**前端呼叫**　`API.categories()`

**回應**

```json
{ "categories": [
  { "id": "C01", "name": "餐飲", "kind": "expense", "color": "#FF8A3D", "icon": "餐" }
] }
```

**陷阱**

- `color` 是**分類自己的顏色**，圓環圖和明細的圓標都吃它。後端一定要回。
- `icon` 是**一個中文字**，不是 emoji 也不是圖片路徑。
- ⚠️ 這支的回傳值**成員2 寫 prompt 要用、成員4 評測要用**。
  是第 1 週唯一要凍結的跨模組契約。

### `GET /api/budgets` — 預算與使用率

**前端呼叫**　`API.budgets()`

**回應**

```json
{ "budgets": [
  { "user": "U3", "period": "month", "cat": "C05", "limit": 3000, "used": 4200,
    "userName": "林宇涵", "catName": "娛樂", "catColor": "#FF4757",
    "over": true, "pct": 1.4 }
] }
```

**陷阱**

- ⚠️ **`period` 這裡是 `"month"` 不是 `"2026-09"`**，跟其他地方的 `period` 意思不一樣。
  這是前端現有的命名歧義，後端照著回就好，但知道一下免得誤會。
- `over` 和 `pct` 都是**後端算好的**，前端只負責畫條。

### `GET /api/advices` — 財務建議

**前端呼叫**　`API.advices({ scope, period })`

**回應**

```json
{
  "advices": [
    { "id": "A1", "scope": "family", "period": "2026-09", "level": "warn",
      "title": "…", "body": "…",
      "basis":   ["餐飲支出 12,400，佔總支出 30%", "比上月增加 2,100"],
      "suggest": ["把餐飲預算調到 10,000"],
      "conf": 0.82,
      "userName": null }
  ],
  "rules": [ { "rule": "金額一律由資料庫計算", "why": "…" } ]
}
```

**陷阱**

- ⚠️ **`basis` 是字串陣列**，不是 JSON 物件。前端直接逐條顯示。
  （資料庫欄位叫 `basis_json`，但回給前端時要轉成**人看得懂的句子陣列**。）
- `userName` 可以是 `null`（家庭層級的建議沒有特定對象）。
- `rules` 是**靜態的邊界規則清單**，每次都回一樣的內容也沒關係。
- `level` 只有三個值：`good` / `info` / `warn`。

### `GET /api/family` — 家庭、成員、監管關係

**前端呼叫**　`API.members()`　**用在**　成員與權限頁

**回應**

```json
{
  "me": "U1",
  "members":  [ { "id": "U1", "name": "林建國", "role": "parent", "avatar": "國",
                  "age": 52, "joined": "2026-01-05",
                  "income": 68000, "expense": 41230, "budget": 45000, "savingsGoal": 20000 } ],
  "roles":    [ { "id": "parent", "name": "家長", "layer": "家庭", "desc": "…" } ],
  "guardianships": [ { "guardian": "U1", "ward": "U3", "since": "2026-02-11",
                       "scope": "完整明細",
                       "guardianName": "林建國", "wardName": "林宇涵" } ],

```

**陷阱**

- ⚠️ `roles` 和 `permissions` 是**靜態說明資料**（角色定義、權限矩陣），
  不是每個家庭都不一樣的東西。**建議寫死在後端常數裡回傳**，不要建表。
- `members[].age` 只是顯示用的個人資料。⚠️ **任何權限判斷都不准讀它**——幾歲該被管是那一家自己的事，而且年齡會變，用它當依據權限就會在某個生日當天自己改變。
  後端資料表存的是 `birth_year`，**回傳時要換算成 age**。
- `guardianships` 要帶 `guardianName` / `wardName`，前端不查表。

### `PUT /api/auth/me/avatar` — 上傳大頭貼

**前端呼叫**　`API.uploadAvatar(dataUri)`　**用在**　個人資料頁

**請求主體**

```json
{ "image": "data:image/jpeg;base64,/9j/4AAQSkZJRgABAQ..." }
```

**回應**

```json
{ "avatarUrl": "data:image/jpeg;base64,/9j/4AAQ...", "avatar": "國" }
```

**前端拿去幹嘛**

- `avatarUrl` 有值 → 顯示圖片
- `avatarUrl` 是 `null` → 退回顯示 `avatar` 那個文字

**這個設計是刻意的**：`avatar`（單一中文字）保留不動，
另外加一個可為 null 的 `avatarUrl`。這樣**前端現有的文字頭像完全不用改**，
只要多一層「有圖就用圖」的判斷。

**陷阱**

- ⚠️ **Render 的磁碟是暫時性的。** 檔案寫進 `/uploads/` 這種地方，
  服務重新部署或重啟之後**就不見了**。免費方案沒有持久磁碟。<br>
  所以大頭貼要**存資料庫**（`users.avatar_blob BYTEA` + `avatar_mime TEXT`）。
  大頭貼縮到 256×256 之後大約 20~50 KB，存資料庫完全沒問題。
- ⚠️ **縮圖在前端做。** 後端縮圖要裝 Pillow，映像檔會大好幾十 MB。
  瀏覽器的 canvas 本來就會縮圖，`canvas.toBlob()` 一行搞定。
- ⚠️ **不可以只看副檔名或 `Content-Type` 判斷是不是圖片。**
  那兩個都是使用者說了算的，可以隨便偽造——
  有人可以把一個腳本改名成 `avatar.jpg` 上傳。<br>
  後端要用 `toolkit.images.validate_avatar()`，它看的是
  **檔案開頭的識別位元組**，那是格式本身的一部分，偽造不了。
- 大小上限 **200 KB**，超過回 422。沒有上限的話有人上傳 500 MB 就能把服務打掛。
- 用 **PUT 不是 POST**：換大頭貼是「把它設定成這張」，
  做幾次結果一樣，所以是冪等的。

**後端大概長這樣**

```python
from app.toolkit import errors, images

@router.put("/me/avatar")
def upload_avatar(payload: AvatarUpload,
                  uid: int = Depends(current_user_id),
                  db: Session = Depends(get_db)):
    try:
        data, mime = images.from_data_uri(payload.image)
    except images.InvalidImage as exc:
        raise errors.unprocessable(str(exc)) from exc

    user = db.get(User, uid)
    user.avatar_blob = data
    user.avatar_mime = mime
    db.commit()
    return {"avatarUrl": images.to_data_uri(data, mime), "avatar": user.avatar}
```

## 監管是唯讀的 ⚠️ 這一節請整組讀過

### 三條界線

| 管理者可以 | 管理者不可以 |
|---|---|
| ✅ 看子女的記帳明細 | ❌ 修改子女的紀錄 |
| ✅ 看子女的統計與超支狀態 | ❌ 刪除子女的紀錄 |
| ✅ 收到子女新增紀錄的通知 | ❌ **登入子女的帳號** |

**第三條最重要，而且不只是安全問題，是產品決定。**

監管的正當性建立在「看得到但碰不到」。如果管理者能登入對方的帳號，
被監管的人就**無法信任自己的紀錄沒有被動過手腳** —— 那整個監管機制的信任基礎就沒了。

所以：

- 前端的「切換身分」鈕**已經拿掉了**，改用真正的登入／登出
- `POST /api/auth/switch`（管理者登入子女帳號）**任何一端都不可以做**
- 管理者要看子女的資料，走 `GET /api/transactions?userId=U3`，**不是換身分**
- ⚠️ **可見範圍只由 `guardianships` 決定，不要用角色判斷。**

  ```sql
  -- 我看得到誰：自己 + 我監管的人
  SELECT :me AS user_id
  UNION
  SELECT ward_id FROM guardianships
   WHERE guardian_id = :me AND ended_at IS NULL;
  ```

  **家長沒有例外。** 是家長不等於看得到每個人的消費明細——
  前者是「管得動」，後者是「看得到」，是兩件事。
  沒有被指派監管誰的 master，就只看得到自己。

  這樣做的理由是：「誰看得到我」必須是一份**可以查、可以列出來**的清單。
  一旦寫成 `if role == 'master': return everyone`，被監管的人就無法確認
  自己的紀錄到底被誰看過。

  ⚠️ **監管是單向的。** 你看得到我，不代表我看得到你。
  被監管的人看不到任何別人，包含監管他的人。
- ⚠️ **看不到那個人，連他的存款目標也不要送。**
  名字、角色、監管關係是公開的（被監管的人必須知道自己被誰看著），
  但收入、支出、預算、存款目標是個人財務資料，
  **不在可見範圍內就不要放進回應裡**。前端把欄位藏起來不算保護。
- 前端的路徑是 `#/member/U3`（成員與權限點某一列進去），
  從通知點進來會變成 `#/member/U3/T1051`——**那一筆會用藍框標起來**，
  不然使用者還要自己在一長串紀錄裡找是哪一筆。
  這個畫面上**每一列都沒有刪除鈕**，只有「唯讀」標記。

### 後端要怎麼擋

```python
# services/permission.py
def can_view(db, me_id, target_id, family_id) -> bool:
    """能不能看。監管者對被監管者是 True。"""

def can_edit(db, me_id, owner_id) -> bool:
    """能不能改。**只有本人**。監管者是 False。"""
    return me_id == owner_id

def can_delete(db, me_id, owner_id) -> bool:
    """能不能刪。**只有本人**。"""
    return me_id == owner_id
```

⚠️ `can_view` 和 `can_edit` **不是同一件事**，不要共用一個函式。
這是很容易偷懶的地方，偷懶的後果是監管者可以改小孩的帳。

## 即時通知

### 為什麼用輪詢，不用 SSE 或 WebSocket

看起來 SSE 更「即時」，但它有一個硬傷：

> **`EventSource` 沒辦法送自訂標頭。**
> 你不能帶 `Authorization: Bearer <token>`，只能把 token 放在網址上。

而網址會進**瀏覽器歷史、伺服器日誌、Referer 標頭、代理伺服器**。
為了 SSE 破壞「token 絕不放查詢參數」這條規則，不划算。

WebSocket 可以帶標頭，但要另外處理連線管理、斷線重連、
多個 worker 之間的廣播 —— **對一個六週的專題來說太重了**。

**輪詢 20 秒**對「子女記了一筆帳」這種通知完全夠用。而且：

- 斷線重連是免費的（下一次輪詢自然就接上了）
- 過代理伺服器不會有問題
- Render 免費方案的服務休眠不會讓它壞掉

### `GET /api/notifications` — 通知清單

**前端呼叫**　`API.notifications({ since })`　**用在**　右上角的通知鈴鐺

**請求**

| 參數 | 型別 | 說明 |
|---|---|---|
| `since` | `str` | 上次拿到的最大 id。**只回比它新的**，第一次不帶 |
| `unreadOnly` | `bool` | 只要未讀的 |

**回應**

```json
{
  "notifications": [
    {
      "id": "N12",
      "type": "ward_transaction",
      "actorId": "U3", "actorName": "林宇涵",
      "txId": "T1051",
      "amount": 320, "cat": "C01", "catName": "餐飲", "merchant": "全家",
      "createdAt": "2026-09-11T13:20:05Z",
      "readAt": null
    }
  ],
  "unread": 3,
  "maxId": "N12"
}
```

**前端拿去幹嘛**

- `unread` → 鈴鐺上的紅點數字
- 有新的（`maxId` 變了）→ **播提示音 + 跳出通知**
- `actorName`、`amount`、`catName`、`merchant` → 組成通知文字：
  「林宇涵剛記了一筆 餐飲 NT$ 320（全家）」
- `txId` → 點通知跳到那一筆
- `maxId` → 存起來，下次當 `since` 傳回去

**陷阱**

- ⚠️ **一定要用 `since` 分頁，不要每次都回全部。**
  通知會一直累積，三個月後一次回三千筆，手機會當掉。
- ⚠️ **`unread` 是「總未讀數」，不是「這次回傳那幾筆裡的未讀數」。**

  這個很容易寫錯：如果用分頁後的結果去算，第二次輪詢帶了 `since`、
  沒有新通知、回傳空陣列，`unread` 就變成 0，**紅點會被清掉**，
  使用者以為自己看過了。

  ```sql
  -- ✅ 對：不受 since 影響
  SELECT COUNT(*) FROM notifications
   WHERE recipient_id = :me AND read_at IS NULL;
  ```

  （這個 bug 我在實作 mock 時真的踩到了，所以特別寫出來。）
- ⚠️ **只回「我該收到的」通知。** 通知是寫給特定收件人的，
  查詢時要 `WHERE recipient_id = 我`，不是用監管關係現算——
  監管關係解除之後，舊的通知還是屬於當時的收件人。
- `createdAt` 用 **ISO 8601 + UTC**（結尾 `Z`），前端自己轉本地時間。
  回「3 分鐘前」這種字串的話，前端就沒辦法排序或重新計算了。
- ⚠️ **`notifications` 由新到舊排（最新的在 `[0]`），但 `maxId` 要給「整體最新」的那一個。**

  這兩件事很容易打架。清單是新→舊，所以「最後一筆」是**最舊的**——
  如果順手寫成 `maxId = rows[-1].id`，下次帶著這個 `since` 回來，
  比它新的全部都會被算成「已經給過了」，**新通知永遠進不了清單**，
  但 `unread` 又是用全部算的，於是紅點跳動、清單卻不動。

  ```sql
  -- 查詢：只拿比 since 新的，由新到舊
  SELECT * FROM notifications
   WHERE recipient_id = :me
     AND (:since IS NULL OR id > :since)
   ORDER BY id DESC
   LIMIT 20;

  -- maxId 另外查，不要從上面那批取
  SELECT MAX(id) FROM notifications WHERE recipient_id = :me;
  ```

  （這個我也踩到了。前端 `state.items = 新的.concat(舊的)` 靠的就是新→舊這個順序。）
- ⚠️ **`since` 是嚴格大於（`>`），不是大於等於。**
  寫成 `>=` 的話，每次輪詢都會把同一筆重送一遍，於是每 20 秒叮一聲、
  清單裡出現重複的同一筆。

### 前端的音效怎麼做

⚠️ **不要放 mp3 檔案。** 用 Web Audio API 直接合成一個短音：

```js
const ctx = new AudioContext();
const osc = ctx.createOscillator();
const gain = ctx.createGain();
osc.frequency.value = 880;
gain.gain.setValueAtTime(0.15, ctx.currentTime);
gain.gain.exponentialRampToValueAtTime(0.001, ctx.currentTime + 0.3);
osc.connect(gain); gain.connect(ctx.destination);
osc.start(); osc.stop(ctx.currentTime + 0.3);
```

好處：**不用託管音檔、不用等下載、離線也能響**。

⚠️ **瀏覽器會擋自動播放。** 使用者第一次跟頁面互動（點任何東西）之前，
`AudioContext` 會是 `suspended` 狀態。所以要在第一次點擊時 `ctx.resume()`。

⚠️ **一定要有靜音開關**，存在 `localStorage`。
半夜跳出聲音會讓人直接關掉整個系統。

## 認證怎麼串（前端已經做好了）

前端有登入頁（`#/login`）、註冊頁（`#/register`）、個人資料頁（`#/profile`），
`req()` 會自動帶 `Authorization: Bearer`，收到 401 會自動續期並把請求重送一次。
**後端只要把下面四支做出來、形狀對得上，前端一行都不用改。**

```
1. 登入頁送 POST /api/auth/login  { email, password }
2. 後端回 { accessToken, refreshToken, expiresIn, user }
3. 前端存進 localStorage['fambudget.auth']，
   之後每個請求帶 Authorization: Bearer <accessToken>
4. 收到 401 → 自動打 POST /api/auth/refresh { refreshToken }
   → 拿到新的 accessToken → 把剛才失敗的請求重送一次
5. 登出 → POST /api/auth/logout，前端清掉 token
```

---

### `POST /api/auth/register` — 註冊

**前端呼叫**　`API.register({ name, email, password, savingsGoal })`

**回應**　同 `login`（註冊完直接登入，不用再叫使用者登一次）

**陷阱**

- ⚠️ **email 要存成小寫**，比對時也要小寫。
  `Ming@lin.tw` 跟 `ming@lin.tw` 是同一個人，讓他註冊兩次之後誰都登不進去。
- ⚠️ **「這個 email 已經註冊過了」要回 409，不是 422。**
  409 Conflict 的語意就是「跟現有資源衝突」。
- 密碼規則用 `toolkit.passwords.check_strength()`，不要自己寫一套。

### `POST /api/auth/login` — 登入

**前端呼叫**　`API.login({ email, password })`

**回應**

```json
{
  "accessToken": "eyJhbGciOiJIUzI1NiJ9...",
  "refreshToken": "eyJhbGciOiJIUzI1NiJ9...",
  "expiresIn": 1800,
  "user": { "id": "U1", "name": "林建國", "email": "jianguo@lin.tw",
            "role": "parent", "avatar": "國", "avatarUrl": null }
}
```

**陷阱**

- ⚠️ **「帳號不存在」跟「密碼錯」要回同一句話、同一個狀態碼（401）。**
  分開講等於送給攻擊者一支帳號列舉工具：他不用猜密碼，
  先用錯誤訊息把「哪些 email 有註冊」撈出來，再針對這些人下手。
  <br>（前端的 mock 故意分開講，那是為了 demo 時看得懂自己打錯什麼。**後端不要學。**）
- ⚠️ **查無此人的時候也要跑一次密碼雜湊比對。**
  不跑的話「不存在」會比「密碼錯」快很多，用回應時間一樣問得出來。
- `expiresIn` 用**秒**，跟 OAuth 2.0 一致。

---

### `POST /api/auth/refresh` — 換新的 access token

**前端呼叫**　`req()` 自動打，畫面程式碼不會直接叫它

**請求主體**　`{ "refreshToken": "..." }`
**回應**　`{ "accessToken": "...", "refreshToken": "...", "expiresIn": 1800 }`

**陷阱**

- ⚠️ **refresh token 要輪替**：換發新的，同時把舊的撤銷（`sessions` 那一列標記失效）。
  不輪替的話，一條外洩的 refresh token 可以用滿 14 天。
- ⚠️ **前端同時只會打一次 `/refresh`。**
  一次載入會同時發好幾個請求，過期時它們會一起收到 401；
  前端用一個「續期中」的旗標擋住，只有第一個會真的去換，其他的等它。
  後端也要能承受重送（同一個 refresh token 連打兩次）——
  **回 401 就好，不要把使用者的所有 session 都撤銷**，
  那會變成「網路抖一下就被登出所有裝置」。
- ⚠️ **這支不要驗 access token**，它的存在意義就是 access token 已經死了。

---

### `POST /api/auth/logout` — 登出

**請求主體**　`{ "refreshToken": "..." }`
**回應**　`204 No Content`

**陷阱**

- ⚠️ **後端失敗了，前端還是會把本機的 token 清掉。**
  使用者按了登出就一定要登出，不能因為伺服器沒回應就把他留在登入狀態。
  所以這支要做成**冪等**的：重複登出、token 已經失效，都回 204，不要噴 400。
- access token 是無狀態的，撤不掉——它會自己在 30 分鐘內過期。
  真正被撤銷的是 refresh token。要立刻全面失效的話用 `/api/auth/logout-all`。

---

### 前端這邊的三個地雷（寫給接手的人）

- ⚠️ **換人一定要清掉畫面上的殘留。**
  登入／登出是在同一頁切的（單頁應用，不會整頁重載）。
  通知清單、快取的 `ME`、開著的面板如果不清，
  **會把上一個使用者的記帳明細顯示給下一個人看**。
  `Notify.reset()` 就是為了這個而存在的。
- ⚠️ **沒登入不要輪詢通知。** 會一路 401，還會在登入頁叮一聲。
- ⚠️ **大頭貼縮圖在前端做**（`shrink()`，canvas 裁成正方形縮到 256×256，
  轉 JPEG，超過 200 KB 就降畫質重來）。
  實測 1600×900 的 PNG 原圖 1030 KB → 存進去 4 KB。

## 群組（帳本）

一個家庭可以開好幾本帳：家用、旅遊基金、宇涵的零用。
**每一筆記帳都屬於其中一本**，而且每一本可以各自設一個每月存款目標。

分類回答「錢花在什麼」，群組回答「這筆算在哪一份預算上」——兩個是不同的軸。

### 可見範圍是兩條路的聯集

```sql
-- 過一條就看得到。⚠️ 是 OR，不是 AND
SELECT * FROM transactions t
 WHERE t.user_id IN (                    -- A：我或我監管的人記的
         SELECT :me
         UNION SELECT ward_id FROM guardianships
          WHERE guardian_id = :me AND ended_at IS NULL)
    OR t.group_id IN (                   -- B：記在我有加入的帳本裡
         SELECT group_id FROM group_members WHERE user_id = :me)
```

兩條各自回答一個不同的問題：

- **A 是監管。** 家長對子女的可見度不該被帳本切斷——否則子女只要另外開一本
  不加家長的帳，記在那裡就完全躲掉了。他甚至不用離開任何群組，
  所以「離開群組要核准」也堵不住這個洞。
- **B 是分享。** 把誰加進帳本，就是選擇讓他看到那本帳，這是記帳的人
  自己的行為。共用帳本只分享那一本，不是分享整個人。

⚠️ **寫成 `AND` 就變回交集了**，那是早期版本的錯：它讓監管一鍵可繞，
同時又讓「把人加進帳本」什麼也不代表。

⚠️ **算某個人的統計時只走 A。** 加上 B 會把共用帳本裡別人的錢
算進這個人的總額——家用帳本裡配偶花的錢，不該出現在我的支出裡。

工具箱有寫好的：`toolkit.scope.visible_users()` / `visible_groups()` / `filter_rows()`。

---

### `GET /api/groups` — 我加入的群組

**前端呼叫**　`API.groups()`／`API.groups({ includeArchived: true })`
**用在**　右上角的切換器、群組管理頁

| 參數 | 型別 | 說明 |
|---|---|---|
| `includeArchived` | `bool` | 連封存的一起回。預設 `false` |

**回應**

```json
{
  "me": "U1",
  "groups": [
    { "id": "G1", "name": "家用", "icon": "家", "color": "#6C9FFB",
      "owner": "U1", "note": "日常開銷，全家共用",
      "members": ["U1", "U2", "U3", "U4"],
      "memberNames": ["林建國", "陳淑芬", "林宇涵", "林宇軒"],
      "count": 7, "goal": 0, "canEdit": true }
  ]
}
```

**陷阱**

- ⚠️ **只回我加入的。** 別人的帳本<b>連名字都不該看到</b>。
- ⚠️ **`count` 要算「我實際看得到的筆數」，用跟明細同一條規則。**

  這個我踩到了：一開始 count 和明細用了不一樣的條件，
  切換器上寫「家用 10 筆」，點進去卻只有 7 筆。
  數字和清單只要不是同一段條件算出來的，遲早會對不起來。
  **面板上的數字和點進去看到的必須一致**，否則使用者會以為系統壞了。
- `canEdit` 是「我是不是建立者」。改名、加人、封存都只有建立者能做。

---

### `POST /api/groups` — 建立

**請求主體**　`{ "name": "旅遊基金", "color": "#8B7CF0", "note": "" }`
**回應**　建立好的群組

**權限：只要登入就可以建，不看角色。**
`member` 也能開自己的帳本，而且他是那本帳的建立者（可以改名、加人、封存）。
這是刻意的——**記帳的分類方式是個人的事，不該由家裡的階級決定**。
家裡的階級管的是「誰看得到誰的錢」，不是「你能不能替自己的開銷分類」。

**陷阱**

- ⚠️ **建立者要自動寫一筆 `group_members`。**
  漏了的話他自己也看不到剛建的帳本——`GET /api/groups` 是用 group_members 查的。
- 同一個家庭裡名字不要重複，重複回 **409**。

---

### `PATCH /api/groups/{gid}` — 改名稱／圖示／顏色，或**復原封存**
### `DELETE /api/groups/{gid}` — 封存

**請求主體**（PATCH）　`{ "name": "…" }`／`{ "color": "…" }`／`{ "archived": false }`
**回應**　PATCH 回更新後的群組；DELETE 回 `204 No Content`

**陷阱**

- ⚠️ **封存是設 `archived_at`，不是真的刪。**
  裡面的記帳紀錄還在，真刪了那些紀錄的 `group_id` 會變成孤兒。
- ⚠️ **封存在使用者眼裡跟刪除長得一模一樣**——那本帳從切換器、統計、
  清單裡通通消失了。所以這三件事缺一不可：

  1. `GET /api/groups?includeArchived=true` 要**看得到已封存的**
  2. `PATCH` 帶 `{"archived": false}` 要能**復原**
  3. 按下封存之前要**再確認一次**

  這是踩過才補的：我先做了封存、也在文件裡寫了「不是刪除」，
  但沒做出「看已封存的」和「復原」的畫面——
  **對使用者來說，一個救不回來的東西就是被刪掉了**，
  文件上怎麼定義不重要。
- 復原不需要還原任何資料。封存從頭到尾沒有動過任何一筆記帳，
  它只是讓那本帳重新出現在清單上。

---

### `POST /api/groups/{gid}/members` — 加人
### `DELETE /api/groups/{gid}/members/{user_id}` — 移出

**請求主體**（加人）　`{ "userId": "U2" }`

**陷阱**

- 只能加**同一個家庭**裡的人。
- ⚠️ **建立者不能把自己移出去**，否則這本帳沒人管得動。
- ⚠️ **移出之後他看不到這本帳的任何紀錄，包含他自己記的那些。**
  紀錄屬於帳本，不屬於人。這一點要在介面上講清楚，
  不然使用者會以為自己的資料被刪了。

## 階段性提醒

使用者自己設幾個百分比門檻（例如 60%／85%／100%）。
支出佔**可支配上限**的比例跨過門檻，就發一則通知——走的是同一套通知鈴鐺。

```
可支配上限 = 本月收入 − 每月存款目標
```

所以百分比算的是「花掉可支配額度的幾成」，不是「花掉收入的幾成」。

### 判斷該不該發，比想像中容易寫錯

工具箱有寫好的 `toolkit.alerts`，直接用：

```python
from app.toolkit import alerts

before = alerts.usage_percent(spent_before, allowance)   # 78
after  = alerts.usage_percent(spent_after,  allowance)   # 103

for rule in rules:
    if not alerts.should_fire(rule.percent, before, after,
                              rule.fired_period, period_key):
        continue
    建立通知(rule)                    # ← 成員4 的 notifications
    rule.fired_period = period_key   # 記住這個月響過了
```

**寫成 `if percent >= threshold` 會有三個 bug：**

- ⚠️ **每記一筆都會重發。** 已經 90% 了，再記一筆變 92%，
  `92 >= 85` 還是成立，於是又響一次。
  要比的是「這次之前」和「這次之後」，跨過的當下才算。
- ⚠️ **一次跨過好幾個門檻只響一次。** 80% 的時候記一筆大的直接跳到 105%，
  85 和 100 兩個都該通知。
- ⚠️ **下個月要重新開始。** 用 `fired_period`（`'2026-09'`）記住上次哪個月響的。

另外 `usage_percent` 是**捨去**不是四捨五入：79.9% 還沒到 80%，不該提前響。

- `percent` 限 **1~200 的整數**。0 沒有意義（一開始就成立），

### `DELETE /api/alerts/{aid}` — 刪掉

  關掉保留設定，下個月想開回來直接開。

### 提醒型通知長什麼樣

`GET /api/notifications` 現在會回兩種 `type`：

```json
{
  "id": "N31", "type": "budget_alert",
  "actorId": null, "actorName": null,
  "percent": 85, "reached": 103,
  "groupId": "G2", "groupName": "旅遊基金",
  "spent": 12800, "allowance": 5000,
  "createdAt": "2026-09-12T10:04:00Z", "readAt": null
}
```

**陷阱**

- ⚠️ **前端要用 `type` 判斷，不要靠「有沒有 actorName」去猜。**
  猜的那套在多一種通知的時候就會壞。
- ⚠️ **`percent` 是「你設的門檻」，`reached` 是「實際用掉幾成」，兩個都要送。**
  我一開始只送 `percent`，畫面上寫「已用掉 90%（NT$ 12,800 / NT$ 5,000）」——
  但 12,800 是 5,000 的 256%，讀起來像系統算錯了。
