# 漏洞情資影響面判定與修補優先序系統 — 前端原型

四人一個月專題（Top 10 第 5 題）的第一版前端。
**目前沒有後端**：所有畫面用模擬資料驅動，目的是先把「做完會長什麼樣」定下來，
讓四個人有共同的靶，也讓資料結構在寫後端之前就先被檢查一遍。

---

## 這個系統要解決什麼

漏洞公告每天湧入，內容是**英文散文**；公司的資產清單是**表格**。
中間那道「這條公告跟我有沒有關、影響幾台、要先修哪一台」的比對，目前全靠人腦。
中小企業與校園網管沒有人力逐日做這件事。

系統把公告抽成結構化欄位，與資產清單逐項比對，直接輸出
**「你有幾台受影響、先修哪一台」**。

### 為什麼不是照 CVSS 排序就好

原型的預設資料裡，本批 12 條情資中分數最高的是 `CVE-2026-10611`（CVSS **10.0**），
但它影響的是 MISP，而示範組織沒有這項產品 —— **判定為無關**。
真正排第一的是 `CVE-2026-10931`（CVSS 9.6），因為它同時**對外暴露**且**影響 34 台**。

照 CVSS 排序，第一件事會是去處理一條跟自己無關的公告。
這就是「影響面判定」必須做在「優先序」前面的原因，也是這個系統存在的理由。

## 五個畫面

| 畫面 | 回答什麼問題 | 可以做什麼 |
|------|-------------|-----------|
| **01 總覽** | 這批情資有幾條跟我有關？現在最該做哪一件事？ | 看趨勢圖、嚴重度分佈、SLA 進度環 |
| **02 修補優先序** | 待辦怎麼排的？每一筆的優先度是怎麼算的？ | 依狀態／嚴重度篩選、三種排序、單筆或批次標記「已修補／延後／不適用」、**可復原** |
| **03 漏洞情資** | 哪些命中、哪些無關？原文抽成了什麼欄位？ | 篩選命中／無關、點開看原文與抽取欄位的左右對照 |
| **04 資產清單** | 我登記了哪些？哪幾項寫得不夠清楚？ | 新增／編輯／刪除資產（側滑表單） |
| **05 查詢軌跡** | 模型呼叫了哪些工具、花掉多少額度？ | 逐步檢視工具呼叫與快取命中 |

畫面上的搜尋框、載入骨架、空狀態、錯誤狀態、操作提示（含復原）都是實作好的，
不是靜態圖。狀態改動會存進 `localStorage`，重新整理不會消失；工具列的
「重置示範資料」可以還原。

### 優先度公式

```
優先度 = CVSS ÷ 10 × 暴露係數 × 資產數係數 × 修補可得係數 × 100
```

| 因子 | 取值 |
|------|------|
| 暴露係數 | 對外 1.0、內網 0.6 |
| 資產數係數 | 1 台 1.0、2–5 台 1.15、6–20 台 1.3、20 台以上 1.45 |
| 修補可得係數 | 官方已釋出修補 1.0、只有緩解措施 0.8 |

公式刻意做成**看得見、可以吵**的。每個組織對「對外」的定義不一樣，
係數本來就該讓使用者自己調，而不是藏在後端。
每一張待辦卡上都直接列出四個因子與相乘結果。

## 資料

### CVE 內容是真的

`js/data.js` 裡的 12 條 CVE — 編號、發布日期、CVSS 分數與向量、英文描述、CPE 比對條件、
參考連結 — 全部取自 **NVD CVE API 2.0** 的真實回應。
資產清單、抽取欄位的信心度、判定結果、查詢軌跡則是模擬的。

用真資料的理由：CPE 的實際長相（`cpe:2.3:a:google:chrome:*` 加上
`versionEndExcluding` 這類版本區間）決定了比對邏輯怎麼寫。
拿假資料設計，接後端時整套要重來。

> This product uses data from the NVD API but is not endorsed or certified by the NVD.
>
> （這是 NVD 使用條款要求必須在應用程式中顯著顯示的聲明，已放在頁尾與每個畫面底部。）

### 介接限制決定了架構

| | 每 30 秒滾動視窗 |
|---|---|
| 無金鑰 | **5 次** |
| 有金鑰 | **50 次** |

金鑰免費申請，一個信箱一把，啟用連結七天內有效。
**第一週就該去申請**，額度直接十倍。

NVD 官方建議的作法與本系統一致：先用 `startIndex` 分頁做初次全量落地，
之後用 `lastModified` 做增量更新，自動化同步不超過每兩小時一次。

因此設計上有三道防線，在「05 查詢軌跡」畫面可以看到實際效果：

1. **本地快取優先** — 查過的產品直接讀本地
2. **同一項產品 24 小時內只查一次**
3. **名稱不夠明確的資產先追問，不要先查** — 原型資料裡「防火牆」「公司網站主機」
   兩項就是這樣被擋下來的，省下兩次呼叫

### 為什麼不自動掃描網路

自動掃描要拿到對方網路的存取權限，那是導入時最難跨過的一道門。
改成**使用者自建清單**，中小企業或校園網管自己就能開始用，不必先說服任何人開權限。
代價是清單要人維護 —— 所以系統必須明講哪幾項寫得不夠清楚，而不是默默亂猜。

## Function Calling 的四支工具

這一題的 FC 判定是**必要**，不是加分。理由：要查哪些漏洞完全取決於這家公司的資產清單，
事前無法窮舉；而漏洞資料每日新增、修補狀態會變動，整批同步必然滯後。

| 工具 | 做什麼 |
|------|--------|
| `list_assets` | 讀出資產清單 |
| `check_clarity` | 判斷產品名稱夠不夠明確、能不能組出 CPE。**不夠明確就追問，不消耗查詢額度** |
| `search_cve` | 用 CPE 查對應漏洞，先讀快取再打線上 |
| `rank_actions` | 依四項因子排出待辦順序 |

## 後端接口已經預留好了

前端**不直接讀資料檔**，一律透過 `js/api.js` 這一層。要接真後端，
只要改 `index.html` 裡這一行：

```html
<meta name="api-base" content="http://localhost:8000">
```

留空就是 mock 模式（讀 `js/data.js`、寫 `localStorage`、附帶假的網路延遲，
所以載入狀態是真的看得到的）。填上網址就切成 `fetch` 打真後端，
**畫面程式碼一行都不用改**。

`js/api.js` 最上面列出完整的路由契約，後端照著做即可：

| 方法 | 路由 | 用途 |
|------|------|------|
| GET | `/api/summary` | 總覽數字 + 本週統計 + 近 14 天趨勢 |
| GET | `/api/queue` | 修補待辦（可帶 `status` / `sev` / `sort` / `q`） |
| PATCH | `/api/queue/{cve}` | 更新單筆 `{ status?, owner? }` |
| POST | `/api/queue/bulk` | 批次更新 `{ cves: [], patch: {} }` |
| GET | `/api/advisories` | 情資清單（可帶 `matched` / `sev` / `q`） |
| GET | `/api/advisories/{cve}` | 單筆情資（含抽取欄位與 CPE 比對） |
| GET | `/api/assets` | 資產清單 |
| POST | `/api/assets` | 新增資產 |
| PATCH | `/api/assets/{id}` | 修改資產 |
| DELETE | `/api/assets/{id}` | 刪除資產 |
| GET | `/api/trace` | 最近一次工具呼叫軌跡 |
| GET | `/api/quota` | 介接額度 |
| POST | `/api/sync` | 觸發一次 NVD 同步 |

每個方法都回傳 Promise，`mockAdapter` 與 `httpAdapter` 的簽章完全一致，
所以可以一支一支路由慢慢接 —— 後端做好哪一支就改哪一支，不必等全部完成。

## 資料結構即 API 契約草案

`js/data.js` 的欄位結構就是之後後端要回傳的形狀，先在前端定死再去實作：

```
meta       { org, synced, quota{used,limit,window}, source }
assets[]   { id, name, vendor, product, version, cpe, count,
             exposure:'對外'|'內網', owner, tag, clarity:'ok'|'vague', hint? }
advisories[] { id, published, modified, status, score, sev, vector, desc,
               cpe[]{c,lt,le,ge}, refs[], matched:assetId,
               extracted{ product, vendor, affected, fixed, av, priv, ui,
                          patch, work, conf{欄位:0..1} } }
unmatched[]  { id, published, score, sev, product, desc, matched:null }
queue[]      { rank, cve, asset, priority, f{cvss,expo,cnt,patch}, action }
trace[]      { s, tool, args, res, ms, cache, quota }
```

`extracted.conf` 是每個抽取欄位的信心度，畫面上以進度條呈現，低於 80% 會轉成警示色 ——
這是為了讓人一眼看出**哪些欄位不該直接相信**。

## 建置階段的規格文件

| 文件 | 給誰 | 狀態 |
|------|------|------|
| [`docs/01-field-spec-draft.md`](docs/01-field-spec-draft.md) | 囷洧 | **草稿**，等他接手定稿 |
| [`docs/02-references.md`](docs/02-references.md) | 全組 | 參考網站與既有產品，已查證 |
| [`docs/03-target-user-and-sources.md`](docs/03-target-user-and-sources.md) | 全組 | 應用對象輪廓與資料來源總表，已查證 |

第一份是「欄位定義書」的起頭草稿：從 300 則真實 NVD 公告統計出版本寫法有哪八類、
各佔多少、對應到什麼結構，並附上每一類的真實例句。
還包含一個實測數字——**只是多容許幾個逗號，正則的涵蓋率就從 32% 跳到 56%**，
這是「這題必須用語言模型而不是規則」最直接的證據。

第二份整理了這個主題有哪些網站可以參考，重點是兩個免費免金鑰的資料源
（**EPSS** 被實際利用的機率、**CISA KEV** 已知正在被攻擊的清單），
以及最接近的既有產品 **OWASP Dependency-Track** —— 它跟這題高度重疊，
報告裡必須主動說清楚差異在哪。

第三份回答兩個問題：**這套系統的對象是誰**（用三種組織的實測命中數說明，
最適合的是「有網路設備但只有一名 IT」的校園／機關網管），
以及**資料來源有哪些**（八個來源的總表，含網址、金鑰需求、限流、實測狀態）。

## 部署

原型發布在報告站台底下：<https://llm-capstone-top20.onrender.com/proto/>
報告站台第 5 題的卡片點下去就會到這裡。

`site/proto/` 是這個目錄的副本，為了讓靜態站台能直接發布而一起提交
（Render 上的服務是手動建立的，`render.yaml` 的建置指令不會生效）。
**這個目錄才是原始碼**，改完之後同步一次：

```bash
rm -rf site/proto && cp -r working_space site/proto
```

## 本機執行

```bash
python -m http.server 5174 --directory working_space
```

開啟 <http://localhost:5174>。純靜態，無框架、無外部相依、無建置步驟。

## 目錄

```
working_space/
  index.html       應用外框（含 <meta name="api-base"> 後端接口）
  css/tokens.css   設計權杖：分層表面、風險色、動態
  css/app.css      元件與五個畫面
  js/data.js       模擬資料集（CVE 內容為 NVD 真實資料）
  js/api.js        ★ 唯一的資料入口。mock / http 兩個轉接器
  js/app.js        路由、五個畫面、側滑面板、互動
```

**改資料流時只動 `js/api.js`，改畫面時只動 `js/app.js`，兩邊不會互相牽扯。**

## 重新產生資料集

`js/data.js` 由腳本從 NVD 的實際回應組出。要換一批 CVE 時，
重新呼叫 NVD API 取得原始 JSON，再依上面的資料結構重組即可。
注意無金鑰的限流是每 30 秒 5 次，抓取時要自行間隔。
