# 第一部分：應用對象

## 1-1　用真實資料算出來的：誰會收到最多

方法：取 NVD 上 2026 年 7–8 月公開的 **300 則公告**（約 8 週），
用三種典型組織的資產清單去比對，看各自命中幾則。

| 組織類型 | 資產內容 | 命中 | 平均 | 最忙一天 |
|---|---|---|---|---|
| **A 純辦公室** | Windows、Edge、Chrome、NAS | 8 則 | 1.0 則/週 | 6 則 |
| **B 校園／機關網管** ★ | 防火牆、AP、Linux 伺服器、網站、端點 | **15 則** | **1.9 則/週** | **10 則** |
| **C 小型軟體團隊** | Linux、Docker、PostgreSQL、nginx、OpenSSL | 10 則 | 1.2 則/週 | 5 則 |

**★ B 是最適合的對象。**

### 為什麼是 B：NVD 的資料本身就偏向網路設備

同一批 300 則裡，帶 CPE 標記的公告依廠商分佈：

| 廠商 | 出現次數 | 佔比 |
|---|---|---|
| WatchGuard | 391 | 39% |
| Qualcomm | 354 | 35% |
| Ubiquiti | 165 | 16% |
| Microsoft | 10 | 1% |
| 其他（radare、FreeRDP、MediaWiki…） | 少量 | 9% |
| **前三名合計** | | **90%** |

**九成集中在網路設備與晶片廠商。** 你有防火牆、AP、Linux 伺服器就會持續收到；
純辦公室環境命中很少，而且那些多半 Windows Update 自己就處理掉了。

## 1-2　適合的對象

| 條件 | 說明 |
|---|---|
| **有網路設備與伺服器** | 防火牆、AP、交換器、Linux／Windows Server —— 這是命中的主要來源 |
| **一人身兼所有 IT 工作** | 沒有專職資安人員，沒有人能每天讀 38 則英文公告 |
| **沒有 SBOM、沒有 CI/CD** | 有的話應該用 OWASP Dependency-Track，那是為建置流程設計的 |
| **沒有採購預算** | 有預算的組織已經買了 Tenable／Qualys／Rapid7 |
| **需要留下稽核紀錄** | 資安法、ISO 27001 要證明「有在管漏洞」，但沒有工具產生紀錄 |

**具體是誰**：

- 學校的網管老師或資訊組
- 公家機關的資訊人員
- 中小企業唯一的 IT
- 幫客戶維運設備的系統整合商（一個人顧十幾家客戶）

## 1-4　實際使用情境

### 「1.9 則/週」這個數字會誤導人

看起來少到不值得做一套系統。**真正的成本不在處理，在篩選：**

| | 數量 |
|---|---|
| 每週進來的公告 | **約 38 則** |
| 其中跟你有關的 | **約 2 則** |
| 為了找出那 2 則，要掃過的 | **38 則（全部）** |

**90% 的日子答案是「今天沒事」，但你必須讀完 38 則才敢這樣說。**

→ 這個系統省的不是「修補的時間」，是**「確認自己沒事的時間」**。
這句話比「幫你排優先序」精準得多，建議直接寫進報告。

### 負載是批次的，不是平均的

校園網管那組的 15 則命中裡，**10 則是同一天來的**（2026-07-03，WatchGuard 一次釋出一整批）。

```
2026-07-01  #####          5 則
2026-07-03  ##########    10 則   ← 最忙的一天佔全部的 50%
2026-07-06  ##             2 則
2026-07-07  #              1 則
2026-07-08  ##             2 則
```

前兩天合計佔 75%。**平常沒事、突然一天砸 10 則進來 —— 那一天就是這個工具值回票價的時刻。**

### 三種使用時機

| 時機 | 頻率 | 做什麼 |
|---|---|---|
| **每日確認** | 每天 2 分鐘 | 打開總覽看「今天有沒有」。九成的日子是沒有 |
| **批次處理** | 每週 1–2 次 | 有東西時看優先序、看影響幾台、決定排程 |
| **突發查詢** | 不定期 | 新聞出現重大漏洞，主管問「我們有沒有事」→ 搜尋資產清單，30 秒回答 |
| **稽核／報告** | 每季或年度 | 拿出「修補了幾件、平均幾天、SLA 達成率」的紀錄 |

第三項是最有感的場景：今天要回答「我們有沒有事」得花幾小時人工確認。

---

## 1-5　系統刻意不做的事

| 不做 | 原因 |
|---|---|
| **不掃描網路** | 掃描要拿到對方網路的存取權限，那是導入時最難跨過的門 |
| **不自動修補** | 只告訴你該修什麼，動手的還是人 |
| **不偵測攻擊** | 這不是 IDS／SOC，它只回答「這條公告跟我有沒有關」 |
| **不由模型生成版本號** | 版本號必須來自公告原文，猜錯會讓人升級到不存在的版本 |

**已知的限制**：資產清單由人維護，清單不準結論就不準。
所以系統必須主動標出「這幾項寫得不夠清楚」，而不是默默亂猜。

## 2-2　主力：NVD CVE API 2.0

**為什麼是主力**：只有它同時提供 CVSS **和** CPE 結構化版本區間，
而 CPE 是「這條漏洞跟我哪台機器有關」的比對鍵。

回傳裡真正用到的三個版本邊界欄位（300 則統計）：

| 欄位 | 意思 | 出現次數 |
|---|---|---|
| `versionEndExcluding` | 上界，不含 | 138 |
| `versionStartIncluding` | 下界，含 | 118 |
| `versionEndIncluding` | 上界，含 | 105 |
| ~~`versionStartExcluding`~~ | 下界，不含 | **0（完全沒出現）** |

**重要限制**：這 300 則裡有 **199 則（66%）完全沒有 CPE**，
因為 NVD 還沒分析完（`vulnStatus` 是 `Received`）。
新公告剛出來時只有描述文字沒有結構化資料 —— 這正是需要 LLM 抽取的理由。

官方建議的取用方式：

1. 初次全量：用 `startIndex` 分頁落地
2. 之後增量：用 `lastModified` 只取有變動的
3. 自動化同步**不超過每兩小時一次**

## 2-3　建議加入的兩個（都免金鑰）

### EPSS — 會不會被利用

```
GET https://api.first.org/data/v1/epss?cve=CVE-2026-10931
→ { "cve": "...", "epss": "0.00325", "percentile": "0.25202" }
```

| | CVSS | EPSS |
|---|---|---|
| 衡量什麼 | 萬一被利用**會多嚴重** | 到底**會不會**被利用 |
| 值域 | 0–10 | 0–1（機率） |

**實測影響**：把 EPSS 乘進現有公式後，待辦順序會變 ——
MediaWiki 從第 5 升到第 3，containerd 與 Ubuntu 各降一名
（後兩者的 EPSS 落在最低的 6% 百分位）。
這種前後對照最適合寫進期末報告。

### CISA KEV — 已經在被攻擊

單一 JSON 檔，實測 **1,695 筆**，最後更新 2026-09-04。

| 欄位 | 用途 |
|---|---|
| `dateAdded` | 何時列入 |
| `dueDate` | 美國聯邦機關必須修補的期限 |
| `knownRansomwareCampaignUse` | 是否用於勒索軟體（**354 筆是，佔 21%**） |
| `requiredAction` | 建議動作 |

**建議用法：當成一票否決的置頂條件，不是加權係數。**
命中 KEV 就無條件排第一 —— 它已經不是「可能」而是「正在發生」。

> 註：目前資料集裡的 5 條 CVE 都不在 KEV，因為都是 7–8 月剛公開的新漏洞。
> 這是「KEV 是落後指標」的好教材，可以寫進報告。

## 2-4　選用：OSV.dev

**已實測**（要用完整套件路徑，不是簡稱）：

| 查詢 | 結果 |
|---|---|
| `Go` / `github.com/containerd/containerd` @ 1.7.22 | **13 筆** |

因為 OSV 聚合了 GHSA、CVE、Go Advisory 三種編號，且不受時間窗限制。

| 適合 | 不適合 |
|---|---|

**建議列為第二階段擴充，不進第一版必達範圍。**

# 三、給報告的一段話

> 本系統的對象是**有網路設備與伺服器、但只有一名 IT 人員的組織** ——
> 學校網管、公家機關資訊人員、中小企業唯一的 IT、以及一人顧多家客戶的系統整合商。
>
> 依 NVD 2026 年 7–8 月的 300 則公告實測，這類組織平均每週收到約 38 則公告，
> 其中真正與自身資產相關的僅約 2 則。系統的價值不在於節省修補時間，
> 而在於**節省「確認自己沒事」的時間** —— 九成的日子答案是「今天沒有」，
> 但在沒有工具的情況下，必須讀完全部 38 則才敢下這個結論。
>
> 且負載呈批次特性：實測樣本中 50% 的相關公告集中在同一天釋出，
> 這正是人工處理最容易漏接、而自動化最能發揮價值的時刻。

> This product uses data from the NVD API but is not endorsed or certified by the NVD.
