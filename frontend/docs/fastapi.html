01

後端到底在做什麼

先不要碰 FastAPI。我們從更基本的問題開始：為什麼需要後端？

前端一個人做不到的三件事

我們的前端（就是你現在看到的這個網站）已經能記帳、能看統計、能跳超支警告。 那為什麼還要寫後端？因為有三件事前端做不到：

做不到的事為什麼
資料存不住 前端的資料存在瀏覽器裡。換一台電腦就不見了，手機和筆電也看不到同一份帳。
多人看不到同一份資料 爸爸記的帳，媽媽的手機要看得到。資料必須放在一個大家都連得到的地方。
擋不住作弊 前端的程式碼使用者全都看得到、也改得動。「只有管理者能刪除」這種規則寫在前端等於沒寫——權限檢查一定要在後端做。

後端就是一支「聽問題、給答案」的程式

把後端想成一個永遠待命的櫃檯。前端（瀏覽器）走過去問問題，櫃檯回答。 這一問一答有固定的格式，叫做 HTTP 請求與回應：

前端問
GET /api/transactions?kind=expense HTTP/1.1
Host: fambudget-backend.onrender.com
Authorization: Bearer eyJhbGciOiJIUzI1NiJ9...
後端答
200 OK
Content-Type: application/json

{"transactions": [{"id": 1, "amount": 320, "kind": "expense"}], "total": 1}

就這樣。後端的全部工作就是：收到這種請求，回一段 JSON。 FastAPI 幫你做的，就是把這件事變得非常好寫。

JSON 是什麼？

一種寫資料的格式，長得跟 Python 的 dict 幾乎一樣： {"名字": "值", "數字": 123, "清單": [1, 2, 3]}。 前後端之間所有資料都用這個格式傳，因為每種程式語言都讀得懂它。

為什麼選 FastAPI

Python 的後端框架有好幾個。我們選 FastAPI 有三個理由， 第三個對這個專題特別重要：

寫起來就是普通 Python

定義一個函式，上面加一行裝飾器，就是一支 API。 不需要學一整套新的類別繼承架構。

自動驗證輸入

你宣告「這個欄位是整數」，前端傳文字進來它會自己擋掉並回報錯誤。 你一行驗證程式碼都不用寫。

自動產生文件

跑起來打開 /docs，你會看到一個可以直接送出請求的網頁。 四個人分工時，這等於免費得到一份永遠不會過期的對接文件。

02

第一支 API：五行程式

先跑起來，再理解。把下面五行存成 hello.py：

from fastapi import FastAPI

app = FastAPI()

@app.get("/hello")
def say_hello():
    return {"message": "你好"}
跑起來
uvicorn hello:app --reload

打開 http://localhost:8000/hello，你會看到 {"message":"你好"}。 然後打開 http://localhost:8000/docs——這才是重點。 你會看到一個互動式網頁，列出你寫的每一支 API， 可以直接按「Try it out」送出請求看結果。這份文件是自動產生的， 你沒有寫任何文件。

這五行各自在做什麼

程式碼意思
app = FastAPI()建立一個應用程式。整個專案只會有一個，我們的在 backend/app/main.py。
@app.get("/hello")裝飾器。告訴 FastAPI：「有人用 GET 打 /hello 的時候，執行下面這個函式。」
def say_hello():普通的 Python 函式。函式的名字不重要，裝飾器上的路徑才是網址。
return {...}回傳一個 dict，FastAPI 會自動轉成 JSON 送出去。你不用自己做轉換。
uvicorn 是什麼？

FastAPI 只是「寫 API 的工具」，它自己不會聽網路。 uvicorn 是真正在 8000 埠聽請求的伺服器程式。
uvicorn hello:app 的意思是「hello.py 這個檔案裡， 那個叫 app 的變數」。--reload 是存檔後自動重啟， 開發時很方便，正式環境不要開。

03

路由與方法

一支 API ＝ 一個方法 ＋ 一個路徑。兩者合起來才是唯一的。

五個方法，各自代表一種意圖

方法意思我們專案的例子
GET我要看資料GET /api/transactions
POST我要新增一筆POST /api/transactions
PUT把這個東西設定成這樣PUT /api/savings-goal
PATCH只改其中幾個欄位PATCH /api/transactions/5
DELETE刪掉DELETE /api/transactions/5

注意上面 GET /api/transactions 和 POST /api/transactions 路徑一樣但方法不同，所以是兩支不同的 API。這很常見。

PUT 和 POST 的差別：冪等

POST 打兩次會產生兩筆資料。PUT 打兩次結果一樣。
「把九月的存款目標設成 20000」不管執行幾次結果都一樣，所以用 PUT。 這個性質叫冪等。
這不只是名詞正確性的問題：網路不穩時前端可能會重送請求， 冪等的路由重送不會有副作用，非冪等的就會產生重複資料。

04

三種收資料的方式

前端要把資料送進來，有三個位置可以放。選錯位置是新手最常見的問題。

一、路徑參數 —— 指定「哪一個」

# 網址：DELETE /api/transactions/5

@router.delete("/transactions/{tx_id}")
def delete_transaction(tx_id: int):
    # tx_id 自動就是 5（而且已經轉成整數了）
    ...

路徑裡用大括號寫一個名字，函式參數用同樣的名字接。 你宣告 : int，FastAPI 就會幫你轉型別； 有人打 /transactions/abc，它會自己回錯誤，你的函式根本不會被執行。

二、查詢參數 —— 篩選、排序、分頁

# 網址：GET /api/transactions?kind=expense&page=2

@router.get("/transactions")
def list_transactions(
    kind: str | None = None,       # 有預設值 → 可有可無
    page: int = 1,                # 沒帶的話就是 1
):
    ...

怎麼分辨是路徑參數還是查詢參數？ FastAPI 的規則很簡單：名字有出現在路徑的大括號裡 → 路徑參數； 沒有 → 查詢參數。你不用特別宣告。

加上說明與驗證
from fastapi import Query

page: int = Query(1, ge=1, description="第幾頁，從 1 開始")

ge=1 是「大於等於 1」，有人傳 page=0 會被自動擋下。 description 會顯示在 /docs 上——等於順手把文件寫好了。

三、請求主體 —— 送一整包資料進來

from pydantic import BaseModel

class LoginRequest(BaseModel):
    email: str
    password: str

@router.post("/login")
def login(payload: LoginRequest):
    # payload.email、payload.password 直接就能用
    ...

FastAPI 看到參數的型別是一個 Pydantic 模型，就知道「這包東西在請求主體裡」， 會自動把 JSON 轉成物件。這是下一節的主角。

密碼絕對不可以放在查詢參數

查詢參數會出現在網址上，而網址會被瀏覽器歷史、伺服器日誌、 Referer 標頭全部記下來。密碼、權杖這類敏感資料一律放在請求主體。
這就是為什麼登入一定是 POST 而不是 GET。

05

Pydantic：型別標註突然變得有用

Python 的型別標註（x: int）平常只是給人看的註解，不會真的檢查。 Pydantic 讓它變成真的會執行的驗證。

沒有 Pydantic 的話你要寫什麼

❌ 自己驗

def create(data: dict):
    if "amount" not in data:
        return error("缺少 amount")
    if not isinstance(data["amount"], int):
        return error("amount 要是整數")
    if data["amount"] <= 0:
        return error("amount 要大於 0")
    # ...每個欄位都要寫三次

✅ 用 Pydantic

class TxCreate(BaseModel):
    amount: Decimal = Field(gt=0)
    kind: Literal["income", "expense"]
    merchant: str | None = None

# 驗證的程式碼：零行
# 格式錯誤 FastAPI 自己回 422，
# 而且會明講是哪個欄位錯、錯在哪

回應也要宣告：一道安全網

class UserResponse(BaseModel):
    id: int
    display_name: str
    # 注意：這裡沒有 password_hash

@router.get("/me", response_model=UserResponse)
def me():
    user = db.get(User, 1)
    return user   # 就算整個 user 物件含密碼雜湊…
                  # …FastAPI 也只會送出 id 和 display_name
這就是我們把 models 和 schemas 分開的原因

models/ 說的是「資料庫裡存什麼」——User 一定要有 password_hash。
schemas/ 說的是「API 收送什麼」——UserResponse 絕對不能有 password_hash。
兩者分開之後，你不可能「不小心」把密碼雜湊回傳給前端， 因為 response model 裡根本沒有那一欄。

06

錯誤與狀態碼

出錯時不要 return {"error": "..."}，要丟出 HTTPException。 

from fastapi import HTTPException, status

if tx is None:
    raise HTTPException(
        status_code=status.HTTP_404_NOT_FOUND,
        detail="找不到這筆紀錄",
    )

差別在哪？return 會讓 HTTP 狀態碼還是 200（成功）， 前端的 fetch 不會進入錯誤處理分支，它會以為一切正常然後拿到一包看不懂的東西。 raise HTTPException 才會真的回傳錯誤狀態碼。

這個專案會用到的狀態碼

碼意思什麼時候用
200成功預設值，不用特別寫
201建立成功註冊、新增一筆帳。讓前端一看就知道東西建好了
401你還沒證明你是誰沒帶 token、token 過期 → 前端該導去登入頁
403我知道你是誰，但你不能做這件事一般成員想刪別人的帳 → 前端該顯示「權限不足」
404找不到那筆資料不存在
409衝突email 已經被註冊過了
422格式不對Pydantic 自動回的，你不用自己寫
500我們的程式壞了沒接到的例外。看到這個就是要去修 bug
503依賴的服務不行模型服務叫不動。不要回 500，我們沒壞
401 和 403 一定要分清楚

分錯的後果很具體：前端會把「權限不足」的使用者一直踢回登入頁， 他重新登入還是不能用，然後就來問你為什麼系統壞了。

07

依賴注入：FastAPI 最核心的概念

這一節最重要。看懂了，後面的資料庫和登入都會變得很簡單。

先看問題

我們有三十幾支需要登入的路由。每一支都要做這七件事： 

# 1. 從標頭拿出 Authorization
# 2. 檢查格式是不是 "Bearer xxxxx"
# 3. 驗證簽名
# 4. 檢查有沒有過期
# 5. 拿出 user_id
# 6. 去資料庫撈使用者
# 7. 確認帳號沒被停用

三十幾支每支都複製一次？不可能維護。而且只要有一支忘記寫， 那支就變成任何人都能打的漏洞。

解法：宣告你需要什麼，FastAPI 幫你準備好

from fastapi import Depends

@router.get("/transactions")
def list_transactions(me = Depends(get_current_user)):
    # 能執行到這一行，代表上面七步全部通過了
    # me 就是已經驗證過的登入者
    ...

Depends(get_current_user) 的意思是 「執行我之前，先幫我把這件事做完」。 如果驗證失敗，get_current_user 裡會丟出 401， 路由的程式碼一行都不會被執行。

依賴可以疊起來

def require_master(me = Depends(get_current_user)):
    # 這個依賴自己也用了另一個依賴
    if me.role != "master":
        raise HTTPException(403, "只有管理者可以")
    return me

@router.post("/family/invite")
def invite(me = Depends(require_master)):
    # 「要登入」和「要是管理者」兩層檢查都做完了
    ...
這在我們專案的哪裡

backend/app/core/deps.py —— get_current_user 和 require_master 都在這個檔案。 你寫路由時只要 import 進來用就好，不用理解裡面怎麼實作的。

08

接資料庫

我們用 SQLAlchemy。它讓你用 Python 的類別和物件操作資料庫， 不用手寫 SQL 字串。

一張表 ＝ 一個類別

from sqlalchemy.orm import Mapped, mapped_column
from app.core.database import Base

class Transaction(Base):
    __tablename__ = "transactions"

    id: Mapped[int] = mapped_column(primary_key=True)
    user_id: Mapped[int] = mapped_column(ForeignKey("users.id"))
    amount: Mapped[Decimal] = mapped_column(Numeric(14, 2))
    kind: Mapped[str]
    merchant: Mapped[str | None]
金額一定要用 Numeric，不能用 float

浮點數在二進位下無法精確表示 0.1 這種值。累加幾千筆之後 你會得到 12345.670000000002。
財務系統不能接受這個。資料庫用 NUMERIC(14,2)， Python 這邊用 Decimal。

在路由裡用它

from sqlalchemy.orm import Session
from app.core.database import get_db

@router.get("/transactions")
def list_transactions(db: Session = Depends(get_db)):
    return db.query(Transaction).filter(
        Transaction.kind == "expense"
    ).all()

又是 Depends。你不用自己建立連線、也不用記得關閉—— get_db 用了 yield，所以不管路由成功還是出錯， 連線都一定會被關掉。忘記關連線是後端最常見的資源洩漏， 寫成這樣就不會發生。

寫入要記得 commit

tx = Transaction(user_id=1, amount=Decimal("320"), kind="expense")
db.add(tx)
db.commit()        # ← 忘記這行的話，資料根本沒存進去
db.refresh(tx)      # 把資料庫產生的 id 讀回來
批次寫入要嘛全成功，要嘛全不寫

段落記帳一次要寫 5 筆。如果寫到第 3 筆失敗，前面 2 筆已經進去了， 使用者會看到「寫入失敗」但明細裡卻多了兩筆——然後他會再按一次，變成重複記帳。
做法：迴圈裡只 db.add()，迴圈結束後才 commit 一次； 中間出錯就 db.rollback()。

09

登入怎麼做

HTTP 是「無狀態」的：伺服器處理完一個請求就忘光了，下一個請求進來時它不知道你是誰。 那登入之後怎麼記住？

JWT：一張有簽名的通行證

eyJhbGciOiJIUzI1NiJ9 . eyJzdWIiOiIxIiwiZXhwIjoxNzY4fQ . 3vQ2n1k...
└──── 標頭 ────┘   └──────── 內容 ────────┘   └─ 簽名 ─┘
部分裝什麼誰讀得到
標頭用什麼演算法簽的所有人
內容你是誰、什麼時候過期所有人
簽名用密鑰算出來的驗證碼只有伺服器算得出來
JWT 的內容是公開的，不是加密的

中間那段只是 base64 編碼，任何人複製貼到線上工具就能解開來看。 所以永遠不要把密碼、身分證字號放進 JWT。
它保證的是「沒有人能竄改內容」，不是「沒有人看得到內容」。

完整的登入流程

1
使用者送出 email 和密碼
POST /api/auth/login，資料放在請求主體（不是網址）
↓
2
後端比對密碼
把輸入的密碼再雜湊一次，跟資料庫存的比。 不是把資料庫的解回來——bcrypt 是單向的，解不回來。
↓
3
發兩張 token
access token（30 分鐘，每次請求都帶）＋ refresh token（14 天，只用來換新的 access token）
↓
4
之後每個請求都帶著 access token
Authorization: Bearer eyJhbGciOi...
↓
5
過期時前端自動續期
某支 API 回 401 → 前端自動打 /refresh → 拿到新的 → 把剛才失敗的請求重送一次。使用者完全沒感覺。

為什麼要兩張 token？

access token · 30 分鐘

每次請求都帶著，到處跑，外洩風險高 → 所以讓它很快過期。

它不存在資料庫裡，所以沒辦法主動撤銷。這就是為什麼要設短。

refresh token · 14 天

只在換新 access token 時用，露臉次數少。

它存在資料庫的 sessions 表裡，所以登出時可以標記成作廢。

結果是：使用者不用每 30 分鐘重新登入一次（前端自動續期）， 但如果帳號被盜，撤銷 refresh token 之後，攻擊者最多再撐 30 分鐘。

「登出」在 JWT 系統裡的真正意義

我們沒辦法把已經發出去的 access token 收回來——它不在資料庫裡。 所以登出其實是：把 sessions 那筆設 revoked_at ＋ 前端刪掉 token。
手上那張 access token 最多還能用 30 分鐘，但想續期就會被擋下來。

10

檔案怎麼分

三十五支路由全寫在 main.py 會變成兩千行的怪物，而且四個人一起改必定衝突。 FastAPI 用 APIRouter 解決這件事。

routers/auth.py — 各自的檔案
from fastapi import APIRouter

router = APIRouter()

@router.post("/login")     # 注意：這裡不寫 /api/auth
def login():
    ...
main.py — 掛上去
from app.routers import auth

app.include_router(auth.router, prefix="/api/auth", tags=["身分認證"])

# 結果：routers/auth.py 裡的 "/login"
#       實際網址變成 /api/auth/login

prefix 會自動加在每一支路由前面。 tags 是給自動文件用的分類，打開 /docs 就會照這個分組。

這就是四個人能平行動工的關鍵

每個人改自己的 router 檔案，git 幾乎不會衝突。 main.py 只有七行 include_router， 任何人打開它三十秒就能看懂整個系統有哪些功能。

為什麼 routers 不寫邏輯

我們的規定是：routers 只做三件事——收請求、驗權限、回結果。 真正的計算與規則寫在 services/。

❌ 全寫在路由裡

要測「存款目標超支的判斷對不對」，你得起一個 HTTP 請求、 準備 token、準備資料庫……測一個算式要準備半天。

✅ 邏輯放 services

savings_status(income, expense, goal) 是純函式， 直接呼叫就能測，一秒跑完。

實作一支路由的順序

1
先寫 schemas/
決定這支 API 收什麼、回什麼。先把資料形狀定下來，後面才不會改來改去。
2
再寫 models/
資料表長什麼樣。欄位定義照專題手冊的資料庫設計那一節。
3
邏輯寫進 services/
計算、規則。純函式，好測試。
4
最後回到 routers/ 把 TODO 填掉
路由只負責串起來：驗權限 → 呼叫 service → 回結果。
5
打開 /docs 直接試打
不用等前端、不用裝 Postman。右上角 Authorize 貼上 token 就能試需要登入的路由。
前端已經寫好了，回應形狀要對得上

frontend/js/api.js 裡面有完整的路由契約， 而且 mock 模式已經用假資料把所有畫面跑起來了。
你的 API 回應只要跟那份形狀一致，前端把 <meta name="api-base"> 填上網址就能直接接上，一行前端程式碼都不用改。
不確定要回什麼形狀時，去看 api.js，那是唯一的真相來源。

卡住的時候

下面這幾個是一定會遇到的，先看過有印象就好。

你看到的錯誤原因與解法
blocked by CORS policy 前端網域沒有被允許。改 .env 的 ALLOWED_ORIGINS。 網址要完整（含 https://），結尾不要加斜線。
ValidationError:
database_url Field required		 沒建立 .env，或少了必填變數。 這是刻意的設計——寧可啟動時就失敗，也不要等使用者按下按鈕才發現設定是空的。
422 Unprocessable Entity 送進來的資料格式不對。回應主體裡會明講是哪個欄位、錯在哪，仔細讀它。
501 Not Implemented 那支路由還沒實作。這是正常的，不是 bug——去找對應的 TODO。
資料沒有存進去 忘記 db.commit()。這個錯誤不會有任何提示，是最容易卡很久的一個。
改了程式但沒生效 啟動時沒加 --reload。
ModuleNotFoundError: No module named 'app' 你在錯的目錄下執行。要在 backend/ 底下跑，不是在 backend/app/。

三個永遠可以用的除錯方法

1. 打開 /docs 試打

排除前端的干擾。如果在 /docs 上打得通、在前端打不通， 那就是前端或 CORS 的問題，不是你的路由。

2. 看實際送出的 SQL

把 core/database.py 的 echo=False 改成 True， SQLAlchemy 會把每一句 SQL 印出來。查完記得改回去。

3. 先 print 再說

在可疑的地方 print(變數)，看值是不是你以為的那樣。 八成的 bug 是「我以為這裡是 5，結果是字串 '5'」。
