RESTful API 說明書

REST 不是技術，是一套取名字的約定。約定好之後， 別人看到你的網址就猜得出它會做什麼——不用問你、不用翻文件。
這份文件會先用圖書館把概念講完，再回頭誠實檢查 我們自己的 38 支路由：哪些符合、哪些故意不符合、哪些該改。

預計閱讀25 分鐘
前置知識看過 FastAPI 說明書
本專案38 支路由
01

REST 是什麼

先講結論：REST 是一套幫 API 取名字的規矩。 它不會讓你的程式跑比較快，但會讓別人看得懂。

沒有約定的世界長什麼樣

假設四個人各寫各的，沒有約定，你會得到這種東西： 

POST /getUserList          ← 「取得」用 POST？
GET  /deleteTransaction?id=5   ← 用 GET 刪東西？
POST /api/v2/doUpdateBudgetNew ← new？那 old 是什麼
POST /transaction_create       ← 底線？其他都是駝峰

四個人四種風格。每接一支都要先問作者「這支怎麼用」， 而且 GET /deleteTransaction 那支很危險—— 瀏覽器和爬蟲會自動發 GET 請求，你的資料可能會被自己的搜尋引擎刪掉。

有了約定之後

GET    /users              看使用者清單
DELETE /transactions/5     刪掉第 5 筆交易
PATCH  /budgets/3          改第 3 筆預算的某些欄位

不用問任何人，你就看得懂這三支在做什麼。 這就是 REST 的全部價值。

名字的由來（知道就好，不重要）

REST 是 REpresentational State Transfer 的縮寫， 來自 Roy Fielding 在 2000 年的博士論文。
原始論文講的東西比我們用到的多很多，但業界講的 REST 九成就是這份文件講的這些約定。你不需要讀那篇論文。

02

核心觀念：網址是名詞，動作是方法

整份文件如果你只記得一句話，記這句：
網址講「對誰做」，HTTP 方法講「做什麼」。

用圖書館想

把 API 想成圖書館的櫃檯。書是資源，網址就是「哪一本書」， 方法就是「你要對它做什麼」：

GET
/books
給我書單
GET
/books/5
給我第 5 本書
POST
/books
進一本新書
PATCH
/books/5
改第 5 本的書名
PUT
/books/5
把第 5 本整本換掉
DELETE
/books/5
報廢第 5 本

注意看：網址只有兩種——/books（全部）和 /books/5（其中一本）。六件不同的事，只用了兩個網址。 動作全部藏在方法裡。

最常見的錯誤：把動詞寫進網址

❌ 動詞在網址

POST /getBooks
POST /createBook
POST /updateBook
POST /deleteBook

四個網址，全部都 POST
網址會無限增加

✅ 動詞在方法

GET    /books
POST   /books
PATCH  /books/5
DELETE /books/5

兩個網址，四個方法
加功能不會加網址
為什麼「動詞在網址」會失控

因為動詞是無限的。今天有 createBook，明天就會出現 createBookWithAuthor、createBookBulk、 createBookV2……
名詞是有限的。 圖書館就是只有書、作者、借閱紀錄這幾種東西。 用名詞當網址，API 的規模就被鎖住了。

03

五個方法各自的意思

方法白話用在我們的例子
GET 我要看讀資料，不可以改任何東西 GET /api/transactions
POST 我要新增一個建立新資源，伺服器決定 ID POST /api/transactions
PUT 把它設定成這樣整個換掉，沒給的欄位會變空 PUT /api/savings-goal
PATCH 只改這幾個欄位局部更新，沒給的欄位保持原狀 PATCH /api/transactions/5
DELETE 拿掉它刪除 DELETE /api/transactions/5

PUT 和 PATCH 差在哪？這題最多人搞混

假設第 5 筆交易長這樣： 

{ "amount": 320, "merchant": "自助餐", "note": "午餐" }

PATCH /transactions/5

送 { "amount": 350 }

結果：
{ "amount": 350,
  "merchant": "自助餐",   ← 保留
  "note": "午餐" }        ← 保留

PUT /transactions/5

送 { "amount": 350 }

結果：
{ "amount": 350,
  "merchant": null,       ← 被清空！
  "note": null }          ← 被清空！
用錯的後果是真的會弄丟資料

使用者只想改金額，結果店家和備註都不見了——而且不會有錯誤訊息， 因為從伺服器的角度看，你確實叫它「把這筆設定成只有 amount 的樣子」。
不確定的時候用 PATCH。 局部更新永遠比整個換掉安全。

04

網址怎麼設計

五條規則

#規則❌✅
1用名詞，不用動詞 /getBooks/books
2集合用複數 /book/5/books/5
3全部小寫，多字用連字號 /savingsGoal/savings-goals
4結尾不加斜線 /books//books
5層級表示從屬關係 /getFamilyMembers?f=1/families/1/members

層級要切到哪一層？

從屬關係可以無限往下疊，但超過兩層就很難唸了： 

/families/1/members                       還好
/families/1/members/4                     還好
/families/1/members/4/transactions        開始長了
/families/1/members/4/transactions/9/tags  沒人記得住

超過兩層就改用查詢參數： 

/transactions?userId=4            比 /families/1/members/4/transactions 好
我們的做法

本專案一個使用者只屬於一個家庭，而且登入之後後端就知道你是誰、 在哪個家庭。所以網址裡完全不需要出現家庭 ID—— /api/transactions 自然就是「我看得到的那些」。
這比 /families/1/transactions 更安全： 使用者沒機會把 1 改成 2 去偷看別人家的帳。

05

狀態碼是回應的一部分

很多新手把所有回應都設成 200，再用回應內容的 success: false 表示失敗。 這會讓前端寫得很痛苦。

❌ 全部回 200

200 OK
{ "success": false,
  "message": "找不到" }

前端的 fetch 不會進錯誤分支
每支 API 都要自己拆內容判斷

✅ 用狀態碼

404 Not Found
{ "detail": "找不到這筆紀錄" }

前端 if (!r.ok) 一行搞定
瀏覽器、CDN、監控都看得懂

三位數的第一個數字就是分類

2xx  成功        你要的事做好了
3xx  轉址        東西搬家了（我們用不到）
4xx  你錯了      請求有問題，重送一樣會失敗
5xx  我錯了      伺服器壞了，重送可能會成功

4xx 和 5xx 的分界很重要： 4xx 是「使用者送錯東西」， 不用叫工程師起床；5xx 是「我們的程式壞了」，要有人去修。 分錯的話監控系統會一直誤報。

這個專案會用到的

碼意思什麼時候回
200成功讀取、更新、刪除成功
201建立成功註冊、新增一筆帳。POST 成功要回 201 不是 200
204成功但沒內容刪除成功且沒東西要回
400請求有問題語意錯誤（格式錯誤請用 422）
401你還沒證明你是誰沒帶 token、token 過期
403我知道你是誰，但你不能成員想刪別人的帳
404找不到那筆資料不存在
409衝突email 已經被註冊過
422格式不對Pydantic 自動回的，你不用寫
500我們的程式壞了沒接到的例外
503依賴的服務不行模型服務叫不動。不要回 500
401 和 403 分錯的具體後果

前端看到 401 會把使用者導去登入頁，看到 403 會顯示「權限不足」。
分錯的話，權限不足的使用者會被一直踢回登入頁， 他重新登入還是不能用，然後就來問你為什麼系統壞了。

06

安全與冪等

兩個聽起來很學術、但實際影響很大的性質。

安全（Safe）＝ 不會改變任何東西

只有 GET 是安全的。這代表瀏覽器、CDN、爬蟲 可以自己決定要不要幫你多打幾次，不會出事。

所以絕對不要用 GET 做會改變資料的事

如果你寫了 GET /deleteTransaction?id=5：
瀏覽器的預先抓取、聊天軟體的連結預覽、搜尋引擎的爬蟲…… 任何一個碰到這個網址，你的資料就沒了。
這不是理論，是真的發生過的事故。

冪等（Idempotent）＝ 做幾次結果都一樣

方法安全冪等打兩次會怎樣
GET✅✅看兩次，沒事
PUT❌✅設定成一樣的值，沒事
DELETE❌✅第二次回 404，但東西一樣是沒了
PATCH❌看情況設定值就冪等，「加 100」就不冪等
POST❌❌會產生兩筆！
為什麼這件事在我們的專案裡特別重要

使用者在捷運上按下「確認並寫入 5 筆」，網路不穩， 前端沒收到回應就自動重送——結果寫進去 10 筆。
POST 不冪等是天生的，所以批次寫入那支要特別小心： 要嘛前端不自動重送，要嘛後端用一個「這批的唯一識別碼」擋掉重複。

07

參數放路徑還是查詢字串？

路徑參數 — 指定「哪一個」

/transactions/5
/family/members/4

這一段是資源身分的一部分。 少了它，這個網址就不知道在講誰。

查詢參數 — 篩選、排序、分頁

/transactions?kind=expense
/transactions?page=2

拿掉之後網址仍然有意義， 只是範圍變大。所以它們都應該是選填的。

一句話判斷

拿掉它，網址還講得通嗎？
講得通 → 查詢參數。　講不通 → 路徑參數。 

/transactions/5      拿掉 5 → /transactions 講得通嗎？
                     講得通（全部），但意思完全不同 → 路徑參數 ✓

/transactions?page=2 拿掉 page → /transactions 講得通嗎？
                     講得通，而且意思一樣（只是第一頁）→ 查詢參數 ✓
敏感資料絕對不可以放查詢參數

查詢參數會出現在網址上，而網址會被瀏覽器歷史、伺服器日誌、 Referer 標頭、代理伺服器全部記下來。
密碼、token 這類東西一律放請求主體。 這就是為什麼登入是 POST 不是 GET。

08

誠實檢查我們自己的 38 支

我把本專案的每一支路由都對上面的規則檢查過。 結果是：38 支裡有 22 支不符合嚴格的 REST 慣例。

這個數字不代表設計很差

22 支裡面，大部分是業界通用做法或刻意的取捨， 只有 3 支是真的該改。下面逐類講。

第一類：業界通用，不用改（17 支）

路由嚴格說的問題為什麼不改
POST /api/auth/login
POST /api/auth/logout
POST /api/auth/refresh
POST /api/auth/register		 網址有動詞 REST 純粹主義者會說應該是 POST /sessions，但沒有人真的這樣做。 這四支是全世界都看得懂的慣例，改成「正確」的反而沒人看得懂。
GET /api/auth/me 單數、而且 me 不是資源 「目前登入的那個人」的通用寫法。替代方案是 /users/{我的id}，但前端還要先知道自己的 ID，多一趟往返。
GET,PATCH /api/auth/me
PUT,DELETE /api/auth/me/avatar
GET /api/summary
GET /api/family
GET,PUT /api/savings-goal
PATCH /api/auth/password		 用了單數名詞 這些是 singleton resource（單例資源）—— 一個使用者只有一份摘要、只屬於一個家庭、每期只有一個存款目標。 單數在這種情況是正確的，複數才奇怪。

第二類：刻意違反，因為 REST 表達不了（5 支）

路由為什麼 REST 表達不了
POST /api/nlp/parse
POST /api/nlp/parse-batch		 它不建立任何東西。 它把一段文字算成結構化欄位然後回傳， 刻意不寫進資料庫。REST 的五個方法裡沒有一個能表達 「幫我算一下但不要存」。硬要套的話只能叫 POST /parse-results，然後假裝建立了一個不存在的資源—— 那更難懂。
POST /api/nlp/confirm
POST /api/nlp/confirm-batch		 這兩支其實是在建立 transactions，嚴格說應該是 POST /api/transactions。但我們刻意分開， 因為來源必須分得清楚：走這支的 source 記 nlp，走 transactions 的記 manual。 混在一起的話模型正確率的分母就錯了。
POST /api/family/invite 產生一組邀請碼。勉強可以說是 POST /api/family/invites（建立一張邀請）， 其實這樣更好——見下面第三類。

第三類：真的該改（3 支）

這三支改成 RESTful 之後更清楚，不是為了合規而合規：

現在建議改成為什麼比較好
POST /api/advices/generate POST /api/advices 產生建議就是在建立 advices 資源。 已經有 GET /api/advices 了， 用同一個網址加 POST 完全符合直覺，也少一個網址。
POST /api/family/join POST /api/family/members 加入家庭就是建立一筆成員關係。 而且已經有 PATCH /api/family/members/{id} 了， 用同一組路徑比較一致。
POST /api/auth/logout-all DELETE /api/auth/sessions 「撤銷所有工作階段」就是刪掉 sessions 集合。 而且已經有 GET /api/auth/sessions 了。
改不改？

這三支目前前端都還沒在用，所以改的成本很低（改 router + 契約文件）。
但也不是非改不可——一致性比正確性重要。 如果決定不改，就在報告裡誠實寫「我們知道這裡不是嚴格的 REST，理由是 X」， 那比假裝沒發現好得多。

09

什麼時候該違反 REST

REST 是指引不是法律。知道什麼時候該破例，比死守規則更重要。

三個正當的破例時機

1. 那個動作不是 CRUD

「解析這段文字但不要存」「重新計算」「寄一封信」—— 這些本質上是動作不是資源。硬套 REST 會產生 POST /parse-results 這種假資源，更難懂。

2. 業界已有更強的慣例

/login、/logout、/me、 /search、/healthz。
大家都看得懂的東西，比理論上正確的東西有價值。

3. RESTful 會讓前端多跑一趟

我們的 /api/summary 一次回傳 KPI、分類佔比、月趨勢、成員狀態。嚴格 REST 會拆成四支， 前端要打四次。一次回完，使用者體驗好得多。

但這三個不可以破例

1. GET 絕對不可以改資料。 這不是風格問題，是會出事故。
2. 狀態碼要用對。 前端、CDN、監控全都靠它判斷。
3. 同一個專案裡要一致。 你可以選擇不 RESTful， 但不可以一半 RESTful 一半不——那是最糟的情況。

10

十個常見錯誤

動工前掃一遍，寫完之後再對一次。

#錯誤會發生什麼
1用 GET 做刪除或修改 爬蟲和預先抓取會幫你把資料刪光
2全部回 200，用內容表示失敗 前端每支都要自己拆內容判斷，而且監控看不出有錯
3401 和 403 混用 權限不足的使用者被一直踢回登入頁
4該用 PATCH 卻用 PUT 使用者只想改金額，店家和備註被清空，而且沒有錯誤訊息
5沒權限時回空陣列 使用者以為「對方沒記帳」，而不是「我看不到」。要回 403
6把 ID 放在查詢參數當主鍵用 /transactions?id=5 語意模糊，而且不好做權限檢查
7單複數混用 /book/5 和 /books 並存，別人每次都要猜
8回傳的欄位命名不一致 這支叫 userId、那支叫 user_id，前端要一直轉換
9POST 成功回 200 而不是 201 不算大錯，但前端沒辦法用狀態碼區分「建立」和「更新」
10錯誤訊息把內部細節吐出來 psycopg.errors.UniqueViolation: ... 讓攻擊者知道你用什麼資料庫、 表叫什麼名字。要包成人看得懂的訊息
