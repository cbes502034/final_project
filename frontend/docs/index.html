四人 × 一個月 · 期末專題

家庭記帳與財務控管系統

以家庭為單位的記帳系統：每個人有自己的帳本，監管關係決定誰看得到誰， 家長負責家庭治理。LLM 的位置不在「產生建議」，而在 把一段話拆成好幾筆帳——那是這個系統最容易被放棄的環節，也是規則寫不完的地方。

01

源起

主題換過三次。最後選記帳，不是因為它最酷，是因為四個人都對它有共鳴—— 每個人都記過帳，也都放棄過。這件事比題目本身更重要：組員講得出使用情境， 討論才會有內容。

硬性要求：LLM 必須是主軸

如果 LLM 只用來產生財務建議，會有一個致命問題——把 LLM 拿掉，系統照樣能跑。 記帳、統計、圖表、預算全都不需要模型。評審一定會問這題。

解法：把 LLM 放在「記一筆帳」這個動作上

記帳 App 最大的失敗原因不是功能不夠，是懶得輸入。 選分類、填金額、挑日期、打店名——摩擦一高，兩週後就放棄。 讓使用者寫一段話就好，摩擦才降得下來。

為什麼規則式做不到

難點例子規則寫得出來嗎
相對日期今天午餐吃了120 / 昨天加油勉強
中文數字媽媽給我兩千勉強
店名歧義在全家買飲料165 ← 是店名，不是家人做不到
收支方向媽媽給我兩千 → 是收入不是支出做不到
語意分類便利商店算餐飲還是日用品？做不到
合計語意三個平台訂閱費共3400做不到
段落切分一段話裡到底有幾筆帳做不到

每個人的講法都不一樣，規則永遠寫不完。 這就是 LLM 在本系統不可取代的位置。

資料飛輪

使用者每修正一次解析結果，就等於免費標了一筆訓練資料。這些修正存進 nlp_parses，同時是評測的來源與下一輪的訓練資料。 用得越久 → 資料越多 → 模型越準 → 摩擦越低。

LLM 的三個用途，依重要性排序

#用途拿掉會怎樣評測指標
1段落記帳（文字 → 結構化欄位）系統回到手動輸入，核心價值消失一次輸入完全正確率
2消費自動分類使用者每筆都要自己選分類分類 Macro-F1
3財務控管建議少一個加值功能，系統還能用建議可用性評分
02

專案說明

一句話：以家庭為單位的記帳系統，用自然語言降低輸入摩擦，用月／年兩個時間準據做財務控管。

系統要做到的四件事

  • 每個人有自己的帳本，資料互不混雜
  • 子女的消費同步給監管者——依監管關係，不依頭銜
  • 月、年兩個時間準據做統整
  • LLM 抓出收支狀況，產生財務控管建議

三個設計原則

  • 模型不直接寫資料庫：解析與寫入分兩步，中間一定有人確認
  • 金額一律由後端算：模型只負責敘述，每條建議附可驗算的依據
  • 監管雙向可見：系統不提供「隱藏監管」選項

選型的四個前提

限制造成的影響
只有一個月不能有學習曲線陡的東西。每個新框架都要換算成「幾天學會」
四人中三人沒有專案經驗工具要好上手、錯誤訊息看得懂、查得到中文資料
一人有 FastAPI / Docker / Render 實戰後端主幹沿用熟悉的，不為了「更好」而換
沒有 GPU只能在 Colab 或 Kaggle 的免費 T4 上微調小模型，這條直接決定了模型大小的上限
選型原則：能不加的就不加

每多一個相依，就多一個可能在最後一週爆炸的點。這句話是後面所有「不用某某技術」的共同理由。

六週排程

總長六週 = 實作四週 + 測試不到一週 + 報告簡報。 後端線與模型線並行，不是接力 —— 標註資料不用寫程式， 第 1 週就能開始，那是唯一能跟後端開發平行的工作。

為什麼要留到兩輪微調

第一輪幾乎一定會讓你失望 —— 資料太少、參數沒調好、格式沒對齊。 做過的人都知道。第二輪才是真的。
這是報告裡「我們試了但沒成功」和「0.42 → 0.61 → 0.79」的差別。
而且第 3 週系統能用之後，四個人自己用一週收集到的真實修正， 正好餵給第二輪 —— 資料飛輪從投影片上的概念變成真的轉過一圈。

測試不能留到第 5 週

不到一週的測試週只夠「全系統走一遍 + 修小 bug」。 真正的測試要邊做邊測：每支路由寫完當下就用 /docs 試打，不要累積。
第 5 週要走過的清單：三個層級各走一遍：平台 master / 家長 parent / 子女 child、權限的反向測試 —— 成員去打家庭總覽要被擋，這比正向測試重要、段落記帳的邊界：缺欄位、低信心、切分錯誤、空輸入、超長輸入、金額邊界：0、負數、小數、很大的數字、年度統計的「未完整」標示有沒有出現、帳號不存在與密碼錯誤，回的訊息要一樣、批次寫入寫到一半失敗，要全部不寫（不可以留下半筆）

第 1 週要凍結的三份契約

分類體系（成員3 定義並提供 GET /api/categories，成員2 寫進 prompt、成員4 評測要用）—— 這是唯一的跨模組阻塞點。
API 回應形狀（各模組自己定，但要寫進 js/api.js）
解析結果的 JSON Schema（成員2 定在 schemas/nlp.py，成員1 的模型呼叫層要照這個驗）

大頭貼不能存檔案系統

Render 的磁碟是暫時性的 —— 檔案寫進去，服務重新部署或重啟之後就不見了， 免費方案沒有持久磁碟。
所以大頭貼要存進資料庫（users.avatar_blob）。 縮到 256×256 之後大約 20~50 KB，完全沒問題。
縮圖在前端做，後端縮圖要裝 Pillow，映像檔會大好幾十 MB； 瀏覽器的 canvas 一行 toBlob() 就搞定。

平台管理員（master）

系統層級，不屬於任何家庭。能停權，但讀不到任何一筆帳—— 停權是關門，不是配鑰匙。

監管必須雙向可見

系統不提供「隱藏監管」的選項。偷偷監看家人的消費會破壞信任， 而信任正是家庭記帳能持續下去的前提。

可見範圍來自監管關係，不是頭銜。家長能做家庭治理，但他能看誰的明細，一樣要看 guardianships 這張表——沒有被指派監管誰，就只看得到自己。
這條界線讓「誰看得到我」永遠是一個可以查、可以列出來的清單，而不是一句「家長本來就看得到」。

而且監管是唯讀的。監管者看得到對方的記帳明細，但不能改、不能刪，更不能登入對方的帳號。
這條界線讓監管站得住腳：被監管的人知道自己的紀錄不會被動手腳。能登入對方帳號的話，這份信任就沒了。

存款目標怎麼算

可支配上限 = 本月收入 − 每月存款目標
使用率 = 支出 ÷ 可支配上限

使用率 < 80%   → 達標中
80% ~ 100%     → 接近上限
> 100%          → 存不到目標，算出短少多少
家庭總數會蓋掉個人的問題

結餘多的成員會把其他人的超支蓋過去——家庭整體顯示安全，個別成員卻存不到目標。 所以家庭總覽除了總數，一定要逐人列出狀態。這是聚合統計的陷阱，報告裡值得講。

刻意不用的東西

這一段跟工具清單一樣重要。講得出為什麼不用，才顯得清單不是隨手抄的。

React / Vue

十一個畫面已經寫完（含登入、註冊、個人資料、成員紀錄、群組），重寫是純成本。三個沒有專案經驗的人要同時學 React、Vite、hooks， 再加上後端與模型，一個月做不完。

這是有意識的取捨，不是能力不足——要寫進報告。有時間該升級的是打包（Vite）， 不是框架，因為那只影響建置流程，不必重寫畫面。

Django

內建 admin 與 auth 聽起來很划算，但實戰經驗在 FastAPI，換框架等於放棄既有優勢。 Django ORM 與 Pydantic 是兩套思維，混用會亂。

而且本專案的 API 是給自己的前端用，不需要 Django 的完整後台。

Redis（第一版）

session 用 sessions 表就夠；一個家庭幾百筆交易，直接查資料庫毫秒級； LLM 回應存進 nlp_parses 反而更有用，因為那同時是訓練資料。

多一個服務就多一個要維護、要部署、要除錯的東西。有時間再加。

07

MVC 流程

FastAPI 本身不是 MVC 框架，但分層的職責可以一對一對應過去。 報告裡用 MVC 講會比較好懂，實作上就是 routers / services / models 三層。

View
frontend/ 前端
  • app.js 十一個畫面的繪製
  • api.js 唯一的資料入口
  • 不含任何金額計算
  • 只負責顯示與收集輸入
Controller
routers/ + services/
  • routers/ 接收請求、驗權限、回傳
  • services/ 商業邏輯
  • schemas/ Pydantic 驗證進出
  • 模型呼叫也在這一層
Model
models/ + PostgreSQL
  • SQLAlchemy 資料表定義
  • Alembic 管理結構變更
  • 唯一的真實資料來源
  • 所有金額從這裡算出來

一次請求走完的路：以「段落記帳寫入」為例

1
View · 使用者按下「確認並寫入 5 筆」
app.js 把畫面上五列的欄位收回來，呼叫 API.nlpConfirmBatch(items)。 前端不做任何金額運算，只把使用者確認過的值送出去。
2
View · api.js 決定送去哪裡
mock 模式寫進 localStorage；http 模式 fetch 打 POST /api/nlp/confirm-batch。兩個轉接器的簽章一樣，上層完全無感。
3
Controller · router 收下並驗證
Pydantic schema 驗欄位型別；core/deps.py 從 JWT 取出目前使用者； services/permission.py 確認這個人有沒有權限寫這筆。驗不過就 403，不進 service。
4
Controller · service 執行商業邏輯
寫入 transactions，同時把「模型原本解析的值」與「使用者改成什麼」 一起寫進 nlp_parses。這一步就是資料飛輪的入口。
5
Model · SQLAlchemy 落地
交易提交進 PostgreSQL。金額欄位是 NUMERIC(14,2)， 不用浮點數——財務系統用 float 會有進位誤差。
6
回程 · 重算後回傳
router 回 {created: 5}，前端接著重打 GET /api/summary——總覽的數字一律由後端重算， 前端不自己加總，否則兩個畫面遲早會對不起來。
為什麼強調「金額由後端算」

前端自己加總看起來比較快，但只要有兩個地方各自加總， 數字對不起來只是時間問題。這個專案在原型階段就踩過一次： 我的總覽用明細加總、家庭總覽用成員表，同一個人出現兩個支出數字。

1帳號與家庭角色分開 users 是登入身分，family_members 才是角色——一個人可以同時是甲家的管理者、乙家的成員
2監管關係獨立成表 guardianships 有起訖時間。解除監管是設 ended_at 而不是刪除，因為稽核要看得到歷史
3nlp_parses 是資料飛輪的核心 記下原始輸入、模型輸出、使用者修正值，既是評測來源也是下一輪訓練資料
4advices.basis_json 存的是後端算好的數字 不是模型生成的——這樣使用者才驗算得了
5金額一律 NUMERIC(14,2) 不用浮點數。財務系統用 float 會有進位誤差，對不起來的帳最難查
安全與隱私

password_hash 用 bcrypt 或 argon2，絕不存明碼。 sessions 只存 refresh token 的雜湊，登出就是設 revoked_at。
audit_logs 記錄「誰看了誰的資料」——監管功能一旦存在，就必須有紀錄可查， 否則權限會變成沒人管的黑箱。

LLM 的部分另外寫成一份獨立文件——那邊要談模型選型、訓練參數、 工具定義與評測指標，內容性質跟這份手冊差太多，放在一起兩邊都不好讀。

為什麼這份手冊裡看不到模型的細節

題目要求自行微調開源模型、而且要有 function calling， 那條路的技術決策（挑哪顆模型、QLoRA 怎麼設、五個工具各自為什麼存在、 沒有 GPU 要怎麼上線）自成一個題目。
這份手冊講的是系統本身：功能、API、架構、分工。兩份分開看比較清楚。

10

分工心智圖

不是「一個做前端、一個做後端」，而是每人吃一條完整的功能模組—— 從資料表、API、畫面，一路到該模組自己的 LLM。 填上名字後按儲存（存在你自己的瀏覽器）。要給組員看，按複製分享連結，對方打開就會帶著這份名單。

連線上的數字是該分支的 API 支數 橘色＝該模組自己的 LLM 工作 ⚑ 第 1 週要凍結的跨模組契約
尚未儲存過
這樣切的三個好處

責任清楚——某個畫面壞了，知道找誰。
可以平行動工——四個人各改各的檔案，衝突少。
每個人都碰得到 LLM——這是任務的硬性要求，垂直切片自然做到， 不需要另外指派一個「模型負責人」。LLM 的部分各自在自己的分支下微調， 主要的分工還是落在後端模組上。

⚑ 分類體系是唯一的跨模組阻塞點

成員3 定的分類體系，成員2 要寫進 prompt、成員4 做建議時要用。 第 1 週就要凍結，其他兩份契約各模組自己就能定。
