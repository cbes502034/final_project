檔案系統說明書

打開一個沒看過的專案，最讓人不知所措的就是「東西到底放在哪裡」。 這份文件把每個資料夾走一遍，講清楚它放什麼、不放什麼， 最後給一張「我要改某某功能，該打開哪個檔案」的對照表。

01

為什麼要分資料夾

四個人同時改一個專案，資料夾就是分界線。沒有分界線， 就會變成每天都在解 git 衝突。

❌ 全部擠在一起

project/
  index.html
  app.js
  server.py
  models.py
  utils.py
  utils2.py
  helper.py
  「那個算錢的函式在哪？」
  「呃…utils 還是 helper？」

✅ 照職責分

project/
  frontend/     畫面
  backend/      資料與規則
    app/
      routers/  收請求
      services/ 做事
      models/   存什麼
  「算錢的？services/analytics.py」

分資料夾真正解決的三件事

問題資料夾怎麼解決
找不到東西 路徑本身就是分類。看到 services/analytics.py 你就知道它是商業邏輯、跟統計有關
四個人一直衝突 每個人只改自己資料夾裡的檔案，git 幾乎不會撞到
不知道能不能改 「這是誰的？」看檔頭第一行就有負責人。 toolkit/ 底下的不要改
02

前後端分離是什麼意思

這個專案最上層只有兩個資料夾：frontend/ 和 backend/。 它們是兩個獨立的程式，各自能單獨跑起來。

frontend/backend/
語言HTML / CSS / JavaScriptPython
跑在哪使用者的瀏覽器我們的伺服器
誰看得到原始碼所有人（按 F12 就看得到）只有我們
負責畫面、互動、收集輸入資料、權限、計算、模型
部署靜態檔案，走 CDNPython 服務
怎麼溝通 只透過 HTTP + JSON，沒有別的管道
最重要的一個推論：前端的程式碼使用者全都看得到、也改得動

所以任何「檢查」寫在前端都等於沒寫。
「只有管理者能刪除」「金額不能是負數」「這個人看不到那筆資料」—— 這些前端可以做（體驗比較好，不用等伺服器回應）， 但後端一定要再檢查一次。
前端的檢查是「防止使用者打錯字」，後端的檢查才是「防止有人作弊」。

分離帶來的好處

可以各自開發。 前端在 mock 模式下不需要後端就能跑完整的畫面； 後端用 /docs 就能試打，不需要前端。
可以各自部署。 改個文字只要重新發布前端，後端不用動。

04

前端逐層看

為什麼沒有 node_modules、沒有 build

這個前端沒有用任何框架，也沒有建置步驟。 改完 CSS 存檔、按重新整理就看得到，不用等編譯。 

python -m http.server 5174 --directory frontend

一行就跑起來了。這是有意識的取捨——一個月的專題， 三個人沒寫過專案，學 React + Vite 的時間拿去做模型比較划算。

js/api.js —— 整個前端最重要的檔案

所有資料都從這裡進出，沒有第二條路。 畫面要資料就呼叫 API.summary()，它不知道資料從哪來。 

        app.js（畫面）
             ↓ API.summary()
        api.js
        ├─ mock 轉接器 → 讀 data.js（假資料）
        └─ http 轉接器 → fetch 真後端

切換方式是改 index.html 的一行： 

<meta name="api-base" content="">                        留空 = mock
<meta name="api-base" content="https://…onrender.com">   填上 = 真後端
這個設計讓四個人可以平行動工

兩個轉接器的簽章完全一致，所以可以一支一支路由慢慢接—— 後端做好哪支就改哪支，不必等全部完成。
而且前端在 mock 模式下功能是完整的，後端還沒開始就能展示。

css/ 的兩個檔案分工

檔案放什麼什麼時候改
tokens.css 顏色、字體、圓角、陰影這些設計決定 要換整體配色時。改一個值，全站跟著變
app.css 各個元件長什麼樣：卡片、按鈕、表格 加新元件、調版面時

⚠️ 不要在 app.css 裡寫死顏色。 要用 var(--accent) 這種權杖，不然改配色時要翻遍整個檔案。

05

後端逐層看

後端分成四層。每一層只跟相鄰的層講話，這是整個結構的核心規則。 

routers/    收請求、驗權限、回結果      ← 不寫計算邏輯
    ↓
services/   真正做事：計算、規則         ← 不碰 HTTP
    ↓
models/     資料表長什麼樣               ← 不寫商業邏輯
    ↓
PostgreSQL

schemas/    橫跨在旁邊：定義 API 進出的形狀

models/ 和 schemas/ 差在哪？這題最多人搞混

回答的問題例子
models/ 資料庫裡存什麼 User 有 password_hash
schemas/ API 收送什麼 UserResponse 沒有 password_hash
分開的好處立刻看得到

使用者資料表一定要存密碼雜湊，但任何一支 API 的回應都不該把它送出去。
兩者分開之後，你不可能「不小心」把密碼雜湊回傳給前端—— 因為 response model 裡根本沒有那一欄，FastAPI 會自動過濾掉。

為什麼 routers/ 不寫邏輯

❌ 全寫在路由裡

要測「存款目標超支的判斷對不對」，你得起一個 HTTP 請求、 準備 token、準備資料庫……測一個算式要準備半天。

✅ 邏輯放 services/

savings_status(income, expense, goal) 是純函式， 直接呼叫就能測，一秒跑完。

ownership.py —— 分工的單一事實來源

「誰負責哪些路由、哪些檔案」寫在這個檔案，不是寫在文件裡。 它是程式讀得到的，而且 pytest 會檢查它有沒有跟程式碼走散。 

cd backend
python -m app.ownership      印出分工表 + 進度條
06

toolkit/ 工具箱

這個資料夾跟其他資料夾的差別：它已經寫好了。 你 import 來用，不用改也不用讀懂內部。

檔案包住什麼你會用到的
config.pypydantic-settings settings.database_url
db.pySQLAlchemy Base、get_db
passwords.pypasslib / bcrypt hash_password、verify_password
tokens.pyPyJWT make_access_token、read_access_token
deps.pyFastAPI 依賴 current_user_id、paging
errors.pyHTTPException not_found、forbidden、unauthorized
period.py日期計算 month_range、recent_months
money.pyDecimal to_decimal、ratio、quantize
images.py圖片驗證 validate_avatar、from_data_uri
三個約定

1. 不要改 toolkit/ 裡的東西。 有問題在群組講，改了別人會踩到。
2. 不要在裡面寫跟「記帳」有關的邏輯。 這裡的東西換一個題目也要能用。記帳規則寫在你們的 services/。
3. 金額一律走 money 模組，不要用 float。 浮點數累加會產生 12345.670000000002 這種結果。

怎麼查一個工具怎麼用

python -c "from app.toolkit import period; help(period.month_range)"

每支函式都寫了參數、回傳、丟出什麼例外、範例。 或是直接看 tests/test_toolkit.py—— 測試是最好的使用範例，而且保證是對的。

07

一個請求的旅程

跟著「使用者按下確認並寫入 5 筆」走一遍，你就知道每個檔案在哪一步出場。

1
frontend/js/app.js
使用者按下按鈕。把畫面上五列的欄位收回來， 呼叫 API.nlpConfirmBatch(items)。前端不做任何金額運算。
2
frontend/js/api.js
決定送去哪裡。mock 模式寫進 localStorage； http 模式 fetch 打 POST /api/nlp/confirm-batch。
3
backend/app/main.py
CORS 檢查通過，把請求交給對應的 router。
4
backend/app/toolkit/deps.py
在路由執行之前驗證 token，取出使用者 ID。 驗不過直接回 401，路由一行都不會跑。
5
backend/app/schemas/nlp.py
Pydantic 驗證送進來的資料格式。 欄位少了、型別錯了，自動回 422，你不用寫驗證程式碼。
6
backend/app/routers/nlp.py
路由本體。只做三件事：確認權限、呼叫 service、回結果。
7
backend/app/services/permission.py
這個人能不能寫這筆？不能就丟 errors.forbidden()。
8
backend/app/models/transaction.py ＋ nlp.py
寫進 transactions，同時把「模型原本解析的值」 和「使用者改成什麼」寫進 nlp_parses。這一步是資料飛輪的入口。
9
回程
router 回 {"created": 5}， 前端接著重打 GET /api/summary 拿新的數字。
總覽的數字一律由後端重算，前端不自己加總。
為什麼強調「前端不自己加總」

前端自己加比較快，但只要有兩個地方各自加總，數字對不起來只是時間問題。
這個專案在原型階段就踩過一次：我的總覽用明細加總、家庭總覽用成員表， 同一個人出現兩個支出數字。

frontend/index.html 裡的 ?v=19 是給瀏覽器看的快取版號。 不加的話使用者會繼續看到舊版，你會以為部署沒生效。
另外 Render 的 CDN 對 HTML 有 5 分鐘快取， 改 HTML 之後線上最多會慢 5 分鐘才看到。急著驗的話網址後面加 ?cb=1。

09

命名規則

四個人用同一套，讀別人的程式碼才不用一直轉換。

東西寫法例子
Python 檔案、函式、變數小寫底線 savings_goal、month_range()
Python 類別大駝峰 Transaction、SavingsGoal
Python 常數全大寫 MAX_BYTES、WARN_RATIO
資料表小寫底線複數 transactions、savings_goals
API 路徑小寫連字號複數 /api/savings-goal
JSON 欄位小駝峰 savingsGoal、avatarUrl
JavaScript 函式、變數小駝峰 nlpParseBatch、savingsLevel
CSS classBEM 風格 .card__title、.nav__i--out
Git 分支成員代號 + 領域 m2-ledger
Python 用底線、JSON 用駝峰，這個轉換要在 schemas/ 做

Python 的慣例是 savings_goal，JavaScript 的慣例是 savingsGoal。兩邊都照自己的慣例來， 在 Pydantic 模型上設定別名自動轉換：

class SavingsOut(BaseModel):
    savings_goal: int = Field(alias="savingsGoal")
    model_config = ConfigDict(populate_by_name=True)

不要讓前端遷就後端，也不要反過來。 兩邊各自寫得自然，轉換集中在一個地方。

10

什麼不進版控

__pycache__/        Python 的編譯快取，每台機器都不一樣
.venv/  venv/       虛擬環境，幾百 MB
.pytest_cache/      測試快取
.env                ★ 環境變數，裡面有密碼和金鑰
*.db                本機的資料庫檔案
.DS_Store           macOS 自動產生的
.env 絕對不可以 commit

裡面有 JWT_SECRET——拿到它的人可以偽造任何人的登入權杖。
而且 git 的歷史刪不掉：就算你下一個 commit 把它刪除， 之前那個版本還在歷史裡，任何人 clone 下來都找得到。
真的不小心 commit 了，唯一的補救是立刻換一組新的密鑰， 不要以為刪掉檔案就沒事了。

要給別人看「需要哪些環境變數」，用 .env.example—— 它只有變數名稱和說明，沒有真正的值，所以可以進版控。
